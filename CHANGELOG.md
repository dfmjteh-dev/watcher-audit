## [1.0.0] — 2026-11-13

Первый публичный релиз: исходный код открыт под AGPL-3.0 (коммерческая
лицензия — `COMMERCIAL.md`), релизы — в `dfmjteh-dev/watcher-audit`. Проект в
активной разработке. Сервер 1.0.0, агенты 1.0.0 (Windows, Linux, Android).

### Важно при обновлении

- **Агенты старше 0.16 больше не обновляются на месте.** Убран код перехода
  с 0.15 и старше: перевод задач GuardRepair с PowerShell на лаунчер, заглушки
  скриптов для проверки Guard 0.15, снятие задач `WatcherCapture`/`WatcherUploader`
  (схема до 0.9), понижение MSI ниже 0.16. Станцию со старым агентом — удалить
  агента и поставить заново из комплекта. Агенты 0.16.x обновляются как обычно:
  база восстановления для защиты, включённой обновлением с 0.15, по-прежнему
  закрепляется при первом обновлении.


### Добавлено

- **Android-агент собирается и обновляется вместе с сервером, как Windows и
  Linux.** Релиз приносит APK без подписи; `install-server.sh` при первой
  установке выпускает ключ подписи APK сервера (`/root/watcher-keys/android-apk.p12`),
  при каждой сборке комплекта подписывает им APK (zipalign + apksigner) и
  загружает в «Обновления». Ключ тот же на всех обновлениях — телефоны
  обновляются без переустановки. Раньше APK подписывался вручную отдельным
  ключом и в установочный архив релиза не попадал.
  Устройства, поставленные с прежним ключом, обновятся только после
  переустановки агента (подпись APK другая — так требует Android).


### Удалено

- Переадресация адресов веб-UI до 0.9 (`#/fleet`, `#/terminal`, `#/h/<хост>`,
  `#/groups`, `#/users`, `#/audit`, `#/config/...`) — открывайте `#/hosts`,
  `#/console`, `#/settings/...`.
- **Общий токен агентов (`ApiToken`) больше не принимается.** Агенты — только
  по своей учётке (токен регистрации, Настройки → Агенты). Убраны настройки
  сервера `ApiToken` и `AllowLegacyApiToken` (в старом `.env` игнорируются),
  свойство MSI `APITOKEN`, `--api-token` у `watcher-agent-setup` и Linux-скриптов,
  `ApiToken` в конфигах агентов. Хост без учётки в «Хостах» помечен «без учётки».
  `AllowAnonymousAgents` остаётся — только для разработки и тестов.


### Исправлено

- **Установка без Docker больше не уходит молча в режим systemd.**
  `install-server.sh` без Docker объясняет, что выбрать, и в терминале
  предлагает поставить Docker Engine из официального репозитория Docker;
  `--install-docker` — то же без вопроса. Без терминала и без флага —
  понятная ошибка с готовыми командами.
- **Режим `--systemd` на Debian 12 не запускал HTTPS** (с 0.14.4): Caddy 2.6.2
  из пакетов не понимает `trusted_proxies`. Установщик теперь ставит Caddy 2.7+
  из официального репозитория Caddy, если в apt он старее.
- **Консоль: команды живой SSH-сессии показывались слитно** («uptimedf -h /exit»).
  Enter в bash/readline — CR, pam_tty_audit сохраняет его как есть, а перенос
  строки в веб-UI делался только по LF. Теперь CR и CRLF показываются как
  перенос — в списке «Консоль», в панели ввода и в поиске с подсветкой; уже
  записанные сессии исправляются без миграции (данные не менялись).
- **Режим `--systemd` на Debian 12 собирает комплект агентов без Docker.**
  Требование osslsigncode 2.6 осталось от подписи PowerShell-скриптов, которых
  с 0.16 нет; под ним пряталась ошибка wixl 0.101 с абсолютными путями —
  `build-msi.sh` передаёт путь к файлам относительно `.wxs`.
- В веб-UI при создании токена регистрации Windows-подсказка вела на
  несуществующий с 0.16 `install.ps1` — теперь команда `msiexec`.

## [0.16.0] — 2026-11-12

### Важно при обновлении

Сервер 0.16.0, агенты 0.16.0 (Windows, Linux, Android). Сначала сервер
(Настройки → Сервер — загрузить `watcher-server-0.16.0.tar.gz`, или
`install-server.sh`), он сам пересоберёт комплект агентов; потом группам —
целевая версия 0.16.0 в «Обновлениях».

- **После обновления все Windows- и Linux-агенты станут защищёнными
  (GuardRepair)**, в том числе ставившиеся 0.15.x без защиты: Windows — из MSI
  обновления, Linux — сам по ключу с сервера. Остановить или удалить агента на
  станции после этого можно только командой с сервера (Хост → «Обслуживание
  защищённого агента»). Базу восстановления такие агенты получают с сервера
  при первом групповом обновлении после 0.16.0.
- **Обновление сервера 0.15.x через веб может зависнуть** на «обновление
  поставлено в очередь»: помощник на хосте (версии 0.15.x) просыпается раньше,
  чем сервер дописал заявку, и systemd останавливает его по лимиту перезапусков.
  Если статус не меняется дольше пары минут, на хосте сервера выполните
  `sudo systemctl reset-failed watcher-server-update.service watcher-server-update.path && sudo systemctl restart watcher-server-update.path`
  — помощник подхватит уже загруженный архив. С 0.16 исправлено.

- Windows-агент обновляется только MSI: пакеты `windows-zip`, `update.ps1` и
  переход `C:\Watcher` через групповой ZIP убраны (на проде все Windows-агенты
  из MSI). Станция, установленная `install.ps1` без MSI, обновлений больше не
  получает — переустановите её из MSI комплекта. Комплект агентов стал меньше
  на ~550 МБ: zip-пакета обновления в нём больше нет.
- Windows-агент 0.16 начнёт выгружать транскрипты PowerShell задач
  планировщика, служб и SQL Agent. В их выводе бывают пароли и токены. Если
  хранить их не нужно, отметьте в настройках группы «Консоль и SSH» → «Не
  сохранять PowerShell, запущенный… планировщиком заданий и службами».
  Прежние потери `transcript-no-4688` миграция отметит принятыми.
- MSI агента больше не несёт внутри копию общего MSI: комплект и пакет
  автообновления Windows вдвое меньше (~240 МБ вместо ~470). Базой
  восстановления защиты становится сам MSI по подписи `watcher-agent.msi.sig`,
  которая лежит рядом в комплекте — **кладите её на шару GPO вместе с MSI**.
  Без неё агент ставится и защищается, а базу защита получит с сервера при
  первом групповом обновлении.
- MSI агента 0.15.2 (релизный и из комплекта сервера) не устанавливается —
  после обновления сервера комплект агентов пересоберётся автоматически;
  назначайте группам новую версию, а не 0.15.2.

### Изменено (возврат на старую версию агента)

- Агенты, защиту которых включило обновление с 0.15.x, получают базу
  восстановления с сервера: в ответ на отказ Guard «нет базы» сервер выдаёт
  пакет текущей версии хоста, Guard закрепляет его без переустановки, затем идёт
  обычное обновление до цели. Без этого такие агенты не обновлялись бы вовсе.

- Откат агентов — как обновление: задайте группе в «Обновлениях» более старую
  целевую версию. MSI с 0.16 допускают понижение (одна транзакция Windows
  Installer); защищённые агенты 0.16+ возвращаются и на 0.15.1–0.15.x — Guard
  удаляет текущую версию и ставит старую с теми же снимками и проверками, при
  сбое возвращает текущую. Где понижение невозможно (незащищённый Windows на
  MSI 0.15.x, защищённые агенты до 0.16 на rpm/0.15.x MSI, ниже 0.15.1) — у
  хоста видна причина `blocked …` вместо бесконечных неудачных попыток.

### Изменено (защита Linux-агентов)

- Linux-агент без защиты включает её сам, как Windows-агент при обновлении MSI:
  сервер передаёт ключ обслуживания из комплекта, заверенный ключом обновлений
  (`certs/maintenance-key.sig`, собирается `install-server.sh`), агент сверяет
  подпись и запускает `GuardRepair setup`. Linux-агенты 0.15.x станут
  защищёнными после обновления до 0.16 — раньше для этого нужна была
  переустановка из комплекта. Комплект нужно пересобрать (это делает обновление
  сервера через install-server.sh).
- `GuardRepair setup` на Linux больше не требует подписанного пакета-базы: без
  него защита включается, база приходит с сервера с первым обновлением.

### Изменено (обслуживание защищённого агента)

- Панель «Разрешённое обслуживание» переделана в «Обслуживание защищённого
  агента»: кнопки действий с пояснением, что и когда произойдёт (остановить на
  15/30/60 минут, возобновить, восстановить, удалить с подтверждением); учётка
  выбирается сама, файл для онлайн-команды не скачивается; ход команды —
  лентой «выдано → получено агентом → выполнено/ошибка» человеческим текстом.
  Смена ключа и выбор учётки — в «Дополнительно».
- Отдельный мастер «Станция без связи»: файл разрешения, пакет для обновления
  и готовая команда `GuardRepair submit` для Windows или Linux.
- `GuardRepair submit` печатает понятный итог (принято, до какого времени,
  как проверить; либо почему не принято — просрочено, не для этой станции, уже
  выполнено). Новая команда `GuardRepair status` — состояние защиты, база
  восстановления, ожидающие и последние выполненные разрешения.

### Исправлено (защита на Linux без libicu)

- GuardRepair на Linux без libicu (минимальные AlmaLinux/Rocky/RHEL) аварийно
  завершался при включении защиты: «Couldn't find a valid ICU package». Собран,
  как остальные агенты, без зависимости от ICU.

### Исправлено (обновление сервера из веб-интерфейса)

- Заявка помощнику обновления больше не создаётся во временном файле внутри
  `requests/`: помощник, разбуженный этим файлом, выходил ни с чем, systemd
  перезапускал его по кругу и останавливал (`start-limit-hit`), и обновление
  висело в очереди. Помощник теперь дожидается заявки от прежних версий сервера.

### Исправлено (установка Windows)

- Обновление незащищённого Windows-агента останавливалось на подготовке отката
  («Expected one previous MSI product»), если в Windows Installer осталась
  осиротевшая регистрация агента от сбойной установки. Теперь учитывается только
  установленный продукт.

- Переустановка MSI той же версии падала, если от прошлой установки остался
  завершённый журнал `WatcherUpgradeRecovery\<ProductCode>` (phase committed):
  установщик пытался вернуть из него конфиг. Теперь учитывается только
  незавершённый журнал (phase prepared).
- Защита Linux-агента работает без shell-скриптов: `setup-guard.sh` заменён
  командой `GuardRepair setup` (её вызывают `watcher-agent-setup` и postinstall
  пакета), `recover.sh` — постоянным лаунчером
  `/var/lib/watcher/guard/GuardRepair tick` в `watcher-guard.service`. Станции 0.15.x
  переходят на лаунчер при обновлении пакета; откат пакета возвращает прежний
  `recover.sh` прежним postinstall. Офлайн-разрешение на Linux:
  `sudo /var/lib/watcher/guard/GuardRepair submit файл.json`.
- Обновление Windows-агента **без защиты** (снимок и откат при сбое,
  `WatcherUpgradeRecovery`) работает без PowerShell: бывший
  `installer/legacy-msi-recovery.ps1` перенесён в `GuardRepair legacy-msi-prepare /
  legacy-msi-restore / legacy-msi-recover`. Попутно исправлено:
  - ручное обновление от администратора падало на регистрации временной
    SYSTEM-задачи (владельца SYSTEM администратор назначить не может);
  - с 0.16 MSI всегда кладёт `WatcherGuard\setup` — это больше не считается
    «незавершённой установкой Guard» и не блокирует обновление и откат;
  - откат больше не включает защиту, если в прежний MSI комплекта зашит ключ
    обслуживания: станция возвращается такой, какой была;
  - сертификат подписи комплекта (самоподписанный) больше не обязан быть в
    «Доверенных корневых» на станции: достаточно, чтобы прежний MSI и exe агента
    были подписаны одним сертификатом;
  - архив прошлой попытки (`<код>.previous-*`, 200+ МБ) удаляется после
    успешной подготовки;
  - хеш `install.ps1` прежней версии снимается, только если файл есть, иначе
    обновление установок 0.16+ останавливалось бы на подготовке.

### Изменено (транскрипты PowerShell)

- Windows-агент выгружает **каждый** транскрипт PowerShell, а не только SSH, с
  меткой происхождения (SSH, планировщик и службы, SQL Agent, рабочий стол,
  PowerShell Remoting, «не определено») и режима (интерактив или одна
  команда). Неопознанный транскрипт больше не становится потерей
  `transcript-no-4688` — он выгружается с меткой «не определено» через 10 минут
  после закрытия; копии из карантина прежних версий тоже выгружаются.
- «Консоль»: фильтр «Происхождение» (по умолчанию без автоматизации), бейджи
  происхождения, SSH-команды Windows (`ssh host "…"`, `-EncodedCommand`,
  `-File`) — «без терминала» и в фильтре «Тип». `-EncodedCommand` показывается
  расшифрованным, исходник — по раскрытию; поиск находит и по расшифровке.
- Настройка группы/хоста «Не сохранять PowerShell, запущенный…»
  (`skipTranscriptOrigins`). По умолчанию сохраняется всё.
- «Потери» хоста: у каждой причины — что сделать.

### Исправлено

- Обновление Guard на Windows не могло заменить запущенный лаунчер
  `WatcherGuard\GuardRepair.exe` (UnauthorizedAccessException, откат
  обновления): занятый файл теперь переименовывается в `*.old` и удаляется
  на следующем тике. Сбой лаунчера пишется в
  `C:\Program Files\WatcherGuard\logs\launcher.log` вместо аварийного
  завершения без текста (0xE0434352).
- Групповое обновление защищённого Windows-агента 0.15.x падало (1603) и
  откатывалось: `install.ps1` читал `Watcher.SessionService.json` до того,
  как Guard вернул конфиги, стёртые удалением прежней версии MSI. Ошибка была
  и в 0.15.2. Найдено на стенде; на проде так упало бы обновление всех
  защищённых хостов.
- `install.ps1` и `GuardRepair install` пишут собственные журналы
  (`C:\ProgramData\Watcher\logs\install-*.log`,
  `C:\Program Files\WatcherGuard\logs\install-*.log`): прежний
  `C:\Windows\Temp\watcher-install-ca.log` при неудачном обновлении
  перезаписывает откат, и причина сбоя на станции терялась.

- MSI агента 0.15.2 не ставился нигде: msiexec отвечал 1605 («действие
  допускается только для установленных продуктов») ещё до начала установки,
  журнал install.ps1 не появлялся. msibuild вставлял новые свойства в конец
  таблицы Property с переиспользованными номерами строк, а Windows Installer не
  загружает таблицу с нарушенным порядком ключей (2211/2229) и не находит
  ProductCode. msiinfo такой MSI читал без ошибок. Сборка теперь упорядочивает
  строки всех таблиц после правок (`installer/msi-table-order.py`) и проверяет
  порядок; то же — для MSI, настроенного на сервер.

### Изменено

- Версия агента показывается без хвоста коммита сборки (`0.15.1`, а не
  `0.15.1+3d60033…`): агенты собираются без него, сервер отрезает его у
  прежних агентов при приёме и в уже сохранённых записях (миграция 32).
- «Обновления»: убран раздел «Доступные версии» — новая версия сразу видна в
  выборе целевой версии группы. Список пакетов с удалением перенесён в
  свёрнутый блок «Пакеты на сервере и ручная загрузка» внизу страницы.
- Тепловая карта «день недели × час» в отчёте активности заменена лентой
  активности за период: площадной график по часам (период до 14 дней) или по
  дням, выходные выделены фоном, значение — в подсказке у перекрестия (мышь или
  стрелки клавиатуры), под графиком — табличный вид. API отчёта: поле `heatmap`
  заменено на `perHour` (ключ `yyyy-MM-ddTHH`, зона сервера).
- GuardRepair на Windows работает без PowerShell: задача планировщика
  запускает постоянный лаунчер `C:\Program Files\WatcherGuard\GuardRepair.exe tick`
  (бывший `recover.ps1`), права (бывший `protect.ps1`) и включение защиты
  (бывший `guard-install.ps1`, теперь `GuardRepair install`) — в самом
  GuardRepair. Скрипты `guard-*.ps1` убраны из MSI. У агентов 0.15.x задача
  переводится на лаунчер после успешного обновления, на тике новой версии.
  Офлайн-разрешение: `"C:\Program Files\WatcherGuard\GuardRepair.exe" submit файл.json`.
- Установка Windows-агента без PowerShell: custom actions MSI вызывают
  `GuardRepair agent-install` / `agent-uninstall` (бывший `install.ps1` —
  конфиги, CA, служба, аудит консоли). MSI кладёт GuardRepair в
  `C:\Program Files\WatcherGuard\setup`, а не в каталог агента; в
  `C:\Program Files\Watcher` остаются только Capture, SessionService, ffmpeg и
  конфиги. `install.ps1`, alias `Watcher.Guard.exe` и
  `installer/test-windows-policies.ps1` убраны. Обновление без защиты
  запускает MSI из копии службы (`--apply-msi-update`), удаление без MSI —
  `sc stop`/`sc delete`. Журнал установки —
  `C:\ProgramData\Watcher\logs\install-*.log`. Прежние файлы каталога
  агента (`install.ps1`, `update.ps1`, `GuardRepair.exe`, `guard-*.ps1`) Guard
  убирает из политики и удаляет после фиксации обновления — только заглушки и
  файлы с хешем из своей политики.

## [0.15.2] — 2026-11-09

Версия сервера и агентов: **0.15.2**.

### Исправлено

- Установка Windows больше не запускает PowerShell Add-Type/csc.exe для

### Исправлено

- **Сегмент при непрерывном движении на экране рос без предела.**
  `MaxSegmentSeconds` (5 мин) проверялся только на кадрах без движения:
  видео или анимация на экране давали один файл в гигабайты (на проде —
  станции `WS-FIO-FO*`). Теперь сегмент закрывается по сроку на любом кадре

- **Файл больше предела сервера блокировал очередь агента.** Сервер
  отвергал его (413, `MaxUploadSizeMb` = 512 МБ), агент отправлял его заново
  каждые ≤5 мин — нагрузка на сеть, и ничего записанного позже не
  выгружалось. Сервер сообщает предел в ответе heartbeat (`maxUploadBytes`),
  агент такой файл не отправляет (и при 413 от старого сервера), а удаляет —
  с потерей «too-large» в журнале потерь хоста.

### Добавлено

- **Удаление выбранных записей.** На вкладках «Видео» и «Консоль» хоста
  администратор отмечает сегменты или сессии и удаляет их кнопкой «Удалить
  выбранное» (с подтверждением; вывод сессии — вместе с ней). Каждое удаление

  hold не удаляются.
- **Подсказки заголовков окон** в конфиге: «Пауза / запись, когда заголовок
  окна содержит» выбираются из заголовков, уже встречавшихся на хосте
  (группе), как и программы; запятая в заголовке значение не делит. У
  браузеров подсказка — только название страницы: без «и ещё 3 страницы» и
  «— Личный: Microsoft Edge» (правило «содержит» сработает при любом числе

- **Загрузка сервера на «Обзоре».** Панель «Сервер»: CPU и память хоста
  сервера, приём и отдача по сети, сколько из этого — сам Watcher, и графики
  за последний час (замер раз в 15 с из `/proc`). В Docker сеть — трафик
  контейнера Watcher, CPU и память — всего хоста.
- **Страницы обновляются сами.** «Обзор», «Хосты», страница хоста, «Агенты»,
  «Обновления», «Хранилище», журнал потерь и сегменты видео за сегодня
  подгружают новое раз в 15–60 с, пока вкладка открыта, — без сброса плеера и
  без «Загрузка…». Не обновляются сами формы конфига и список «Консоли»
  (каждый его запрос пишется в журнал доступа) — там кнопка «Обновить».
- **Страница входа:** внизу версия сервера и «Who. What. When. In detail.»
  вместо надписи о журнале доступа.
- **Сколько станции стоит агент.** Агент присылает с heartbeat CPU и память
  всех своих процессов (служба/выгрузка, запись экрана в сессиях, консольный
  агент и их ffmpeg — чужой ffmpeg не считается) и размер очереди
  невыгруженного. В «Хостах» — колонка «Агент» (значок ⏳ — есть очередь), в
  «Инфо» хоста — строка «Агент на станции». Нужны агенты 0.13.

- **Пользователь хоста виден всегда.** В «Хостах» — колонка «Пользователь»
  (последний, кто попал в запись видео или консоли) и поиск по ней, в «Инфо»
  хоста — строка «Последний пользователь». В списке сегментов видео колонка
  «Пользователь» теперь есть всегда, когда он известен — раньше она

  умолчанию) удаляются и видны в «Потерях» хоста. Срок задаётся в конфиге
  группы или хоста («Хранение на станции», `queueMaxAgeDays`, 0 — без срока)
  и действует и после перезапуска агента без связи с сервером.

- **Дошёл ли конфиг.** В «Инфо» и на странице конфига хоста видно, какой
  конфиг действует (группа + настройки хоста), получил ли его агент и
  применила ли его запись экрана в каждой сессии пользователя (и пишет ли она
  сейчас). На странице конфига группы — на скольких хостах он уже действует;

- **Журнал потерь вместо счётчика.** Вместо красного числа «с перезапуска
  агента» — список: какой файл, за какое время запись, сколько весила и
  почему потеряна (не хватило места, сервер был недоступен дольше срока
  хранения, запись оборвалась и не восстанавливается, транскрипт PowerShell
  без аудита 4688). Кнопка «Принято» гасит значок до следующей потери;
  уведомления — на каждую новую потерю. Агенты старше 0.13 — по-старому,
  счётчиком.

- **Удаление хоста.** В «Инфо» хоста (только admin) — «Удалить хост» вместе
  со всеми записями, с подтверждением именем хоста и записью в журнал
  доступа. Агент на станции удаляет себя сам: сразу, если на связи, или когда
  вернётся (Linux — пакет, Windows — MSI), и не регистрируется заново.

- **Удаление отозванных учёток** в «Настройки → Агенты».
- **«Снять с записи».** Кнопка в шапке хоста (admin/operator): экран и/или

  значок «не пишется» с причиной; «Вернуть запись» — одной кнопкой. Для
  группы — секция «Пауза записи» в её конфиге.

- **Несколько мониторов и разные экраны — без искажений.** Раньше весь рабочий
  стол растягивался в заданный размер без сохранения пропорций: два монитора
  сжимались по ширине вдвое, экран 4:3 растягивался в 16:9. Теперь размер в
  конфиге — предел для одного монитора, пропорции сохраняются, маленький экран
  пишется как есть. В плеере у записи с несколькими мониторами — кнопки «все /
  1 / 2…»: показать один монитор крупно (Chrome и Edge; выбор запоминается для
  хоста). Подключили или отключили монитор — агент Windows это замечает
  (раньше размер запоминался при старте), сегмент начинается заново.

- **Кто и что на хосте.** В «Инфо» хоста — пользователи (кто попадал в видео
  и в консоль, сколько записей, когда последний раз) и время по программам за
  30 дней.
- **Конфиг выбором, а не вписыванием.** Пользователей и программы в правилах
  записи можно выбрать из тех, что уже встречались на хосте (или хостах
  группы), своё — вписать; расписание — сеткой «день × час» с готовыми
  вариантами (пн–пт 9–18, всегда).
- **«Записывать только когда активна программа».** Обратное паузе по
  программе: экран пишется только пока на переднем плане одна из выбранных
  программ (или окно с нужным заголовком); исключения действуют поверх.

- **Отчёты** (новый раздел, admin и viewer): активность ПК — сколько времени
  за период шла запись на каждом хосте, теплокарта «день недели × час»;
  самые используемые приложения — время на переднем плане, на скольких хостах
  и у скольких пользователей; самые активные пользователи — время, хосты,
  основные программы. Фильтры: период, группа, хост, пользователь, «только
  рабочее время (пн–пт 9–18)»; каждая таблица выгружается в CSV для Excel.
- **Служебные подключения в «Консоли».** Машина, которая ходит на машину по
  SSH по расписанию (сборщик LLDP раз в минуту, бот конфигов раз в 5 минут),
  больше не топит «Консоль» в сотнях одинаковых сессий в сутки. Правило в
  конфиге группы или хоста — пользователь, откуда (IP или подсеть) и с чего
  начинается каждая команда; у правила свой выбор: «скрывать» (запись
  сохраняется, в списке видна по «Служебные: показать», одинаковые подряд
  свёрнуты в «×N») или «не сохранять». Быстрее всего — кнопкой «Скрыть
  похожие» в открытой сессии (администратор): поля заполнены по сессии.
  Сессия совпадает, только если каждая её команда подходит под правило —
  чужая команда под той же учёткой и с того же адреса остаётся на виду.
  Правка правил сразу пересчитывает пометку уже записанных сессий;
  «не сохранять» задним числом ничего не удаляет.

  отмена). Кнопка «Сохранить» в строке группы убрана: её принимали за

- Настройки → Вход через AD: в проверке подключения поле называется просто
  «Логин».

### Исправлено

- **Windows: «Записывать только этих пользователей» не писал никого** у
  учётки Microsoft/Azure AD: запись сверяла список с именем профиля, а
  служба и сегменты — с именем сеанса (`abutakov`). Теперь везде имя сеанса.
- **Доменные учётки с точкой (a.butakov) не попадали в «кого записывать».**
  Запись экрана на Windows отправляла имя очищенным для файлов (`abutakov`):
  оно же было в подсказках и в списках, а сверялось с настоящим. Теперь в
  записях настоящее имя; сверка одна на службу, запись Windows/Linux и консоль —
  без регистра и домена (`AVZ\a.butakov`, `a.butakov@avz`), а уже
  сохранённое `abutakov` по-прежнему совпадает с `a.butakov`.
- **Windows: несколько мониторов с разным масштабом (125% + 100%)** —
  граница мониторов в записи не совпадала с кадром, и при выборе монитора
  в плеер попадала часть соседнего или обрезался свой. Запись теперь видит
  экраны в физических пикселях (Per-Monitor DPI V2).
- **Плеер:** выбранный монитор показывается в своих пропорциях на всю высоту
  плеера (раньше вписывался в широкую рамку всего кадра и выходил мелким);
  кадр нескольких мониторов рядом — плеер на всю ширину, список под ним.
- **Самоудаление агента Windows** удаляет и каталог агента целиком: после
  обновлений по zip в нём оставались `update.ps1` и `.rollback`, о которых
  MSI не знает.
- **«Скрыть похожие» для команд по SSH:** обёртка оболочки (`bash -c 'cmd'`)
  в записи `linux-exec` разворачивается в саму команду — правило по началу
  команды теперь подбирается и для таких сессий.

- **Агенты больше не требуют `libicu`.** На минимальной системе без неё
  (AlmaLinux 10, `debian:12-slim`) агент 0.12.2 падал при старте
  («Couldn't find a valid ICU package») и уходил в цикл перезапусков, а
  установка выглядела успешной. Агенты собраны без данных локалей
  (`InvariantGlobalization`), регистр кириллицы в правилах исключений работает
  как раньше.
- **`watcher-agent-setup` проверяет, что службы поднялись.** Если служба
  падает или перезапускается в первые секунды — печатает журнал и выходит с
  ошибкой вместо «Готово».
- **Пустой сегмент — не потеря.** Сегмент, в котором нет ни одного кадра
  (Capture остановлен сразу после старта: выход из системы, смена
  пользователя), удаляется без счётчика потерь — раньше такой файл в 28 байт
  давал красное «Потери сегментов» на ровном месте.
- **Причина записи «motion 0,52%» → «motion 0.52%».** Процент форматировался
  по языку станции: на русской Windows с запятой, на Linux с точкой. Теперь
  везде точка; уже сохранённые записи исправляет миграция БД 9, от старых
  агентов сервер приводит к точке при приёме.
- **Переименование машины больше не ломает выгрузку.** Раньше после смены
  имени (hostnamectl, «Свойства системы») каждый heartbeat и каждая запись
  получали `403 host does not match agent credential` и повторялись вечно:
  хост в веб-UI «пропадал», очередь на станции росла. Теперь сервер опознаёт
  агента по учётке: хост переименовывается вместе со всей историей, записи,
  сделанные до переименования, тоже уходят. Если новое имя уже занято другим
  хостом — хост остаётся под прежним именем, в журнале доступа —
  `agent.host-rename-conflict`.
- **Linux: оборванная запись экрана больше не теряется.** Linux-агент писал
  сегмент обычным mp4, индекс которого появляется только в конце, поэтому
  после выхода из сессии, ребута или падения файл не читался и уходил в
  «потери». Теперь, как на Windows, запись идёт фрагментами по секунде и
  восстанавливается до последнего фрагмента (`startReason: recovered`).
- **Windows и Linux: фрагменты сразу пишутся на диск.** Статичный экран
  кодируется в крошечные фрагменты, и ffmpeg копил их в буфере: при обрыве они
  пропадали вместе с ним, и восстанавливать было нечего (на опыте: без исправления —
  файл 28 Б, с ним — 50 кадров из 60).

  целиком: поменяли у хоста одно поле — остальные по-прежнему из группы. Ключа

  проверяет права администратора, а не падает молча в `msiexec /qn`.

- **Linux: запись экрана вставала после смены разрешения.** XShm-сегмент был
  под размер экрана на момент запуска; после смены разрешения (подстройка под
  окно консоли VM, второй монитор) снимок падал с `XShmGetImage failed`, и
  агент завершался. Теперь сегмент пересоздаётся под текущий размер (размер —
  у X-сервера, `XGetGeometry`, а не из кэша Xlib); если экран временно не снять
  — такт пропускается, сегмент закрывается, в логе одна строка.
- **Linux: после фатальной ошибки захват не перезапускался** — процесс выходил с
  кодом 0, и `Restart=on-failure` его не поднимал до следующего входа
  пользователя. Теперь код выхода 1.
- **Обновление пакета не обновляло обёртку вывода консоли** в `/etc` (её
  копирует `watcher-agent-setup`) — после автообновления на станции оставалась
  старая, без выгрузки идущих сессий кусками. Теперь `postinstall` обновляет её,
  если агент уже настроен.
- Вывод сессии, оборванной вместе с SSH-соединением (shell убит SIGHUP и не
  успевал записать итоговый `.json`), не выгружался вовсе — теперь агент
  закрывает такую запись сам, увидев, что shell завершился. Ввод такой сессии
  ядро сбрасывает уже после её закрытия — раньше он попадал в отдельную запись
  «unknown» с задвоенным вводом, теперь — в ту же сессию.

### Важно при обновлении

- **Автообновление включается ключом на станции.** Чтобы станции сами
  обновлялись с сервера, при установке этой версии передайте открытый ключ
  обновлений: `install.ps1 -UpdateKey …`, `msiexec … UPDATEKEY=…`,
  `watcher-agent-setup --update-key …`. Без ключа станция работает как раньше и
  обновляется вручную. Переход на автообновление — один раз вручную на этой
  версии, дальше — с сервера.
- **Ключ обновлений выпускается при установке сервера**: `install-server.sh`
  (в том числе при переустановке поверх, если ключа ещё нет) спрашивает пароль,
  прописывает открытый ключ в `appsettings.json` и печатает его для станций; для
  Docker Compose — шаг `new-update-key.sh --out ~/watcher-update-key --env .env`.
  **Закрытый ключ заберите с сервера** и удалите там — им подписываются пакеты.
- **`install.ps1 -RdsMode` удалён** (с 0.9.0 принимался и игнорировался). Скрипт
  или GPO, который его ещё передаёт, теперь получит ошибку PowerShell и ничего не
  установит — уберите параметр. `RDSMODE=1` у MSI и exe-бутстрапера ошибкой не
  стал: свойство просто ни на что не влияет.

- Обновление агентов с сервера (H2): Настройки → Обновления — загрузить пакет

  назначить группе целевую версию (сначала пилотной; откат — прежней версией).

  09:00-18:00», по часам станции) и исключённые программы и окна по заголовку.

- Активное окно рядом с видео (H9): агенты Windows и Linux пишут, какое окно
  было на переднем плане (программа и заголовок). В плеере видно окно в текущий
  момент и смены окна в сегменте, на вкладке «Видео» — поиск по окнам за всю
  историю хоста с переходом к моменту. Включено по умолчанию; в конфиге группы
  («Активное окно») — только программа или выключить. Поиск пишется в журнал
  доступа. Активность входит и в манифест выгрузки (H7). Старые агенты
  работают как раньше — без активности.

- Authenticode-подпись агента Windows (H3): `make-bundle.sh` подписывает
  `Watcher.Capture.exe`, `Watcher.SessionService.exe` и `install.ps1`, если
  задан `WATCHER_SIGN_PFX`. Подходит любой сертификат подписи кода; для своего

  Root) и раздача GPO — `docs/codesign.md`. Для ИБ заказчика — `docs/av-edr.md`:
  пути, процессы, поведение агента и что внести в исключения AV/EDR.

- Пакеты Linux-агента `.deb` / `.rpm` (H3): один пакет `watcher-agent` на экран
  и консоль/SSH, настройка — `sudo watcher-agent-setup --server-url …
  --enroll-token … [--users …]`, удаление снимает хуки PAM/bashrc. Экран из
  пакета пишется у любого пользователя рабочего стола (кого — решает сервер,
  `AllowUsers`/`ExcludeUsers`). `docs/install.md`, «Пакеты .deb / .rpm».
- Релиз (H3): Linux-агент (tar.gz, .deb, .rpm) прикладывается к GitHub Release;
  в релизах из CI `SHA256SUMS` подписан cosign (Sigstore, без ключа) —
  `docs/install.md`, «Проверка подлинности релиза» (0.10.0 — без подписи, см.
  выше).

- Выгрузка записей с проверяемой целостностью (H7): вкладка хоста «Выгрузка» —
  zip за период с видео и консолью, `SHA256SUMS` (хеши, посчитанные при приёме
  от станции — проверка `sha256sum -c`), `manifest.json` и записью в журнале
  доступа с хешем манифеста. Право выгрузки отдельное и по умолчанию выключено
  у всех, включая admin: выдаётся в «Пользователях» или группами AD
  (`Server__Ldap__ExportGroups`). Подробности — `docs/operations.md`, «Выгрузка
  записей».

- Вход через Active Directory / LDAP (H1): логин и пароль домена, роль по
  группам AD (с вложенными), LDAPS или StartTLS. Отключённый в AD пользователь
  теряет доступ сам — сессии перепроверяются раз в `RecheckMinutes`. Локальные
  учётки и аварийный `admin` остаются. Настройка — `docs/operations.md`, «Вход
  через Active Directory / LDAP».

- Резервная копия и восстановление (H5): `Watcher.Server --backup <каталог>
  [--include-blobs]` — снимок БД на работающем сервере, список файлов записей и
  манифест; `--restore <копия>` — на остановленном сервере, текущая БД
  откладывается рядом. Команды для Docker и systemd — `docs/operations.md`,
  «Резервная копия и восстановление».

- Встроенные алерты (H4) для установок без Prometheus: хост молчит дольше
  `HostSilentHours` (72 ч — станции выключают на ночь и выходные), неверные часы
  станции, потери сегментов, мало места на сервере, retention стоит. Каналы —
  webhook (Mattermost, Slack, Rocket.Chat, Telegram) и SMTP; настройки —
  `Server__Alerts__*`, `docs/configuration.md`, «Алерты».
- Экспорт журнала доступа в SIEM (H4): syslog RFC 5424 с CEF или JSON, UDP / TCP /
  TLS со своим CA. Отправка по курсору из БД — переживает недоступность SIEM и
  перезапуск сервера; настройки — `Server__Siem__*`, `docs/operations.md`,
  «Экспорт журнала доступа в SIEM».

### Важно при обновлении

- **Windows: только служба.** Capture запускает служба `WatcherSessionService` в
  сессии каждого пользователя, она же выгружает очередь (D1, D2).

  станции своя учётка (G1). Общий `ApiToken` работает как переходный путь
  (`Server__AllowLegacyApiToken`, по умолчанию включён); такие хосты помечены в
  «Хостах».

  `Server__AllowAnonymousAgents=true` (для dev).

  конфигами, но записей не видит; `viewer` видит записи, опционально только
  своих групп. Существующие пользователи остаются с прежней ролью.
- **Миграции БД.** Схема обновляется нумерованными миграциями; перед ними сервер
  кладёт копию `watcher.db.v<N>.bak`. База от более нового сервера — отказ
  старта, а не тихая порча (R12).
