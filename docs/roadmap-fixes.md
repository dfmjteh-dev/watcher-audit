Это отдельный трекер — не дублирует `docs/roadmap.md` (там фазы нового функционала).
Здесь — конкретные задачи на исправление несхождений документации с кодом и

указано иное в «Зависит от». При закрытии — переносить пункт сюда же со
статусом ✅ и короткой заметкой, что сделано (по аналогии с `roadmap.md`), не
удалять.

Примечание к конвенции `development.md` («без отдельного трекера задач», раздел
«Ветки и коммиты»): этот файл не создаёт отдельный issue-tracker, он — такой же
Markdown-файл в `docs/`, обновляемый тем же PR, что и фикс, как и `roadmap.md`.

- Добавить `RDSMODE`-property/variable в Package.wxs и Bundle.wxs, передать в
  custom action → `install.ps1 -RdsMode`.
- Проверить живьём на тестовом RDS-стенде (институциональная привычка проекта
  — не оценка «на глаз»), задокументировать в `docs/install.md`.

регистрацию Scheduled Task мимо `install.ps1` — при будущих изменениях
параметров задачи (например, RDS-флаг) этот путь не подхватит их

Что сделать: убрать `push_artifacts()`, вынести дефолт пароля в
`.env`/аргумент без значения по умолчанию в коде, по возможности вызывать
`install.ps1` вместо дублирования регистрации задачи.

**Сделано (2026-10-07):** убран `push_artifacts()` (не вызывался), а также
`publish_dir()` — тоже оказалась мёртвой (push_capture/push_uploader строят
путь публикации инлайн, функция не вызывалась ни разу). `VM_PASS` теперь
`${VM_PASS:?...}` — без значения по умолчанию, скрипт падает с понятной
ошибкой, если переменная не задана (пример с явным паролем уже был в
`docs/operations.md:242`, менять не пришлось).

Вызов `install.ps1` вместо дублирования регистрации Scheduled Task — решили
не делать. `install.ps1` ожидает MSI/bundle-раскладку (`-ServerUrl`
обязателен, конфиги генерирует сам, работает с `$InstallDir`/`$PSScriptRoot`,
требует Admin), а `deploy.sh` — инструмент быстрой итерации на тестовой VM:
гонит raw `dotnet publish`-вывод с дефолтным `appsettings.json` без конфигов
сервера. Переиспользование потребовало бы либо копировать `install.ps1` на VM

### Задача 17 — ввод консольной сессии записывается дважды

**Статус:** ✅ · **Объём:** S–M · **Зависит от:** — · **Приоритет:** средний

Найдено живой проверкой Задачи E4 (`roadmap-next.md`, 2026-10-08) на Debian 12:
в `input` записи `terminal-input` каждая команда сессии идёт два раза подряд
блоками (`echo a`, `exit`, `echo a`, `exit`) — уже в JSON очереди агента, то
есть это не сервер и не UI. Причина, судя по механике: `pam_tty_audit` включает
аудит TTY для всей SSH-сессии, а `watcher-term-wrap.sh` запускает внутри неё
`script(1)` — нажатия попадают в аудит дважды: когда `script` читает внешний
pty и когда `bash` читает внутренний pty `script`'а. `SessionCollector` склеивает
по `ses=` и не различает tty.

Что сделать: в `SessionCollector` брать записи только одного tty сессии
(например, первого увиденного или внутреннего pts, который открыл `script`) —
проверить на стенде, что в поле `TTY_INPUT`/`tty` у двух потоков разные
значения; без обёртки (`script` нет) ввод не должен пропасть. Поиск по вводу
сейчас работает (дубль не мешает находить), страдает читаемость и размер.

**Сделано (2026-10-08):** причина подтверждена по сырому `audit.log` тестового
стенда: на одну сессию (`ses=545`) — две TTY-записи с одинаковыми данными,
`comm="bash" major=136 minor=1` (pty script'а) и `comm="script" major=136
minor=0` (pty входа); терминал входа есть в `USER_LOGIN` той же сессии —
`terminal=/dev/pts/0`. Эвристика вроде «взять самый длинный» не нужна: ядро
само говорит, какой терминал — вход. `AuditLineParser` разбирает `USER_LOGIN`
(`terminal=` → `major:minor` по нумерации устройств Linux) и `major/minor` у
TTY; `SessionCollector` копит ввод по tty и пишет ввод терминала входа. Если
терминал входа неизвестен (агент стартовал посреди сессии) или на нём пусто —
весь ввод подряд, как раньше: дубль лучше потери аудита.

Попутно: `USER_LOGIN` неудачного входа приходит с `ses=4294967295` (u32 -1),
`int.Parse` на нём бросал бы `OverflowException` — раньше такие строки не
разбирались вовсе (тип не интересовал), с этой задачей стали бы. `ses`
теперь через `TryParse`, неназначенная сессия отбрасывается.

Живая проверка (собранный из ветки агент временно на тестовом Linux-клиенте,
потом возвращён прежний): SSH-сессия через `watcher-term-wrap.sh` — ввод один
раз (было два); сессия без обёртки (пользователь на время убран из
`enabled-users`) — ввод на месте; неудачный вход по паролю с `ses=4294967295`
— агент работает, ошибок в журнале нет. Тесты: `AuditLineParserTests` +4
(USER_LOGIN, major/minor, неназначенная сессия, таблица терминалов),
`SessionCollectorTests` +3 (вложенный pty, без терминала входа, пустой
терминал входа).
