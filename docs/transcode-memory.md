# Контроль памяти при пережатии

Исправление инцидента 2026-11-04: одновременный запуск 15 ffmpeg по статической
оценке 600 МиБ привёл к global OOM. Реализация — `TranscodeMemory.cs`,
интеграция — `Transcode.cs`; формат БД и значения конфигурации не меняются.

Перед каждой задачей под общей блокировкой читаются `MemAvailable` и
`MemTotal` из `/proc/meminfo`, а также текущий расход и лимиты cgroup:
`memory.current`/`memory.max` (v2) либо `memory.usage_in_bytes`/
`memory.limit_in_bytes` (v1). Пути определяются по `/proc/self/cgroup` и
`/proc/self/mountinfo`. Проверяются доступные предки до корня монтирования;
учитывается самый строгий запас. Unlimited не ограничивает бюджет, swap
не увеличивает его. Недоступность обязательных метрик запрещает новые задачи.
На Linux без memory cgroup используется запас хоста. На системах без Linux
procfs пережатие приостанавливается: платформенный источник ещё не реализован.

Резерв — максимум 1024 МиБ и четверти эффективной ёмкости памяти. Начальная
оценка задачи — максимум `MemoryPerWorkerMb` и 1536 МиБ. Наблюдаемый пиковый
RSS ffmpeg/ffprobe задач пережатия повышает оценку с запасом 25%; в пределах
жизни процесса оценка не уменьшается. Процессы проверки входящих загрузок
не дают кредит к резервам пережатия, но их расход уже уменьшает общий запас.

У ещё не разросшихся задач резервируется разница между суммарной оценкой
и текущим RSS. Это предотвращает массовую выдачу по одному устаревшему
значению свободной памяти. `Workers` остаётся верхней границей, включая
явное значение. После паузы для запуска нужен дополнительный запас 256 МиБ.

Раз в секунду проверяется давление памяти. Если запас меньше максимума
256 МиБ и 5% ёмкости, отменяется одна активная задача за проверку. ffmpeg
завершается вместе с деревом процессов, после чего задача убирает свой
`.part`, освобождает lease и остаётся pending без увеличения числа ошибок.
Повторный прогон после такого ограничения начинается через пять секунд;
при долгом дефиците воркеры ждут до окончания бюджета прогона.

Диагностика: `memory` внутри состояния transcode в `/api/overview` и сообщения
`transcode memory` в журнале. Поля: причина (`ready`, `low-memory`,
`critical-memory`, `metrics-unavailable`), ёмкость, запас, резерв, оценка
задачи, RSS процессов пережатия, активные задачи и эффективный потолок.
Размеры — в байтах. При недоступных метриках размерные поля равны нулю
и не являются измерением реального расхода.

## Проверка и ограничения

Локальная проверка 2026-11-05: **740 серверных тестов прошли**, без пропусков.
Команда: `dotnet test tests/Watcher.Server.Tests/Watcher.Server.Tests.csproj
--no-restore --verbosity minimal -p:UseSharedCompilation=false -m:1`.
Сборка выполнена с анализаторами проекта, включая правила безопасности.
Проверки форматирования изменённых C#-файлов (`dotnet format whitespace
--verify-no-changes`) и `git diff --check` прошли.
NuGet выдал NU1900: источник сведений об уязвимостях недоступен; успешная
сборка не означает успешный аудит NuGet-зависимостей.

Регрессионные тесты используют управляемые снимки памяти и подставной
кодировщик: бюджеты хоста и предков cgroup v1/v2, unlimited, отсутствие метрик,
одновременная выдача, резервирование, гистерезис, повышение оценки по RSS,
явный Workers, отмена с очисткой части и повторная обработка исходника.

Для приёмки требуется отдельный длительный прогон на стенде 16 vCPU /
16 ГиБ с тяжёлыми многомониторными записями и загрузками, ограничением RAM
и проверкой контейнеров с лимитом/без лимита и запуска без Docker. Проверки
на подставных данных не подтверждают отсутствие OOM в реальной нагрузке.
Резкое внешнее выделение памяти между секундными проверками остаётся
ограничением опросного механизма. Недоступные предки за границей cgroup mount
не могут быть измерены этим процессом.
