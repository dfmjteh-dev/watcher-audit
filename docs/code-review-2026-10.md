## 🔴 Потеря данных

### R1 — терминальный ввод молча теряется после каждой перезагрузки Linux-хоста

**Статус:** ✅ исправлено (PR #33): `externalId` ввода включает время начала сессии по часам станции — повтор того же файла по-прежнему дедуплицируется, а новая сессия с тем же `ses=` больше не получает 409 и не теряется.

`src/Watcher.Server/Program.cs:408` — `externalId = $"{host}:in:{sessionId}"`,
где `sessionId` — audit `ses=` из ядра. Комментарий на строке 405 говорит, что
он «уникален per-host на время жизни хоста», но это не так: счётчик audit
session id в ядре живёт в памяти и **после загрузки снова начинается с 1**.

Сценарий: хост перезагрузился → новые SSH-сессии получают `ses=1, 2, 3…` →
сервер находит старые записи с тем же `externalId` и отвечает 409 → агент
считает 409 успехом (`UploadClient.cs:53`) и переносит файл в `sent/` →
**ввод всех сессий после перезагрузки не попадает на сервер**, пока счётчик
не превысит максимум до перезагрузки. На сервере, который перезагружают
раз в месяц и где за месяц было 5000 сессий, это означает 5000 потерянных
сессий подряд. В логах сервера ошибок нет.

**Фикс.** Добавить в `externalId` идентификатор загрузки:
`/proc/sys/kernel/random/boot_id` (агент читает его при старте и кладёт в meta)
или хотя бы `startedAt`. Пример: `{host}:in:{bootId}:{ses}`. Тест: две записи
с одинаковым `ses` и разным `bootId` обе принимаются.

### R2 — 409 «уже на сервере» решается по имени, а не по содержимому, и агент удаляет файл

**Статус:** ✅ исправлено (PR #34): агент передаёт sha256, при совпадении имени с другим содержимым сервер отвечает 422, а не 409, и агент не удаляет файл.

`src/Watcher.Server/Program.cs:111`: дубликат определяется только по `filename`
(глобально `UNIQUE` в `segments`). `src/Watcher.Uploader/Uploader.cs:61`: на 409
агент считает сегмент выгруженным и удаляет локальную копию. При совпадении
имени у **разных** записей вторая молча уничтожается. Как совпадают имена:

- **Linux, несколько графических сессий на одном хосте** (XRDP/VNC/multi-seat):
  имя `{host}_{ts}.mp4` без пользователя (`Capture.Linux/SegmentWriter.cs:62`),
  хотя `sessionUser` в meta есть. Две сессии, начавшие сегмент в одну секунду,
  дают одно имя. На Windows это уже исправлено (`BuildBaseName` с пользователем).
- **Одинаковые имена машин в разных местах**: склонированные VM, `ubuntu`,
  `localhost`, `DESKTOP-XXXX` из одного образа. Для многих организаций и
  VDI-парков это обычная ситуация. Сервер заодно склеивает такие хосты в
  одну строку `hosts` (см. G1 в `roadmap-next.md`).
- Переход на зимнее время: имя строится из **локального** времени
  (`DateTime.Now`), и час 02:00–03:00 повторяется.

**Фикс (минимальный).** Сервер: если `filename` совпал, а `sha256` нет,
возвращать не 409, а 422 `{"error":"filename collision"}`; агент на 422 не
удаляет файл, а переименовывает с суффиксом и шлёт заново. Плюс добавить в имя на Linux
`sessionUser`, а в имя на обеих ОС время в UTC. Полностью проблема одинаковых
имён решается учётками хостов (G1).

### R3 — оборванная по таймауту SSH-сессия теряет весь последующий ввод

**Статус:** ✅ исправлено (PR #33) — та же корневая причина, что R1.

`src/Watcher.TerminalAgent/SessionCollector.cs`, `SweepAbandoned`, при
`AbandonedSessionTimeoutSeconds = 3600` (`Config.cs:75`). Если в SSH-сессии
нет ввода больше часа (обычное дело: открытая консоль админа), она
финализируется и выгружается. Когда пользователь снова начинает печатать,
создаётся новая запись с тем же `ses` → тот же `externalId` → 409 → ввод
после паузы на сервер не попадает. Та же корневая причина, что в R1: при
таком `externalId` у одной сессии может быть только одна запись.

**Фикс.** Добавить в `externalId` номер части (`{ses}:{partNo}` или время
начала части), а в UI склеивать части одной сессии. Либо не финализировать
сессию по таймауту, а только сбрасывать накопленное на диск (flush), оставляя
её открытой до `USER_END`.

## 🔴 Безопасность (помимо этапа A в roadmap-next.md)

### R4 — инъекция аргументов ffmpeg через серверный конфиг

**Статус:** ✅ исправлено — `ArgumentList` в обоих `SegmentWriter`, диапазоны и
whitelist `Preset` в обоих `ConfigReload.Apply`, схема на сервере
(`AgentConfigValidation.cs`, 400 на `PUT .../config`).

`src/Watcher.Capture/ConfigReload.cs` принимает `Preset` как произвольную
строку; `SegmentWriter.cs:84` склеивает аргументы ffmpeg через
`string.Join(' ', …)` в одну командную строку. `Preset = "ultrafast -y C:\\Users\\Public\\x.mp4"`
добавляет ffmpeg лишние аргументы, в том числе дополнительный выходной файл по
произвольному пути. Задать конфиг может любой залогиненный пользователь
веб-UI (ролей нет, C1), в том числе через XSS (A1), и он применяется **на всех
станциях группы**. Сервер проверяет только, что конфиг — JSON-объект
(`Program.cs`, `PUT .../config`).

Числа тоже не проверяются: `CaptureIntervalMs = 0` даёт busy-loop на всех
станциях, `DownscaleWidth = 0` — падение при `Resize`.

**Фикс.** На агенте — `ProcessStartInfo.ArgumentList` вместо склейки строки
(в обоих Capture) и whitelist `Preset` (`ultrafast…veryslow`). На сервере —
схема конфига с диапазонами (интервал 100–10000 мс, CRF 0–51, разрешение
320–7680…), невалидное значение — 400. Агент тоже не принимает значения
вне диапазона: защита с двух сторон.

### R5 — root-агент читает файлы из каталога, куда пишут пользователи

**Статус:** ✅ исправлено. При исправлении нашлось хуже, чем описано ниже:
`outFile` из `.json` шёл в `Path.Combine` без проверки, поэтому
`"outFile":"/etc/shadow"` (или `../..`) работал **без симлинка**, и
`protected_symlinks` от него не защищал, а после выгрузки `File.Move` уносил
этот файл в `sent/`. Сейчас имена берутся из имени `.json`, файлы
открываются с `O_NOFOLLOW|O_NONBLOCK` (FIFO не вешает агент), тип и
владелец проверяются по открытому дескриптору (`statx`), владелец всех
трёх файлов должен быть `sessionUser`. Регулярка на имя из фикса ниже не
понадобилась: имя берётся из листинга каталога, и `/` в нём быть не может,
а доменные логины (`user@domain`) строгая регулярка отрезала бы. Плюс
`raw-output/sent/` должен принадлежать агенту (инсталлятор пересоздаёт
чужой).

`src/Watcher.TerminalAgent/UploadRunner.cs:63`: имена `.out`/`.timing` берутся
из `.json`, который пишет сам пользователь (обёртка `watcher-term-wrap.sh`) в
`raw-output` с правами `1777`, после чего root-процесс открывает эти файлы и
отправляет на сервер. Если там лежит симлинк на `/etc/shadow`, root-агент
отправит его содержимое на сервер, где оно будет видно в веб-UI.

От этого по умолчанию защищает `fs.protected_symlinks=1` (ядро не даёт root
пройти по чужому симлинку в sticky-каталоге, доступном всем на запись), и на
большинстве современных дистрибутивов этот sysctl включён. Полагаться на
него не стоит: настройку могут выключить, и есть старые ядра.

**Фикс.** Открывать с `O_NOFOLLOW` (или `lstat` + проверка, что это обычный
файл), проверять, что владелец файла совпадает с `sessionUser` из meta, а
имена файлов — с шаблоном `^[a-z_][a-z0-9_.-]*-\d+-\d+\.(out|timing)$`.

### R7 — данные агента используются без проверки: 500 вместо 400, и retention по чужим часам

**Статус:** ✅ исправлено. 500 на кривом meta закрыт ещё задачей A5
(`TryParseUploadMeta`/`TryParseTerminalMeta`). Часы: сдвиг меряется не по
`startedAt` (станция могла быть офлайн неделю), а по заголовку
`X-Watcher-Agent-Time` с текущим временем агента на каждом запросе. Если
сдвиг больше 10 минут, время записи исправляется, а исходное хранится в
`station_started_at`. Запись из будущего ставится на время выгрузки.
Retention удаляет только то, что старо и по `started_at`, и по `uploaded_at`.
Бейдж «часы ±N» в «Хостах». Детали в `architecture.md`.

`Program.cs` (`/api/upload`, `/api/upload-terminal`):
- `JsonDocument.Parse` и `DateTime.Parse` без `try`: кривой meta даёт 500. Агент
  повторяет запрос до бесконечности, раз в `MaxRetryDelaySeconds`, а файл
  остаётся в очереди навсегда.
- `startedAt` — это **часы станции**. Retention (`Retention.cs`) удаляет по
  `started_at`: у станции с батарейкой BIOS, сбросившей дату на 2000 год,
  сегменты удаляются при первом же проходе retention. Станция с датой в
  будущем не чистится никогда. Блобы раскладываются по каталогу этого же дня.

**Фикс.** Разбор meta с `TryParse` → 400. Если `startedAt` расходится с
серверным `uploaded_at` больше чем на N суток, хранить время сервера и
помечать сегмент «часы станции неверны» (полезно и как сигнал в `#/fleet`).

### R8 — `RetentionMaxBytes` применяется к видео и консоли по отдельности

**Статус:** ✅ исправлено. `RetentionMaxBytes` — один бюджет на обе таблицы,
удаляются самые старые записи из любой из них (`RunOnceBySpace`). Новый
`MinFreeDiskPercent` (5% по умолчанию, 0 — выкл.): если на томе свободно
меньше, retention удаляет самые старые записи независимо от возраста ровно на
нехватку до порога, `/api/overview` отдаёт `diskLow`, `#/` показывает
предупреждение. Ввод консоли (`size_bytes = 0`) по месту не удаляется. Частично
записанные блобы при полном диске закрыл R9.

`Retention.cs:51` и `:110`: лимит проверяется отдельно для `segments` и
`terminal_sessions`, в сумме диск может занять до 2× лимита. Кроме того, нет
проверки свободного места: при `RetentionMaxBytes = 0` (дефолт) диск
заполняется полностью. Тогда `File.Create` на upload падает, и остаются
частично записанные блобы без строки в БД.

**Фикс.** Один общий бюджет на обе таблицы. Плюс порог по свободному месту
(`MinFreeDiskPercent`): ниже порога retention удаляет самые старые записи
независимо от возраста, а `#/` показывает предупреждение.

### R9 — блоб пишется до вставки в БД, файлы-сироты

**Статус:** ✅ исправлено как предложено: `.part` с уникальным суффиксом на
каждый запрос → `Insert` → `File.Move` (`BlobFiles.cs`), в обоих upload-эндпоинтах.
Если `Insert` упал с `UNIQUE` из-за гонки, ответ 409 (или 422, если sha256 другой),
как у обычного повтора, а не 500. Если не удался `Move`, строка удаляется.
Retention раз в сутки удаляет `.part` старше часа.

`Program.cs:145` → `:175` (и то же в terminal-ветке): файл создаётся сразу по
итоговому пути, строка в БД вставляется после. Если `Insert` упал (гонка двух
одинаковых загрузок → `UNIQUE`, диск, исключение), файл остаётся на диске без
строки в БД, retention его никогда не найдёт. При гонке два запроса ещё и
пишут в один и тот же файл одновременно.

**Фикс.** Писать во временный файл (`*.part`), затем `Insert`, затем атомарный
`File.Move`. При ошибке удалять `.part`. Раз в сутки retention удаляет `.part`
старше часа.

### R10 — JSON в `watcher-term-wrap.sh` собирается через `printf` без экранирования

**Статус:** ✅ исправлено. Сценарий реальнее, чем описано ниже: у winbind

Брать время из `.json`, а пользователя и хост определять самому агенту, как
предлагалось ниже, не понадобилось: пользователь сверяется с владельцем
файлов (R5), хост у агента с учёткой берётся из учётки (G1).

`scripts/watcher-term-wrap.sh:48`: `host`, `sessionUser` подставляются в JSON
как есть. Сейчас это безопасно только потому, что имена пользователей и хостов
обычно не содержат `"` и `\`. Если имя содержит кавычку, получается невалидный

Заодно `.json` пишет пользователь, а значит, может указать любой `sessionUser`
(см. R5).

Подмена `sessionUser` закрыта в R5: запись, где `sessionUser` не владелец
файлов, агент не выгружает. Остаётся невалидный JSON при кавычке в имени.

**Фикс.** Метаданные (`host`, `user`) root-агент берёт **сам**: владельца
файла `.out` (uid → имя) и `Environment.MachineName`. Из `.json`
пользователя берутся только времена и exit code.

### R11 — Linux-инсталлятор правит `/etc/bash.bashrc`, а это путь только Debian/Ubuntu

**Фикс.** Определять путь (`/etc/bash.bashrc` или `/etc/bashrc`), при
отсутствии обоих — предупреждение. В CI — проверка `shellcheck` для всех `.sh`.
