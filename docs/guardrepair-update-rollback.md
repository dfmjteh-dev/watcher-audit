# GuardRepair: журнал обновления, откат и ограниченный кэш

Продолжение группового канала и миграции ZIP. Новый Guard перед установкой
проверяет прежний локальный пакет, сохраняет состояние и публикует журнал.
Ошибка установки/службы или незавершённый процесс возвращает предыдущую
проверенную версию. Политика новой базы записывается только после проверок.

Механизм действует для обновлений, которые выполняет **новый Guard**.
Установка нового helper старым Guard не получает журнал задним числом.
Для установки/миграции из подготовленного комплекта новая реализация сразу
входит в начальную базу. Старый protected agent без проверенной текущей базы
получит отказ **до запуска установщика**: сначала требуется контролируемая
подготовка соответствующего подписанного пакета и согласованной policy.
Подмена отсутствующей базы произвольным скачанным MSI не допускается.
Для текущего формата поддерживаются опубликованные пакеты начиная с 0.15.1:
и прежняя база, и кандидат должны содержать journal-aware Guard. Старый native
installer меняет helper launcher ещё внутри установки; поэтому отдельная
замена helper при базе 0.15.0 не делает такой rollback crash-safe. Пакеты
прототипов с повторно использованной версией не заменяют согласованный релизный
baseline. Этот переход и пакеты должны быть подтверждены на стенде.

## Подготовка и commit

После consume подписанного grant и проверки отдельной publisher-подписи
Guard проверяет текущую базу (`LastVerifiedPackage`, начальную либо старый
cache/package.json), конфиги и хеши текущих файлов. Переход между native
платформами не разрешается. Затем собираются:

- точные байты JSON-конфигов и имеющихся credentials с контрольными хешами;
- launcher и собственные recover/protect scripts независимого helper;
- запущенные компоненты и фактический startup: Windows automatic/delayed-auto,
  manual/disabled; Linux enabled/enabled-runtime/disabled;
- прежняя policy, дескриптор проверенного пакета и ID принятой операции.

Снимок credential отправителя повторно сверяется с binding grant: смена
идентичности в процессе подготовки не переносит разрешение на новую учётку.
Отсутствующая до обновления credential отключённого компонента не выдумывается.
Снимки и `update-state/transaction.json` размещаются внутри закрытого каталога
Guard, пишутся через временные файлы, Flush(true) и атомарную замену. Это
происходит до запуска установщика. File lock существующего tick исключает
параллельные действия Guard.

Точный startup сохраняется также в policy (`StartupModes`), включая первую
bootstrap нового Guard. Обычный repair после удаления службы возвращает этот
режим, а не превращает disabled в manual. Старые policy без поля читаются.
Существующие правильные режимы не переписываются каждую проверку.

После установки Guard возвращает проверенные конфиги, сверяет неизменность
существующих identities, регистрацию/путь/account и startup службы. Возвращает
ожидаемое running/stopped состояние и при запущенных службах ждёт 20 секунд,
затем проверяет состояние ещё раз. Сверяются версия Windows executable или
установленного DEB/RPM и ожидаемая версия базы. Это проверка локального runtime, а не
доказательство доставки heartbeat или корректной записи всех сессий.

**Commit — атомарная запись policy** с новым LastVerifiedPackage и хешами.
Предыдущая база становится PreviousPackage, начальная ссылка снимается, если
она уже заменена текущим пакетом. До этой записи новый пакет не считается
базой ремонта. После commit снимки прежней версии хранятся в `previous-update`.
Ошибка housekeeping не запускает downgrade уже принятой версии: cleanup
повторяется на следующих тиках.

## Восстановление незавершённого обновления

Журнал читается раньше inbox, проверки времени и maintenance lease. Пока
восстановление не завершено, новые команды не исполняются.

Если policy уже содержит ID операции, commit состоялся: Guard завершает
очистку и сообщает completed. Иначе выполняется rollback:

1. Заново проверяются подпись/размер/SHA-256 прежнего пакета и все снимки.
2. Возвращаются прежняя policy, конфиги, identities и helper launcher/scripts.
3. В фазе `rolling-back` ставится проверенный старый пакет.
4. После успешного native installer сохраняется `restoring`: повтор проверки
   startup/службы уже не запускает бесконечные переустановки исправного пакета.
5. После проверки старых файлов и runtime фиксируется `rolled-back`, операция
   получает failed; журнал убирается из активного состояния, обычный repair
   снова работает. Прежний retry-счётчик repair очищается.

Если rollback не удался, журнал остаётся. Повторы — через 1/5/30 минут с
потолком 30 минут, без постоянного отключения после третьей ошибки. Сдвиг
часов на часы назад не откладывает восстановление на неопределённый срок.
Истечение исходного grant не мешает вернуть уже сохранённую проверенную базу:
короткий internal-repair marker создаётся самим SYSTEM/root. Новое разрешение
через inbox из этого не возникает. Replay-store и watermark не откатываются.

`last-update.json` содержит только ID, версии, outcome и время. Текущий серверный
протокол результатов сохраняется: pending rollback остаётся accepted, после
успешного возврата — failed/operation-failed. Подробные коды этапов и их показ
на сервере остаются отдельной задачей; секреты/содержимое конфигов не передаются.

## Native installer

Windows: чтобы вернуть старый MSI с MajorUpgrade, Guard сначала снимает новый
Watcher-продукт, затем устанавливает проверенный старый пакет. Закрытые
credentials и снимки вне основного каталога сохраняются. Срок внутреннего
marker обновляется между шагами. Reboot-pending 3010 не считается подтверждением
исправной установки: операция остаётся в восстановлении до проверяемого результата.
Обычный MSI не получает разрешения на произвольный downgrade.

Linux: dpkg сохраняет изменённые conffiles (`--force-confold`), RPM получает
`--oldpackage --replacepkgs` только на пути rollback. Документация:
[dpkg](https://manpages.debian.org/trixie/dpkg/dpkg.1.en.html),
[RPM](https://rpm.org/docs/6.0.x/man/rpm.8).
Masked/static/нестандартные unit states не принимаются как поддерживаемый
startup для обновления; нужно сначала привести собственные units в штатное
состояние. Ссылки на месте восстанавливаемого unit отклоняются.

Лимит выполнения постоянной recovery task/oneshot поднят с 10 до 20 минут,
чтобы вместить установку и двухшаговый rollback. Интервал остаётся две минуты,
одновременные тики по-прежнему исключены.

## Кэш

В покое сохраняются текущий и предыдущий package. Во время транзакции прежние
ссылки не удаляются: возможен дополнительный кандидат и native MSI source.
Очистка пропускается при непустом inbox. Downloader публикует cache-файл и
inbox под общим cache.lock, GC не удаляет пакет между этими двумя шагами.
Старые content-addressed MSI/DEB/RPM и неподдержанные ZIP удаляются после
завершения очереди, посторонние имена/ссылки не трогаются. Старый metadata-only
cache сохраняется, пока текущая база не может быть надёжно определена.

В bin остаются текущий и предыдущий helper; дополнительно сохраняется реально
исполняемый coordinator, если он старше обоих. Неизвестные каталоги/файлы не
удаляются. Незавершённые tmp старше часа и их orphan locks очищаются;
активный downloader держит отдельный lock на весь жизненный цикл файла.
Временный MSI source копируется потоково и очищается после installer.
Повреждение/блокировка файловой системы может отложить cleanup; это не повод
откатить успешный commit. Общие данные очереди, записи и журналы потерь не
откатываются и снимками не перетираются.

## Проверка и ограничения

Локальные тесты используют временные каталоги и подставной native platform:
ошибки install/start/registration/identity, смерть процесса при update/rollback,
истечение lease и сдвиг часов, backoff, повтор restoring без переустановки,
повреждённые snapshots/base, startup manual/disabled и ремонт отсутствующей
программы, crash после policy commit, cleanup failure и cache-lock race.
Отдельно проверяются старые MSI/ZIP/launcher/task-migration сценарии и упаковка.

Реальная установка/удаление MSI, DEB/RPM downgrade, Windows ACL, SCM/systemd,
доставка диагностики и отключение питания здесь не исполнялись. До production
нужен общий прогон Windows 10/11/Server 2019 и Linux с перезагрузками на фазах,
полным удалением каталога/регистрации и без сети. Запись журнала не заменяет
проверку сохранности файловой системы при жёстком отключении питания.
Изменений production и запуска CI нет.

Результат прогона 2026-11-05: 183 теста агента и 92 теста Windows-службы
прошли. GuardRepair собирается с security analyzers без предупреждений/ошибок.
Прошли 15 сценариев task migration, 15 сценариев legacy migration, 8 ZIP и
4 Linux launcher сценария, MSI packaging/build-kit, ShellCheck и parsing.
Серверный код/протокол результатов не менялся; полный серверный набор в этом
этапе повторно не запускался. Проверка native rollback в этих тестах подставная.
