# GuardRepair: групповое обновление через существующий доверенный канал

Этап от 2026-11-05 после переноса задачи восстановления. Цель — обновлять уже
защищённые агенты текущим назначением версии группе, без отдельной команды
на каждом хосте. Это совместимый серверный мост для установленного Guard:
формат подписанных команд и независимая подпись пакетов сохраняются.

## Как работает

Оператор загружает подписанный пакет и задаёт целевую версию группе обычным
способом. Если персональная учётка video/terminal уже сообщила закреплённый
maintenance key ID, heartbeat автоматически ставит update-команду в канал
диагностики. Обычное поле `heartbeat.update` такого агента пустое: старый
AgentUpdater всё равно отвергал protected update. Guard получает команду
существующим способом и проверяет binding учётки, подпись, время, replay,
SHA-256 и независимую подпись издателя пакета.

Для Windows нужен **подписанный MSI целевой версии**, включая существующую
защищённую установку из ZIP/install.ps1 (до 0.16). В этом случае Guard ставит MSI в
тот же каталог с сохранением проверенных конфигов и обеих идентичностей;
после регистрации MSI агент сообщает платформу windows-msi. Наличие одного
ZIP на сервере не заменяет MSI: хост показывает `blocked … package unavailable`.
Для Linux используются DEB/RPM платформы, сообщённой агентом.

## Агенты без базы восстановления (0.16)

Если защиту включило обновление незащищённого агента 0.15.x (его загрузчик не
сохранял подпись пакета), у Guard нет базы восстановления, а обновление без неё
он не начинает: отказ `base-unavailable`. Сервер, увидев такой отказ, сначала
выдаёт заявку на **текущую** версию хоста (статус «queued X: recovery base Y
first»). Guard проверяет подпись пакета и, раз версия совпадает с установленной,
закрепляет его базой без переустановки. Следующим heartbeat приходит обычное
обновление до цели. Пакет текущей версии должен лежать в «Обновлениях»
(install-server.sh загружает пакеты своей версии сам); нет — у хоста
`blocked … no recovery base; upload signed … package X`.

## Возврат на старую версию (0.16)

Чтобы откатить агентов, задайте группе в «Обновлениях» более старую целевую
версию — так же, как при обновлении. Пакет этой версии должен лежать в
«Обновлениях».

| Агент | Цель 0.16 и новее | Цель 0.15.1–0.15.x |
|---|---|---|
| Windows, защищённый | обычная установка MSI: с 0.16 MSI допускают понижение, одна транзакция Windows Installer | Guard 0.16+ удаляет текущую версию и ставит старую (тот же путь, что у автоматического отката); старому Guard — `blocked … needs agent 0.16` |
| Windows, без защиты | обычное обновление MSI | `blocked … only to 0.16`: MSI до 0.16 запрещают понижение |
| Linux deb | dpkg / apt `--allow-downgrades` | то же |
| Linux rpm | Guard 0.16+ — удаление и установка; без защиты — `rpm -U --oldpackage` | то же; старому Guard — `blocked … needs agent 0.16` |

Ниже 0.15.1 защищённые агенты не возвращаются: у такого Guard нет журнала
обновления. Как и при обновлении, сбой установки возвращает текущую версию.
Причина блокировки видна у хоста в «Обновлениях».

Сервер использует уже настроенный `MaintenanceSigningKeyPath` либо предыдущий
ключ, если именно он закреплён на агенте. Отсутствие подходящего ключа даёт
`blocked … pinned maintenance signing key unavailable`, без ослабления
проверок. Автоматическая настройка ключей для новых установок — другой этап.
Не требуется вручную выпускать отдельное разрешение каждому агенту.

Одна транзакция SQLite повторно проверяет действующую учётку, её pin и
binding, текущую группу/цель и точные метаданные пакета. Учётки video/terminal
одного хоста конкурируют за одну команду. Выдача команды и резервирование
слота UpdateRollout согласованы; отказ не занимает новый слот и не снимает
существующий. После перезапуска сервера слоты активных групповых команд
восстанавливаются из БД. Запоздавший результат старой команды не освобождает
слот новой команды.

## Обслуживание и повторы

- Любое ещё действующее разрешение обслуживания, в том числе экспортированное
  офлайн или завершённый stop, откладывает автоматическую выдачу до срока.
  Это относится и к отменённой в очереди команде: её уже доставленная копия
  остаётся действующим полномочием до истечения TTL.
- Завершённый uninstall блокирует автоматическую переустановку. Последнее
  подтверждённое состояние uninstall/resume/repair сохраняется при очистке
  истории старше 30 дней, по одной записи на хост. Явный успешный resume/repair
  снимает запрет; обычная новая цель группы его не снимает.
- Попытка той же версии не повторяется чаще раза в час, включая истёкшее
  разрешение или сбой. Ограничение хранится в БД и переживает рестарт сервера.
- Перед доставкой ещё стоящая в очереди автоматическая команда сверяется с
  текущей целью, pin и уже достигнутой версией. Изменившая область команда
  помечается rejected. Подписанную копию, уже доставленную агенту, сервер
  отозвать этим не может — до срока действуют прежние правила протокола.
- Результаты Guard обновляют статус хоста: queued/installing/ok/failed.
  Защищённый агент не перезаписывает его устаревшим last-result обычного updater.
  В истории сохраняется признак `group-update:…`, в аудите —
  `agent.group-update-issued`, пакет и исходная платформа, без секретов.

## Агент и подготовка ZIP-миграции

Новый Guard принимает обновлённые хеши и LastVerifiedPackage только после
проверки регистрации, ожидаемого запуска/остановки служб и файлов. Сервис,
который был запущен вручную, возобновляется; остановленный ручной сервис
не становится автоматическим. При провале этих проверок прежняя база ремонта
не заменяется. Это не новая полноценная транзакция отката: текущие механизмы
MSI/Guard и наличие прежнего проверенного пакета по-прежнему важны.

Обычный незащищённый ZIP-путь копирует полный набор GuardRepair вместе с
основными файлами. Старые ZIP без него поддерживаются; неполный набор или
разные байты переходной копии отклоняются до замены. Откат восстанавливает
прежние managed-файлы, а добавленные впервые удаляет. Конфиги и посторонние
файлы не включаются в этот набор. Пути копирования/восстановления читаются
буквально, в том числе с квадратными скобками.

## Границы и проверка

Группы с уже назначенными целевыми версиями начнут применяться и к защищённым
агентам при установке нового сервера. Перед production-обновлением оператору
нужно проверить эти цели и наличие нужных MSI/DEB/RPM. Локальная разработка
и этот PR не назначают версии групп и не меняют инфраструктуру.

На момент этого этапа защита по умолчанию и первая база не входили в партию.
Следующий этап — [bootstrap и подготовленные комплекты](guardrepair-bootstrap.md).
Следующий этап — [откат защищённых обновлений](guardrepair-update-rollback.md)
(переход старого ZIP был отдельным этапом и убран в 0.16).

Локальная проверка 2026-11-05:

- 762 серверных теста прошли после полной принудительной пересборки,
  0 предупреждений/ошибок сборки. Есть сквозной HTTP-сценарий heartbeat →
  доставка команды → подтверждение и освобождение слота, а также гонки обеих
  учёток, конкуренция независимых диспетчеров, рестарт, отказ ключа/пакета,
  смена цели/pin, cooldown и сохранение запрета uninstall после очистки.
- 140 тестов Uploader прошли: отказ от принятия новой базы при сбое службы
  или регистрации, сохранение ручного режима и прежнего состояния запуска.
- 5 PowerShell-сценариев ZIP прошли с настоящими функциями update.ps1 в
  отдельном временном каталоге: старый/полный/неполный набор, хеш alias и
  восстановление прежних/удаление добавленных managed-файлов. Тело установщика,
  службы и планировщик на машине разработки не запускались.
- Разбор update.ps1 PowerShell 7.4.13 и git diff --check прошли.
  Аудит NuGet в этой проверке отключён; анализаторы безопасности проекта
  при сборке включены.

Для приёмки остаётся пакетный стенд Windows 10/11/Server 2019 и Linux:
переход защищённого ZIP-агента на MSI, существующий MSI и DEB/RPM, обе учётки,
сохранение конфигов/очереди, остановленное обслуживание, сбой службы, ошибка
подписи, повторное обновление и штатное удаление без самоустановки. Работа
старого агента с новым сервером проверяется на VM, а не только unit-тестами.
