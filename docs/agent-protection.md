# Диагностика, защита и независимое восстановление

Подготовленные комплекты `install-server.sh` теперь включают GuardRepair
при установке Windows MSI и Linux через комплектный `install.sh`. Прямые
общие MSI/ZIP/DEB/RPM без настройки сервера сами защиту не включают.

## Что видно на сервере

На странице хоста → «Инфо» показываются известные warning/error по компонентам,
последняя связь каждой персональной учётки и диагностический пакет по запросу
администратора. Пакет содержит версию, платформу, размер/число файлов очереди,
память, число процессов и свободное место. Это снимок метрик, а не архив
произвольных Info/Debug-логов: тексты исключений, аргументы, конфигурационные
значения и содержимое сессий не передаются. Подробные исходные логи остаются
локальными. Текущий список событий содержит известные коды причин.

После двух минут без диагностики UI показывает последнее известное состояние;
отсутствие нового сообщения не доказывает исправность службы. Пакеты и события
живут 14 дней, максимум 2000 событий на хост. В локальном журнале не более
256 событий, автоматический warning/error одного типа ограничен 30 секундами.
Диагностика и результаты принадлежат только персональной учётке агента. Viewer видит только свои группы; управление — admin.

## Ключи и начальная установка

Нужны **две разные пары** ключей: существующий ключ издателя пакетов и отдельный
P-256 ключ обслуживания. Закрытые ключи не должны попадать на станции, в Git,
комплект агента или журналы. PEM обслуживания можно зашифровать; сервер читает
пароль из отдельного закрытого файла. Генерацию пары можно выполнить штатным
`tools/update-signing/new-update-key.sh --out /secure/maintenance-key`, без
`--env` (этот флаг относится к ключу обновлений). Перед запуском генератора
проверить его справку и права каталога. Публичное значение — SPKI DER/base64.

`install-server.sh` создаёт отдельную зашифрованную пару обслуживания в своём
каталоге ключей. Повторный запуск проверяет прежнюю пару и не заменяет её.
Если путь обслуживания сервера ещё не задан, установщик копирует только эту
пару и пароль в `/var/lib/watcher-server-maintenance` (root, чтение группе
службы; Docker mount read-only). Publisher private key туда не попадает.
Существующие пользовательские пути сохраняются; сборщик берёт публичный
ключ через CLI действующего сервера, а не предполагает совпадение с локальной
парой. После обновления старого сервера нужен обычный запуск установщика:
один `--rebuild-kit` не меняет конфигурацию и не перезапускает службу.

Для ручной настройки серверу задать `Server:MaintenanceSigningKeyPath`, при шифровании также
`MaintenanceKeyPasswordFile`. В Docker смонтировать секреты read-only и задать
соответствующие `Server__...` пути. Без ключа UI вернёт понятный отказ и не
создаст разрешение. Настройка не требует изменения обычного UpdatePublicKey.

Windows: использовать MSI с каталогом под доверенным родителем, например
`C:\Program Files\Watcher`, и свойствами `SERVERURL`, `ENROLLTOKEN`, `UPDATEKEY`,
`MAINTENANCEKEY`. Базу восстановления Guard берёт из самого MSI по подписи
`watcher-agent.msi.sig` рядом с ним (комплект кладёт её сам);
без неё защита включается, но файлы агента вернутся только после первого
обновления через Guard.
Переход `C:\Watcher` через групповой ZIP убран в 0.16 — такую станцию
переустановить из MSI. Прямой guard-install менять ACL корня диска
по-прежнему откажется.
Очередь/логи/пользовательские записи должны находиться отдельно от программы.

Linux, автообновление (0.16): агент, поставленный пакетом без защиты (например,
до появления ключа в комплекте), включает её сам. Сервер передаёт в heartbeat
ключ обслуживания из комплекта вместе с подписью ключом обновлений
(`certs/maintenance-key.sig`); агент сверяет подпись своим ключом обновлений и
отдельным юнитом `watcher-agent-protect` запускает `GuardRepair setup`. Это то же,
что на Windows: там ключ зашит в MSI, подписанный тем же ключом обновлений.
Агент 0.15.x делает это уже после обновления, новой версией. База восстановления
приходит с сервера с первым групповым обновлением (как у Windows без `.sig`).
Неудачная попытка повторяется не чаще раза в 6 часов.

Linux: системный пакет DEB/RPM, затем штатный `watcher-agent-setup` с параметрами
сервера, регистрации, `--update-key`, `--maintenance-key`,
`--recovery-package` и `--recovery-manifest`. В готовом комплекте всё передано
через `install.sh`, отдельный ввод ключа не нужен. Режим защиты
рассчитан на системные `/opt/watcher-*`, не на пользовательский tar-install.
Учётки мигрируют в закрытый каталог Guard без повторной регистрации; прежний
файл удаляется после запуска службы только при совпадении сохранённой копии.
Для manual/disabled-службы сначала зарегистрировать агент, чтобы защита
не заблокировала получение его первой учётки. Исходный режим запуска сохраняется.

## Границы защиты

Windows-служба остаётся LocalSystem: нужен WTSQueryUserToken для записи всех
пользовательских сессий. Владельцем программы, приватного каталога, службы и
её ключа реестра становится SYSTEM, администраторы получают чтение вместо
stop/change/delete. Широкие DENY не используются. Проверяются права родителя,
чтобы delete-child не позволял удалить защищённый каталог. Inbox доступен
локальному администратору для передачи подписанного разрешения; это не IPC
для произвольных команд или путей. Исходные ACL/SDDL сохраняются для отката
при частичной ошибке настройки.

Это препятствие штатному вмешательству локального администратора, не защита
от атакующего с kernel/debug/backup/take-ownership привилегиями или загрузкой
другой ОС. Linux root тоже остаётся границей доверия: файлы и units root-owned,
непривилегированный пользователь не может менять программу и конфиги. Root
может отключить механизм вне штатного протокола; это не скрывается.

На Linux с GuardRepair системный менеджер запускает X11 Capture в transient unit
`watcher-capture-guard-<uid>.service` с правами вошедшего пользователя.
Остановка прежнего `systemd --user` launcher больше не выключает этот Capture.
После завершения процесса системный unit перезапускает его через 5 секунд;
подписанный stop останавливает и эти units. Процесс остаётся принадлежащим
пользователю: постоянное завершение процессов или отключение X11-сессии
не покрываются обещанием непрерывности записи.

## Обслуживание онлайн и офлайн

Обычные обновления уже защищённых агентов задаются целевой версией группы
на странице «Обновления». Сервер автоматически выпускает привязанную команду
через существующий доверенный канал; отдельный update на каждом хосте не нужен.
Для Windows требуется подписанный MSI этой версии, также для защищённой
установки из ZIP.

### Инструкция оператора (0.16)

Хост → вкладка «Инфо» → панель «Обслуживание защищённого агента».

- **Станция на связи.** Нажмите нужное действие — рядом написано, что и когда
  произойдёт: «Остановить» (на 15/30/60 минут, потом защита сама запустит агент),
  «Возобновить», «Восстановить», «Удалить…» (с подтверждением). Команда уйдёт
  агенту при следующем обращении к серверу и выполнится в течение пары минут.
  Файл скачивать не нужно. Ход — в «Последних командах»: выдано → получено
  агентом → выполнено или ошибка с причиной.
- **Станция без связи.** Раскройте «Станция без связи», выберите действие и срок
  файла, нажмите «Скачать файл разрешения» (для обновления — ещё «Скачать пакет»).
  Скопируйте файлы на станцию и выполните показанную команду в их папке:
  Windows (командная строка от администратора) —
  `"C:\Program Files\WatcherGuard\GuardRepair.exe" submit watcher-maintenance-<id>.json`,
  Linux — `sudo /var/lib/watcher/guard/GuardRepair submit watcher-maintenance-<id>.json`
  (для обновления добавить `--package <пакет>`). Команда сразу скажет, принят ли
  файл (просрочен, не для этой станции, уже выполнен — тоже). Через пару минут
  проверить: `GuardRepair status` — защита, база восстановления, ожидающие и
  последние выполненные разрешения. На сервере итог появится, когда станция
  снова выйдет на связь.
- **«Дополнительно»**: выбор учётки (обычно не нужен — берётся последняя активная
  с защитой), разовое обновление одного хоста, смена ключа обслуживания.

### Как это устроено

Администратор выдаёт разрешение на действие:
`stop`, `resume`, `repair`, `update`, `uninstall`, `rotate-key`.
Разрешение содержит binding конкретной учётки, kind, действие, время,
одноразовый ID и срок 1..60 минут (UI 5..60). Агент проверяет отдельный pin,
подпись P-256, время и сохраняет потреблённый ID **до** выполнения действия.
Ошибка записи replay-журнала запрещает выполнение. Откат часов более минуты
запрещает новые действия до восстановления доверенного времени.

Stop останавливает компоненты данной установки до истечения разрешения;
затем Guard возобновляет обычную проверку. Resume снимает паузу. Repair
разрешает повторить восстановление после исчерпания автоматических попыток.
Update принимает только MSI/DEB/RPM: HTTPS-загрузка без редиректов, ограничение
размера/времени, SHA-256 и независимая подпись издателя. Защищённый Windows-агент из ZIP
переходит на MSI целевой версии через групповой канал Guard. Очереди, персональные учётки и
проверенные конфиги сохраняются; defaults повреждённый конфиг не заменяют.

Офлайн: скачать JSON-разрешение в UI, передать на станцию и выполнить
`GuardRepair submit grant.json` (Windows — `"C:\Program Files\WatcherGuard\GuardRepair.exe"`, постоянный путь с 0.16; Linux —
`sudo /var/lib/watcher/guard/GuardRepair submit файл.json`, постоянный путь с 0.16). Для обновления добавить
`--package /path/to/package.msi` (либо .deb/.rpm). Файл из пользовательского
inbox повторно проверяет привилегированный Guard перед выполнением. Приём
не означает успех: выполнение происходит следующим тиком, обычно в течение
двух минут, и результат возвращается при восстановлении связи.

Не выдавать противоречащие друг другу разрешения одновременно: каждое
действующее подписанное разрешение остаётся полномочием до своего срока или
потребления. Для офлайн-станции нельзя отозвать уже переданный документ через
сервер. Начальный offline-экспорт без отчёта о pin подписывается активным
серверным ключом; оператор должен убедиться, что именно он закреплён на агенте.

Uninstall оставляет отдельный подтверждённый маркер удаления: истечение срока
не запускает переустановку. Guard сохраняет отчёт до серверного подтверждения,
после него отключает своё расписание и удаляет персональные учётки. При
отсутствии сети служебная задача остаётся только для доставки результата.
Повторная установка использует прежний pin и начинает новый снимок конфигов;
учёток после удаления нет, поэтому ей нужен действующий токен регистрации
(MSI и `install.sh` комплекта его содержат, ручной `watcher-agent-setup` — `--enroll-token`).
Удаление карточки защищённого хоста ожидает подтверждение uninstall; аварийное
`forgetProtected=true` лишь забывает утраченную VM, legal hold не обходит.

## Независимое восстановление

Windows: SYSTEM-задача `\Microsoft\Watcher\GuardRepair` при загрузке и каждые две минуты,
приватный каталог `C:\Program Files\WatcherGuard`, отдельно от основного MSI.
С 0.16 без PowerShell: действие задачи — `WatcherGuard\GuardRepair.exe tick`,
постоянный лаунчер. Он проверяет SHA-256 и запускает версию из `bin\<hash>` по
файлу `launcher` (раньше это делал `recover.ps1`). Права каталогов, реестра и
службы (бывший `protect.ps1`) и включение защиты (бывший `guard-install.ps1`,
команда `GuardRepair install`) — в самом GuardRepair.
Помощник — `GuardRepair.exe` (Linux — `GuardRepair`).
Существующий приватный каталог пока сохраняется для совместимости.
Linux: `watcher-guard.timer`, приватный `/var/lib/watcher/guard`. С 0.16 без
shell-скриптов: `watcher-guard.service` запускает постоянный лаунчер
`/var/lib/watcher/guard/GuardRepair tick` (раньше `recover.sh`), он проверяет SHA-256
и запускает версию из `bin/<hash>`. Включение защиты — `GuardRepair setup`
(раньше `setup-guard.sh`, вызывает `watcher-agent-setup --maintenance-key`),
после обновления пакета postinstall выполняет `GuardRepair setup --refresh`.
Распаковка single-file идёт в закрытый `/var/lib/watcher/guard/bundle`.
Одноразовые тики взаимно исключены.

Проверяются основной executable, известные критичные файлы и конфиги,
регистрация/путь/права службы Windows, сохранённые Linux units. Исправный
остановленный автоматический сервис запускается, ручной/отключённый режим
сам по себе не превращается в автоматический. Конфиги восстанавливаются
побайтно из проверенного снимка; повреждённые до 1 МиБ сохраняются в quarantine.
Новая регистрация, удаление очереди и сброс настроек не используются.

Для восстановления отсутствующего/изменённого бинарника нужен **уже имеющийся
локальный пакет с подписью издателя**. Подготовленный комплект сохраняет
его при первом включении Guard: Windows извлекает generic MSI из встроенного
потока, Linux копирует DEB/RPM с подписанным манифестом. Учётки и конфиги
станции в эту базу не входят; они восстанавливаются из закрытых снимков.
Проверяются SHA-256, платформа, версия, размер и подпись publisher key.
Принятый после успешного update `LastVerifiedPackage` имеет приоритет над
начальной базой. Новый Guard требует проверенную текущую базу до запуска
update: старой установке без неё нужна контролируемая подготовка, а не
непроверенная замена.

При ошибках — паузы 1/5/30 минут, после трёх попыток нужен подписанный repair.
Сетевой сбой сам по себе не переустанавливает агент. Незавершённая операция
update/stop перестаёт удерживать паузу после срока разрешения; повторное
выполнение nonce запрещено. Журнал операций ограничен двумя файлами около
1 МиБ; отдельные результаты сохраняются до подтверждения сервера. Проверять
место приватного каталога вместе с обычной эксплуатацией станции; кэш пакетов,
версии Guard и forensic-копии не являются хранилищем бесконечной ёмкости.

## Ротация и аварийное обслуживание

Для ротации сохранить старый PEM в `MaintenancePreviousSigningKeyPath`,
новый поставить активным. Сервер выбирает прежний ключ по последнему pin
учётки и подписывает `rotate-key` с новым открытым ключом. После подтверждения
и нового отчёта о pin последующие разрешения подписываются новым ключом.
Старый закрытый ключ удалять только после миграции всех нужных станций.

Если сервер/закрытый ключ утрачен, нужен независимый административный доступ
к станции: SYSTEM на Windows или root на Linux. Сначала сохранить приватный
каталог, идентичность, policy, replay-журнал, снимки и журналы для разбора;
исправить часы либо явно заменить pin и серверный ключ в контролируемой
процедуре. Не удалять consumed-журнал ради повторного выполнения старого
разрешения и не стирать данные очереди. Автоматического обхода подписи при
недоступности сервера нет.
