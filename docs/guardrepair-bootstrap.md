# GuardRepair: начальная база восстановления и подготовленные комплекты

Этап после группового канала обновлений. Подготовленный `build-kit.sh`
включает защиту Windows MSI и Linux `install.sh` без ручного ввода ключа
обслуживания. При первом включении сохраняется доверенный пакет ремонта:
сеть и предварительный update для восстановления этой версии не нужны
(Windows — если рядом с MSI лежит его `.sig`, см. ниже).

## База Windows

До 0.16 настроенный MSI нёс внутри полную копию generic MSI (потоки
`WatcherRecoveryPackage`/`WatcherRecoveryManifest`) — комплект и пакет
автообновления весили вдвое больше. С 0.16 копии нет: базой становится **сам
устанавливаемый MSI**, если рядом с ним лежит его подпись ключом обновлений
`<msi>.sig` — тот же формат `watcher-agent-update/1` (платформа, версия,
SHA-256), что у пакетов «Обновлений».

Откуда берётся `.sig`:

- комплект: `build-kit.sh` подписывает уже настроенный `windows/watcher-agent.msi`
  (после Authenticode) и кладёт рядом `watcher-agent.msi.sig`. Держите оба файла
  в одной папке и на шаре GPO; страница «Установка агентов» отдаёт оба;
- автообновление незащищённого агента: агент 0.16+ после проверки подписи
  предложения пишет её в `package.msi.sig` рядом со скачанным пакетом;
- обновление через Guard: база уже есть (`LastVerifiedPackage`), закреплять нечего.

Custom action передаёт `[OriginalDatabase]` в `GuardRepair agent-install --recovery-source`.
GuardRepair от SYSTEM копирует MSI (до 1 GiB) в закрытый `WatcherGuard\cache`,
считает SHA-256 по копии, а не по исходнику на шаре, и проверяет подпись,
платформу и версию (= версия GuardRepair). Policy публикуется после записи.

Без `.sig` (MSI скопирован один, обновление агентом 0.15.x) или с `.sig` от
другого MSI установка **не падает**: защита включается, конфиги, учётки и служба
восстанавливаются, но удалённые файлы агента Guard вернёт только после первого
обновления через Guard. Установщик пишет предупреждение в лог MSI, Guard —
событие `recovery-base` в журнал диагностики. Подделанная пара MSI/`.sig`
даёт только отсутствие базы, а не чужой пакет.

База — MSI комплекта, в нём зашит токен регистрации. Ремонт и откат Guard
передают `ENROLLTOKEN=""`: станция уже зарегистрирована. Локальный
администратор читал токен и раньше — из кэша Windows Installer и с шары.
ProductCode базы совпадает с установленным продуктом. При потере регистрации
продукта Guard использует `/i`, при наличии регистрации — `/fa`.

## Linux и неизменность данных

Архив содержит DEB/RPM и соответствующие `.recovery.json`. `install.sh`
выбирает нужный пакет и передаёт package/manifest и maintenance public key
в `watcher-agent-setup`. Пакет проверяется перед включением таймера и помещается
в `/var/lib/watcher/guard/cache` с правами 0600.

Начальная база (`InitialPackage`) закрепляется один раз. Повторный bootstrap
не заменяет её, а принятый после успешного обновления `LastVerifiedPackage`
имеет приоритет. Старые policy без нового поля продолжают читаться. Каждая
попытка ремонта заново проверяет подпись, размер и хеш кэша. Конфиги и учётки
не берутся из generic-пакета: используются прежние проверенные снимки и
закреплённые пути. Прежние очереди/видеозаписи в пакет не входят.

## Ключ обслуживания

Установщик сервера выпускает отдельную зашифрованную P-256 пару обслуживания.
Идемпотентный генератор под блокировкой не перезаписывает существующую пару;
несовпадение/неполный набор — отказ. Каталог ключей закрыт; сервер получает
только maintenance key/password через отдельный каталог с чтением группе
службы (в контейнере read-only). Publisher private key остаётся вне сервера.

Настроенные ранее `MaintenanceSigningKeyPath`/пароль не меняются. CLI
`--maintenance-public-key` читает текущую конфигурацию сервера, выводит только
публичный SPKI и не открывает БД/Kestrel. Этот ключ используется для нового
комплекта, включая серверы с ранее вручную настроенным ключом. Старые pins
на станциях не заменяются; ротация остаётся отдельной подписанной командой.
Если локальный publisher key отличается от серверного, комплект не заменяется.

Для существующего сервера сначала запускается обычный обновлённый
`install-server.sh`. `--rebuild-kit` сам не настраивает сервер и при отсутствии
доступного maintenance key сохраняет прежний комплект с сообщением об ошибке.

## Проверка и оставшаяся работа

Локально проверяются восстановление удалённых программ и регистрации через
подставную платформу без сети, неизменность учётки/конфига, отказы на подмене
метаданных/пакета, атомарность публикации и повторный seed. Отдельный тест
собирает настоящий MSI из заглушек и извлекает оба потока: байты, ProductCode
и подписи совпадают. Интеграция сборщика проверяет установочный и update MSI,
Linux install.sh/манифесты, отсутствие private key/password и enrollment-токена
в Windows-базе и update MSI. Ключи тестов только временные.

Это ещё не проверка установки на ОС: необходим совместный прогон на Windows
10/11/Server и Debian/RHEL VM: первая установка, удаление основного каталога
и регистрации службы/продукта, отсутствие сети, GPO/UNC, обновление/отказ,
manual/disabled startup и подписанное удаление. Нативные MSI API на Linux
не исполнялись. Production этой работой не меняется.

Переход C:\Watcher через подготовленный ZIP (следующий этап) убран в 0.16.
Откат последующих обновлений и очистка кэша описаны в
[следующем этапе](guardrepair-update-rollback.md). Другие ZIP-пути остаются
отдельной работой. Прямой общий пакет
без серверной подготовки не получает защиту автоматически. Новый bootstrap
не заменяет проверку доступности места для локальных снимков и пакетов.

Результат локального прогона 2026-11-05: 151 тест агента и 762 теста сервера
прошли. Принудительная сборка сервера и сборка GuardRepair — 0 предупреждений
и ошибок. MSI packaging, интеграция комплекта, генерация maintenance key,
CLI public key, 15 сценариев миграции Windows-задачи, 5 ZIP-сценариев и
4 Linux launcher-сценария прошли; ShellCheck, Bash/PowerShell parsing и
`git diff --check` прошли. Проверка NuGet vulnerability feed при первом
restore была недоступна; это не результат аудита зависимостей.

Для воспроизведения проверок упаковки после сборки сервера:

```bash
bash installer/test-msi.sh
bash tools/agent-kit/test-bootstrap.sh
bash tools/update-signing/test-maintenance-key.sh
DOTNET=dotnet bash tools/update-signing/test-maintenance-cli.sh
```
