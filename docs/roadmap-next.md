# Roadmap — следующий этап (после v0.8.0)

Статусы: 🔲 Не начато · 🟡 В работе · ✅ Готово · ⛔ Заблокировано

План составлен после прохода по всей репе (сервер, агенты, инсталляторы,
веб-UI, доки) под четыре вопроса: безопасность/HTTPS, консольный аудит на

## Порядок работ, коротко

| Этап | Что | Зачем именно в таком порядке |
|---|---|---|
| **A** | Быстрые фиксы безопасности (A1–A6) | Дешёвые, без архитектурных решений. A1 (XSS) — реальная уязвимость уже сейчас. |
| **B** | HTTPS для агентов, обязательный токен, закрытый :5050 (B1–B3) | Сейчас прод на голом HTTP: видео, пароли не идут, но **токен агента и все записи** идут открытым текстом по LAN. |
| **C** | Роли, управление пользователями, журнал доступа (C1–C3) | Нужно до редизайна веба: новые страницы сразу строятся с учётом ролей. |
| **D** | Windows: одна схема через службу вместо «обычная/RDS» (D1–D3) | Упрощает инсталлятор и GPO; служба нужна заодно под консольный аудит Windows (этап F). |
| **E** | Редизайн веб-UI (E1–E6) | Опирается на C (роли) и A1 (экранирование). |
| **F** | Консольный/SSH-аудит на Windows (F0 спайк → F1–F3) | Самое неопределённое: сначала спайк на тестовой VM, потом реализация поверх службы из D. |
| **G** | Индивидуальные учётки агентов (G1) | Логичное продолжение B. Не блокер, но убирает подделку `host`. |
| **H** | Готовность к проду во многих организациях (H1–H11) | AD/LDAP, обновление агентов, подпись кода, мониторинг, бэкапы, хранилище. Нужно до массовой раскатки. |

Этапы A и B можно делать параллельно с D. E и F независимы друг от друга.

**До всех этапов** — исправления из `code-review-2026-10.md` (R1–R3, R6): там тихая
потеря данных аудита.

## Этап A — быстрые фиксы безопасности

### Задача A1 — XSS в веб-UI через данные от агентов и URL

**Статус:** ✅ · **Объём:** S · **Приоритет:** высокий

**Что не так.** `index.html` вставляет в `innerHTML` неэкранированные строки.
Часть из них приходит от агента (то есть из любого места, где есть общий
`ApiToken`), часть — из URL:
- `renderHost`: `crumb.innerHTML = \`... <span>${host}</span>\`` — `host` берётся
  из `location.hash`, это **reflected DOM XSS по ссылке** (админу присылают
  ссылку `#/h/<img src=x onerror=...>`).
- Таблица сегментов: `${s.startReason}`, `${s.sessionUser}`; `<option>` с
  `${u}` (sessionUser) — всё это поля из `meta.json` агента.
- Таблица `#/terminal`: `${s.host}`, `${s.sessionUser}` (input экранируется,
  остальное нет).

Сервер эти поля не валидирует (`Program.cs`, `/api/upload` и `/api/upload-terminal`),
поэтому скомпрометированная станция или любой, кто знает токен, получает
выполнение JS в браузере админа, то есть его сессию.

**Что сделать.**
1. Одна функция `esc()` и правило «в `innerHTML` только через `esc()`», либо
   `textContent`/`createElement` для данных. Пройти все шаблонные строки в
   `index.html`.
2. На сервере ограничить `host`/`sessionUser`/`startReason`: длина ≤ 128,
   допустимый набор символов. Не валидно — 400. Это защита второго слоя, не
   замена п.1.
3. Тест: `UploadEndpointTests` отклоняет `host` с `<`/`>`/кавычками.

**Сделано (2026-10-07):** `esc()` в `index.html`, применён во всех
innerHTML-вставках (`crumb` по `location.hash`, таблицы сегментов/терминала/
парка, `<option>` списки, label конфига) — не только перечисленные в находке,
`h.ipAddress`/`h.agentVersion`/`g.name` того же класса (самоопубликованы
агентом/той же cookie-сессией), прошлись по всему файлу, не только по списку
из находки. `UploadValidation.IsSafeMetaField` на сервере — длина ≤128, без
`< > " ' \`` и control-символов — применена к `host`/`sessionUser`/`startReason`
в `/api/upload` и `host`/`sessionUser` в `/api/upload-terminal` (`input`
сознательно НЕ ограничен — текст из терминала непредсказуем по длине/символам,
отказ/обрезка здесь означали бы тихо терять часть аудита, то же R1/R3). Новые
тесты на оба эндпоинта (`Host_with_html_breaking_chars_returns_400`,
`StartReason_with_quote_returns_400`).

### Задача A2 — cookie без Secure за Caddy, SameSite по умолчанию

**Статус:** ✅ · **Объём:** S

**Что не так.** Kestrel за Caddy видит запрос как `http` (нет `UseForwardedHeaders`),
а `CookieSecurePolicy` по умолчанию `SameAsRequest`, поэтому `watcher_auth`
выдаётся **без флага `Secure`**. `SameSite` не задан явно (Lax). CSRF-защиты
нет, а мутирующие эндпоинты (`PUT .../config`, `DELETE /api/groups/...`)
работают на одной cookie.

**Что сделать.** `UseForwardedHeaders` (доверять только прокси из
docker-сети), `Cookie.SecurePolicy = Always` (с настройкой для dev без TLS),
`Cookie.SameSite = Strict`, `HttpOnly` (уже по умолчанию, зафиксировать явно).
Для мутирующих `/api/*` требовать заголовок `X-Requested-With`
или проверять `Origin`. Этого хватает против CSRF при SameSite=Strict без
полноценных antiforgery-токенов.

**Сделано (2026-10-07):** `UseForwardedHeaders` — доверяет только диапазону
дефолтных Docker-бриджей (`172.16.0.0/12`), не конкретному IP (не фиксирован
между перезапусками compose; порт сервера не published на хост, `expose`, не
`ports`, так что доверять сети, а не списку адресов, безопасно). `Server__CookieSecure`
(дефолт `true`) переключает `Cookie.SecurePolicy` между `Always` и
`SameAsRequest` — вторая только для dev/тестов без TLS впереди.
`SameSite=Strict` + `HttpOnly` зафиксированы явно. CSRF-гейт — в `AuthGate.cs`:
мутирующий `/api/*` под cookie-сессией без заголовка `X-Requested-With` → 403
(машинные пути `/api/upload`/`/api/heartbeat` не затронуты — у них Bearer, не
cookie). `index.html`: все мутирующие `fetch` переведены на обёртку `apiFetch`,
которая этот заголовок проставляет сама. Тесты: атрибуты cookie по умолчанию
(`Login_cookie_has_secure_and_samesite_strict_by_default` — Kestrel пишет их в
нижнем регистре, `secure`/`samesite=strict`/`httponly`, не как в
`CookieOptions`), отказ без заголовка (`Mutating_api_request_without_csrf_header_is_rejected`).
Остальные тесты, которые дёргают мутирующие `/api/*` под `_authed`, получили
тот же заголовок по умолчанию на клиенте.

### Задача A3 — нет ограничения попыток логина

**Статус:** ✅ · **Объём:** S

**Что не так.** `/api/login` можно перебирать без ограничений; тайминг-защита
(`DummyHash`) есть, rate limit нет. Требований к паролю нет: `--reset-password
--password 1` пройдёт.

**Что сделать.** Встроенный `Microsoft.AspNetCore.RateLimiting`: fixed window на
IP + на username, например 10 попыток за 5 минут. Минимальная длина пароля
(12) в `CliCommands` и в будущем UI пользователей (C2). Логировать неудачные
входы с IP (пригодится для C3).

**Сделано (2026-10-07):** `AddRateLimiter` с политикой `"login"` — fixed
window по IP (`RateLimitPartition.GetFixedWindowLimiter`, 20/5 мин), отдельно
от неё словарь `loginAttemptsByUser` в `Program.cs` — 10 попыток/5 мин на
username (по IP не ловит распределённый перебор одного логина с разных
адресов, по username не ловит перебор многих логинов с одного — нужны оба).
Счётчик по username сбрасывается на успешный вход. `MinPasswordLength = 12` в
`CliCommands.ResetPassword` (не трогает сгенерированный случайный — тот
всегда 32 hex-символа). Неудачные и заблокированные попытки логируются с IP
(`ctx.Connection.RemoteIpAddress`), пароль не логируется. Тесты:
`Repeated_failed_logins_for_same_user_get_rate_limited`,
`ResetPassword_with_short_password_is_rejected`.

### Задача A4 — заголовки безопасности и отдельный JS-файл

**Статус:** ✅ · **Объём:** S

**Что сделать.** В `Caddyfile`: `header { Strict-Transport-Security ...;
X-Frame-Options DENY; X-Content-Type-Options nosniff; Referrer-Policy no-referrer;
Content-Security-Policy "default-src 'self'; img-src 'self' data:; media-src 'self'" }`.
CSP без `unsafe-inline` требует вынести `<script>`/`<style>` из `index.html` в
файлы. Это естественно делается в E1, поэтому до E1 можно временно разрешить
`'unsafe-inline'` для style.

**Сделано (2026-10-07):** `Caddyfile` — `Strict-Transport-Security`,
`X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`,
`Referrer-Policy: no-referrer`, `Content-Security-Policy` (`'unsafe-inline'`
снят в E1, см. ниже). **Отклонение от
примера в находке**: `<script>` в `index.html` тоже инлайн, не только
`<style>` — CSP без `script-src 'unsafe-inline'` рвёт вообще весь UI (ни одна
кнопка не работает), не только стили, поэтому `'unsafe-inline'` временно
разрешён для ОБОИХ `script-src` и `style-src`, не только `style-src` как
предполагала находка. Сам вынос в файлы — Задача E1, не в объёме A4.

### Задача A5 — контейнер под root, падения на кривом вводе

**Статус:** ✅ · **Объём:** S

**Что не так.**
- `Dockerfile` не задаёт `USER`, сервер работает под root внутри контейнера.
- `/api/upload`/`/api/upload-terminal`: `JsonDocument.Parse` и `DateTime.Parse` по
  данным агента без `try`. Кривой `meta.json` даёт 500 и стектрейс в логе
  вместо 400.
- `/api/upload-terminal` читает весь `.out` в память (`File.ReadAllTextAsync`)
  ради `search_text`, при `MaxUploadSizeMb=512` это до 512 МБ в строке и в SQLite.

**Что сделать.** `USER app` (есть в образе `aspnet:8.0`, нужен `chown` на
`/data`). Разбор meta вынести в одну функцию с `TryParse`, которая на ошибку
возвращает 400. `search_text` обрезать до разумного лимита (например, первые 1–2 МБ)
с пометкой «усечено».

**Сделано (2026-10-07):** `USER app` в `Dockerfile` runtime-стадии
(`mcr.microsoft.com/dotnet/aspnet:8.0` уже содержит этого пользователя для
ровно такого случая) + `chown -R app:app /data /app` до переключения
пользователя, иначе `app` не смог бы писать в примонтированный volume.
`TryParseUploadMeta`/`TryParseTerminalMeta` в `Program.cs` — весь JSON/дата/
число разбор под `try`, 400 вместо 500 на любую ошибку (невалидный JSON,
`startedAt` не дата, `sessionId` не число и т.п.); обе функции возвращают
record struct со всеми полями, эндпоинты больше не трогают `JsonDocument`
напрямую. `ReadSearchTextTruncated` — читает не больше 2 МБ из `.out`
(`SearchTextMaxBytes`), не весь файл в память, с пометкой `...(усечено)` в
конце при обрезке. Тесты: `Malformed_meta_returns_400_not_500`/
`Invalid_json_meta_returns_400_not_500` на обоих эндпоинтах,
`Huge_output_search_text_is_truncated`.

### Задача A6 — `--reset-password --password` светит пароль в `ps`/истории

**Статус:** ✅ · **Объём:** S · **Приоритет:** низкий

**Что сделать.** Режим по умолчанию оставить «сгенерировать случайный» (уже
есть). Явный пароль читать из stdin (`--password-stdin`), а аргумент
`--password` пометить в доках как небезопасный.

**Сделано (2026-10-07):** `--password-stdin` читает пароль через
`Console.In.ReadLine()`, пустая строка со stdin — ошибка, не тихий пустой
пароль. `--password <пароль>` оставлен (скриптам без интерактивного stdin),
но в usage-сообщении и в `docs/install.md`/`docs/operations.md` помечен как
видимый в `ps`/истории — везде, где раньше были примеры с `--password`,
основной вариант теперь `--password-stdin`. Тест:
`ResetPassword_with_password_stdin_reads_from_stdin`.

**Этап A целиком закрыт тем же днём** — все 6 задач (A1–A6) плюс
R1–R3/R6 из `code-review-2026-10.md` (условие «до всех этапов» выше, закрыто

## Этап B — HTTPS для агентов

### Задача B1 — агенты ходят на сервер по голому HTTP

**Статус:** ✅ · **Объём:** M · **Приоритет:** высокий

**Что не так.** Все примеры в доках и `deploy.sh` используют
`http://192.0.2.10:5050`. В Docker-варианте порт 5050 даже не опубликован
(`expose`), то есть доки агентов фактически описывают systemd-fallback.
HTTPS есть только для браузера (`tls internal` в Caddy), а для агентов у
самоподписанного сертификата нет схемы доверия: ни .NET `HttpClient` в
Uploader/TerminalAgent, ни инсталляторы не знают про корневой CA Caddy. На
практике всё (видео, консольный ввод, токен) идёт открытым текстом.

**Что сделать.** Выбрать один из двух вариантов (рекомендация — **1**):
1. **Корневой CA Caddy раздаётся станциям.** `caddy-data/.../pki/authorities/local/root.crt`
   экспортируется командой `install-server.sh --export-ca`. Windows: `install.ps1 -CaCertPath`
   и GPO «Trusted Root» (для GPO-деплоя это стандартная практика). Linux:
   `--ca-cert` в `/usr/local/share/ca-certificates` + `update-ca-certificates`.
   Агентский код менять не нужно: `HttpClient` использует системное хранилище.
2. **Пиннинг отпечатка в конфиге агента** (`ServerCertSha256`) через свой
   `ServerCertificateCustomValidationCallback`. Не трогает системное хранилище, но
   требует кода в двух агентах и ротации отпечатка при перевыпуске.

Если в компании есть свой AD CS / корпоративный CA — вместо `tls internal`
выпустить сертификат им, тогда п.1 вообще не нужен (корень уже доверенный).

Плюс: доки и примеры перевести на `https://<WATCHER_DOMAIN>`, `ServerUrl` с
`http://` на не-localhost — предупреждение в логе агента и в `#/fleet`.

**Сделано (2026-10-07):** выбран вариант 1 (CA Caddy станциям), без изменений
в агентском коде доверия — `HttpClient` использует системное хранилище.
`install-server.sh --export-ca [file]` — `docker compose exec watcher-proxy
cat .../pki/authorities/local/root.crt` в файл. `install.ps1 -CaCertPath` —
`Import-Certificate` в `Cert:\LocalMachine\Root`. `install-capture-linux.sh`/
`install-terminal-agent.sh`/`install-linux-agent.sh` — `--ca-cert`,
`update-ca-certificates` (у `install-capture-linux.sh` через `sudo` — сам
скрипт намеренно не root, см. его же комментарий). MSI/GPO — без нового
MSI-свойства: доверие раздаётся самой GPO (Trusted Root Certification
Authorities), это уже штатный механизм, задокументирован, не реализован
кодом. Предупреждение о `http://` на не-localhost — на каждом старте в логе
`Watcher.Uploader` и `Watcher.TerminalAgent` (не только один раз при
установке), и в `#/fleet`: сервер пишет `Request.IsHttps` (после
`UseForwardedHeaders`) в `hosts.last_heartbeat_https` на каждый heartbeat —
то, что сервер реально увидел на проводе, не самоотчёт агента о своём
`ServerUrl` — и веб-UI показывает бейдж «HTTP» в колонке «Соединение».
Доки (`install.md`, `configuration.md`, `architecture.md`) переведены на
`https://<WATCHER_DOMAIN>` с отдельным dev/без-TLS примером там, где он ещё
актуален. Тест `Heartbeat_over_plain_http_is_flagged_in_fleet_list`
(остальные случаи — живая проверка на тестовом стенде).

### Задача B2 — пустой `ApiToken` = открытый upload

**Статус:** ✅ · **Объём:** S

**Что не так.** `RequireToken` пропускает всё, если `ApiToken` пуст. `.env.example`
по умолчанию пуст (с пометкой «не для прода», но это легко пропустить).

**Что сделать.** Сервер не стартует с пустым `ApiToken`, если не задан явный
`Server__AllowAnonymousAgents=true` (для dev). `install-server.sh` генерирует
токен так же, как пароль, и печатает его.

**Сделано (2026-10-07):** `UploadValidation.AgentTokenMissingWithoutOptIn`
(чистая функция, протестирована отдельно) + проверка в `Program.cs` сразу
после биндинга `ServerConfig` — `Environment.Exit(1)` с понятным сообщением
в stderr, до `Directory.CreateDirectory`/`builder.Build()`. Новый
`ServerConfig.AllowAnonymousAgents` (default `false`). `install-server.sh`
генерирует `ApiToken` (`openssl rand -hex 24`) тем же шагом, что пароль
админа, печатает один раз. `.env.example`/`docs/configuration.md` обновлены —
пустой `Server__ApiToken` теперь требует явного
`Server__AllowAnonymousAgents=true` рядом, иначе и Docker Compose, и
systemd-инстанс не стартуют. Тест: `AgentTokenMissingWithoutOptIn_requires_token_or_explicit_optin`
(7 кейсов) — сам `Environment.Exit` не тестируется юнит-тестом (убил бы
процесс `dotnet test`), только чистая функция решения.

### Задача B3 — systemd-fallback слушает 0.0.0.0:5050 без TLS

**Статус:** ✅ · **Объём:** S

**Что сделать.** `install-server.sh` по умолчанию: `ASPNETCORE_URLS=http://127.0.0.1:5050`
+ Caddy/nginx перед ним (шаблон в репе), либо Kestrel с собственным
сертификатом (`Kestrel:Endpoints:Https`). Прямой HTTP наружу — только явным
флагом.

**Сделано (2026-10-07):** `EXPOSE_HTTP` (default `false`) в `install-server.sh`
— `false` → `127.0.0.1`, `true` → старое поведение (`0.0.0.0`, без TLS, с
явным предупреждением в выводе установщика). **Находка, которой не было в
описании задачи**: простой `ASPNETCORE_URLS` в systemd-юните НЕ работает —
`Kestrel:Endpoints:Http:Url` в самом `appsettings.json` побеждает переменную
окружения (подтверждено живым запуском: Kestrel логирует "Overriding
address(es) ... Binding to endpoints defined via IConfiguration instead" и
реально слушает адрес из файла). Пришлось явно писать адрес в генерируемый
`appsettings.json` (`Kestrel.Endpoints.Http.Url`), не только в
`Environment=ASPNETCORE_URLS=...` юнита — иначе фикс был бы no-op на свежей
установке. `Caddyfile.systemd-example` в корне репозитория — тот же набор
заголовков/CSP, что у Docker-варианта (A4), `reverse_proxy 127.0.0.1:5050`.

## Этап C — роли, пользователи, журнал доступа

### Задача C1 — роли есть в БД, но нигде не проверяются

**Статус:** ✅ · **Объём:** M

## Этап D — Windows: одна схема вместо «обычная станция / RDS»

### Задача D1 — сделать службу единственным режимом запуска Capture

**Статус:** ✅ · **Объём:** M

**Ответ на вопрос «нужно ли разделение»: нет, не нужно.** Сейчас два режима:
- обычный — Scheduled Task на `BUILTIN\Users`, `AtLogOn` + повтор раз в минуту,
  `MultipleInstances=IgnoreNew`;
- RDS — служба `WatcherSessionService` (LocalSystem), которая на каждую
  сессию запускает Capture через `CreateProcessAsUser`, с watchdog'ом каждые 15 с.

Режим службы — **надмножество** обычного: обычная станция — это частный случай
«одна интерактивная сессия». Выигрыш от одной схемы:
- один путь кода и один тестовый сценарий вместо двух;
- исчезают `-RdsMode`/`RDSMODE=1`/`RDSMODE` в Bundle и Package.wxs, Задача 8
  из `roadmap-fixes.md` становится неактуальной; GPO-деплой без вариантов;
- перезапуск после падения Capture — 15 с вместо «до минуты»;
- корректно работает быстрое переключение пользователей на обычной станции
  (там тоже несколько сессий, и задача с `IgnoreNew` даёт ту же проблему, что на RDS);
- имя пользователя (`sessionUser`) приходит всегда; UI уже умеет прятать
  колонку, когда пользователь один.

**Что проверить спайком на обычной Win10/11 (не RDS) до переключения:**
- консольная сессия после перезагрузки: служба стартует раньше логона, сессия
  появляется через `SessionLogon` — запуск должен сработать;
- блокировка экрана / UAC secure desktop: что пишет BitBlt (ожидаемо чёрный
  кадр — тогда не открывать сегмент, это уже покрывается motion-логикой);
- быстрое переключение пользователей: два Capture в двух сессиях, имена
  файлов не конфликтуют (`--session-user` уже это решает);
- обновление поверх старой установки: `Stop-Tasks` уже снимает `WatcherCapture`.

**Что сделать.** `install.ps1` всегда регистрирует службу; `-RdsMode` оставить
как принимаемый, но игнорируемый параметр (с предупреждением) на один релиз,
чтобы не сломать существующие GPO/скрипты. В MSI — то же для `RDSMODE`.
Обновить `architecture.md`, `install.md`, `configuration.md`.

**Сделано (2026-10-08).** Спайк — на тестовых Win10 и Win11 (не RDS),
пользовательские сессии через RDP двумя временными локальными учётками, на

### Задача E4 — консоль: проигрывание в браузере

**Статус:** ✅ · **Объём:** M · **Зависит от:** E2

и вывод (`terminal-output`) одной сессии связываются и показываются рядом; если

**Сделано (2026-10-08):** клик по строке «Консоли» (раздел или вкладка хоста)

Размер терминала — из заголовка `.out` (`Script started on … COLUMNS="…"
LINES="…"`, util-linux 2.38), строки «Script started/done» на экран не
попадают (в `.timing` их нет). `.timing` читается в обоих форматах script(1):

`watcher-term-wrap.sh` время с точностью до секунды; `Db.TerminalOverlapping`).
Общего id по-прежнему нет: интервал `script` лежит внутри интервала SSH-сессии

## Этап F — консольный/SSH-аудит на Windows

**Как сделано на Linux (для сравнения):** ввод — `pam_tty_audit` → auditd →
`AuditLogTailer`; полный вывод экрана — `script(1)`, подключённый через
`/etc/profile.d`, **без замены login shell'а** (замена отклонена из-за риска
заблокировать вход, см. `roadmap.md`, Фаза 8). Отправка — `TerminalAgent` →
`/api/upload-terminal` (`terminal-input` / `terminal-output`).

**Аналоги на Windows** (встроенный OpenSSH Server, `sshd` + PowerShell/cmd):

| Linux | Windows-аналог | Комментарий |
|---|---|---|
| `script` через `/etc/profile.d` (вывод) | **PowerShell Transcription** (GPO / `HKLM\...\PowerShell\Transcription`, `OutputDirectory`) | Встроенный механизм, пишет и команды, и вывод каждой PowerShell-сессии в текстовый файл. Shell не подменяется — ровно тот же принцип, что выбран на Linux. |
| `pam_tty_audit` (ввод) | **Script Block Logging** (Event ID 4104, `Microsoft-Windows-PowerShell/Operational`) + аудит создания процессов с командной строкой (4688) | 4104 — точный текст выполненных команд PowerShell; 4688 закрывает `cmd.exe` и запуск программ. |
| `remoteAddr`, начало/конец сессии из audit | `OpenSSH/Operational` (подключение, пользователь, адрес) + Security 4624/4634 | Связка сессии с IP клиента. |

**Поправка по итогам F0:** 4104 для пользователя без прав администратора в
SSH-сессии не генерируется — ввод и вывод берутся из транскрипта, 4688 —
дополнение (запуски программ), см. Задачу F0.

### Задача F0 — спайк на тестовой Windows VM

**Статус:** ✅ · **Объём:** M

Проверить живьём (как делалось для Фазы 6/8):
1. `DefaultShell` у sshd = `powershell.exe` / `pwsh.exe`: транскрипт пишется
   для интерактивной ssh-сессии? для `ssh host "команда"`?
2. `scp`/`sftp`/автоматизация (Ansible по ssh) не ломаются — у транскрипта нет
   побочных эффектов на stdout, проверить.
3. Сессия с `cmd.exe` как `DefaultShell`: что видно через 4688, есть ли смысл
   рекомендовать PowerShell как shell для ssh.
4. Кодировки (UTF-8 vs OEM 866 в транскрипте), размер файлов, задержка
   появления событий 4104.
5. Куда пишется транскрипт и с какими правами. Файл создаёт процесс
   пользователя, поэтому нужна папка с ACL «только создавать файлы» и
   забор их службой сразу после закрытия сессии. Зафиксировать, какие гарантии
   это даёт, а какие нет (так же, как в доке Фазы 8 описаны ограничения Linux-варианта).
6. RDP + локальная PowerShell — тоже попадают в транскрипт. Решить: это
   плюс (единый «консольный аудит» Windows) или нужно фильтровать по ssh.

**Сделано (2026-10-08), Win11 24H2 (PowerShell 5.1), встроенный OpenSSH,
`DefaultShell` = Windows PowerShell; тестовый локальный пользователь без прав
администратора, вход по ключу. Всё на стенде откатано.**

Результаты по пунктам:

1. **Транскрипт пишется в обоих режимах.** Интерактивная сессия — каждая
   команда с временем запуска, её вывод, в конце блок «Конец записи».
   `ssh host "команда"` — то же (команда видна как `PS>...`). Пишется **по
   ходу сессии**, не в конце; пока сессия жива, файл держит PowerShell
   (эксклюзивно не открывается), после выхода — свободен и с завершающим блоком.
   Оборванная сессия — без завершающего блока. `Stop-Transcript` транскрипт по
   политике не останавливает: ошибка, и запись тут же продолжается в тот же
   файл. Интерактивный `cmd`, запущенный из PowerShell, записывается целиком
   (приглашение, ввод встроенных команд вроде `echo`, вывод).
2. **stdout не меняется:** вывод `ssh host "команда"` побайтно тот же, `scp`
   туда-обратно — файл идентичен, `sftp` работает. Но `sftp-server.exe`
   запускается через `DefaultShell` (`powershell /c "sftp-server.exe"`), и на
   каждое scp/sftp-подключение появляется пустой транскрипт — шум,
   содержимое передачи не видно. Проброс портов (`-L`/`-R`/`-N`) виден только в
   `OpenSSH/Operational`.
3. **`DefaultShell` = `cmd.exe` — транскрипта нет вовсе** (PowerShell не
   запускается), 4688 показывает только запуски программ: `cmd /c ver` виден
   с командной строкой, встроенные команды `cmd` (`dir`, `echo`, `cd`) — нет.
   Вывод: PowerShell как `DefaultShell` — обязательное условие консольного
   аудита Windows (у нас это уже стандарт, `docs/infrastructure/windows-servers.md`
   в system_administrator); установщик должен это проверять и предупреждать.
4. **Кодировка — UTF-8 с BOM, кириллица в командах и выводе без искажений.**
   Заголовок транскрипта **локализован** («Начало записи сценария…», «Имя
   пользователя:», «ИД процесса:») — разбирать по позиции строк, не по меткам.
   Размер: заголовок ~0,8 КБ на сессию, пять команд — ~1,8 КБ.
   **События 4104 для пользователя без прав администратора в SSH-сессии не
   генерируются вовсе** — нет ни 4104, ни даже событий старта консоли
   (40961/53504); у администратора — есть. Проверено и отброшено: доступ
   канала `PowerShell/Operational` (в нём нет NETWORK, а SSH-вход на Windows —
   сетевой; добавление `NU` + перезапуск EventLog ничего не дало) и DACL ETW
   по умолчанию (публикация разрешена всем). Точная причина не найдена. **4104
   как источник ввода не годится** — источник ввода и вывода один: транскрипт.
5. **ACL папки транскриптов работает.** Папка: SYSTEM и Administrators — полный
   доступ; Users — `WD,AD,X,RA,S` (создать файл/каталог, писать); OWNER RIGHTS
   (`S-1-3-4`) — `WD,AD,RA,S` (урезает неявные права владельца: без этого
   владелец файла мог бы читать ACL и менять его); CREATOR OWNER — нет. Файл
   создаётся с владельцем-пользователем. После закрытия сессии пользователь
   **не может** перечислить папку, прочитать, дописать, обрезать, удалить,
   переименовать свой транскрипт, прочитать или изменить его ACL (проверено
   каждое действие). Гарантии ограничены сессией: пока она жива, файл
   открыт процессом самого пользователя — теоретически он может испортить
   запись изнутри своего процесса; та же граница, что у `script(1)` на Linux.
   **Fail-open подтверждён, и он молчаливый:** если папка недоступна для
   записи, вход по SSH, команды и scp работают без единой ошибки, транскрипт
   просто не создаётся — служба должна ловить такие пропуски сама (запуск
   `powershell` от `sshd` по 4688 без парного транскрипта → счётчик в
   heartbeat, как `droppedSegments`).
6. **Транскрипция — машинная политика: пишется вся PowerShell на хосте**, не
   только SSH — RDP, службы, задачи планировщика, агенты мониторинга и
   автоматизация. За время спайка наша собственная автоматизация (PowerShell
   по SSH от служебного администратора) дала 30 транскриптов против 13 от
   тестового пользователя, **с полным текстом команд и их выводом** — у
   автоматизации там бывают секреты. Отличить SSH-сессию можно по 4688:
   `powershell` в командном режиме — дочерний `sshd.exe`, в интерактивном —
   дочерний `conhost.exe`, у которого родитель `sshd.exe`; PID процесса есть в
   заголовке транскрипта. RDP с локальной PowerShell живьём не проверялся.
   `OpenSSH/Operational` даёт пользователя, IP и порт клиента
   («Accepted publickey for … from … port …»).

**Решение по пункту 6 — за владельцем перед F1:** что выгружать — только
SSH-сессии (по цепочке процессов от `sshd`), SSH + интерактивные сессии
пользователей (RDP/консоль, цепочка от `explorer.exe`), или всё. Остальные
транскрипты служба удаляет на станции, не выгружая. Рекомендация — SSH по
умолчанию, интерактивные — опцией.

Не проверено, оставлено на F1: PowerShell 7 (`pwsh`) — своя ветка политики
(`HKLM\SOFTWARE\Policies\Microsoft\PowerShellCore\Transcription`), ставить
обе; движок PowerShell 2.0 (`powershell -Version 2` обходит транскрипцию) — на
Win11 24H2 его нет, на Server 2019 компонент бывает — проверить на
RDS-стенде и рекомендовать удаление компонента.

## Этап G — учётки агентов

### Задача G1 — общий токен на весь парк, `host` никак не проверяется

**Статус:** ✅ (G1a — сервер, G1b — Windows, G1c — Linux) · **Объём:** L · **Зависит от:** B1

**Что не так.** Один `ApiToken` на все станции, лежит в конфиге на каждой.
Любой, у кого он есть, может грузить записи и heartbeat **от имени любого
хоста** (поле `host` в meta берётся как есть), читать эффективный конфиг
любого хоста, заливать файлы до 512 МБ. Отозвать доступ одной станции нельзя
без перевыпуска токена всему парку.

**Что сделать.**
- Enrollment: инсталлятор получает одноразовый (или групповой, с TTL) токен
  регистрации, при первом запуске агент вызывает `POST /api/enroll` с именем
  хоста и получает **собственный** секрет (хранится с ACL SYSTEM/root).
- Сервер привязывает секрет к `hosts.id`: `host` в upload/heartbeat берётся
  **из учётки**, а поле в meta только сверяется.
- В UI (`Настройки → Агенты`): список учёток, последний вход, «отозвать».
- Переходный период: общий `ApiToken` продолжает работать с флагом, в `#/fleet`
  у таких хостов пометка «legacy-токен».
- Альтернатива — mTLS с клиентскими сертификатами. Прочнее, но на порядок
  сложнее в выпуске/ротации для GPO-парка; рекомендация — токены.

**Решения владельца (2026-10-08):** токен регистрации многоразовый, со сроком,
лимитом и группой по умолчанию (один на раскатку через GPO/MSI); повторная
учётка у существующего хоста **не блокируется, а помечается** (в «Хостах» и в
журнале); Linux-аплоадер экрана переезжает из `systemd --user` в системную
службу — секрет хоста не должен лежать в домашнем каталоге пользователя.
Разбито на три PR: G1a — сервер, G1b — Windows, G1c — Linux.

**G1a — сервер (2026-10-08):**
- `enroll_tokens`/`agent_credentials` (`Db.Agents.cs`), секреты и токены —
  только SHA-256 (значения случайные 256 бит, медленный хэш паролей не нужен,
  а поиск по хэшу идёт на каждом heartbeat).
- `POST /api/enroll` `{token, host, kind}` → `{secret}`. `kind` — `video`
  (служба Windows, Linux-аплоадер) или `terminal` (TerminalAgent): у Linux-хоста
  законно две учётки, поэтому «повтор» — это повтор **того же вида**, иначе
  каждая Linux-установка давала бы ложную тревогу. Новый хост сразу попадает в
  группу токена; существующему группа не меняется.
- `/api/upload`, `/api/upload-terminal`, `/api/heartbeat`: хост из учётки,
  чужой `host` в meta — `403`; учётка не своего вида — `403`; отозванная — `401`.
  Общий `ApiToken` принимается, пока `AllowLegacyApiToken=true` (по умолчанию),
  heartbeat по нему ставит хосту `last_auth_legacy` — в «Хостах» пометка
  «общий токен» (и он в фильтре «Проблемы»).
- **Изменение B2:** пустой `ApiToken` больше не останавливает сервер — с
  учётками он значит «общего токена нет», то есть закрыто, а не открыто.
  Открыть без токена по-прежнему можно только `AllowAnonymousAgents=true`.
- Веб-UI: Настройки → Агенты (admin) — токены регистрации (значение
  показывается один раз), учётки (последний вход, IP, «Отозвать», «Это
  переустановка» — снять пометку повтора). Всё в журнале доступа.
- Тесты: `AgentEnrollmentTests` (10), e2e `agents.spec.js`.

**G1b — Windows (2026-10-08):**
- `AgentIdentity` в `Watcher.Uploader.Core` (общий с Linux-аплоадером): регистрация
  по `EnrollToken` на старте цикла выгрузки, повтор раз в минуту (сети при
  GPO-установке может не быть), отказ токена — раз в 15 минут. Секрет — в
  `CredentialPath` (`C:\ProgramData\Watcher\agent\credential.json`): каталог
  создаётся с собственным ACL SYSTEM+Administrators без наследования —
  `ProgramData\Watcher` открыт пользователям (там их очередь).
- `401` по секрету — учётка помечается отклонённой; тем же `EnrollToken`
  повторно **не** регистрируется (хэш токена хранится рядом с секретом), на общий
  `ApiToken` не откатывается — иначе отзыв не работал бы. Новый токен в
  конфиге — регистрируется заново.
- `install.ps1 -EnrollToken`, MSI/бутстрапер `ENROLLTOKEN`. `APITOKEN`/
  `ENROLLTOKEN` в MSI — `Hidden`, custom action — `HideTarget`: токены не
  попадают в журнал `msiexec /l*v` (проверено).
- Живая проверка (Win11, тестовый сервер из ветки): установка с
  `-EnrollToken` — регистрация, `icacls` каталога и файла — только SYSTEM и
  Administrators, heartbeat и выгрузка сегмента по учётке (`legacyAuth=false`);
  отзыв в API — агент получил `401`, заново не зарегистрировался; переустановка
  с новым токеном — новая учётка без пометки повтора (старая отозвана);
  повторный запуск `install.ps1` — новой учётки нет; MSI (`wix build` без
  предупреждений) с `ENROLLTOKEN` — регистрация, токена в журнале msiexec нет.
- Тесты: `AgentIdentityTests` (7).

**G1c — Linux (2026-10-08):**
- Аплоадер экрана — системная служба `watcher-uploader.service` (root,
  `/opt/watcher-uploader`, `ProtectSystem=full`, `ProtectHome=yes`) вместо
  `systemd --user`. Очередь — общая `/var/lib/watcher/queue` с правами `1733`;
  Capture (как и был, `systemd --user`) пишет туда с `UMask=0077`. Конфиг с
  сервера — `/var/lib/watcher/config` (`755`, читают Capture всех пользователей),
  учётка, `sent`, логи — `700` root.
- `install-capture-linux.sh` (от пользователя, системную часть ставит через
  sudo) снимает пользовательский Uploader старых установок и переносит
  неотправленное из `~/.local/share/watcher/queue` в общую очередь.
- TerminalAgent регистрируется сам (учётка вида `terminal`, `AgentIdentity` из
  `Watcher.Uploader.Core` — общая библиотека, не копия: отзыв должен работать
  одинаково), секрет — `/var/lib/watcher-terminal-agent/agent/`.
- `--enroll-token` у `install-capture-linux.sh`, `install-terminal-agent.sh`,
  `install-linux-agent.sh` (один токен на обе части — у хоста две учётки
  разного вида, не «повтор»). Конфиги с токенами пишутся под `umask 077`.
- Найдено живьём: Linux-Uploader не обрабатывал SIGTERM — `systemctl stop`
  завершал его с кодом 143, юнит уходил в `failed` (было и у пользовательской
  службы). Теперь `PosixSignalRegistration`, как у Capture.Linux/TerminalAgent:
  контроль на сборке из `main` — 143, новая — 0.
- Живая проверка (Debian 12, тестовый сервер из ветки): `install-linux-agent.sh
  --enroll-token` — две учётки хоста (экран, консоль), без пометки повтора;
  права каталогов и файлов как выше; сегмент от другого пользователя (`umask
  077`, как пишет Capture) — `claude-rw` не может ни перечислить очередь, ни
  прочитать, ни удалить файл, системный Uploader выгрузил его по учётке;
  SSH-сессия — ввод и вывод выгружены по учётке консоли; миграция со старой
  схемы (пользовательский юнит Uploader + сегмент в `~/.local/share`) — юнит
  снят, сегмент перенесён и выгружен, повторный запуск новых учёток не создал;
  `--uninstall` — службы и каталоги программы сняты. Сам захват экрана на
  стенде не гонялся (нет графической сессии, Capture изменился только конфигом
  путей и `UMask`).
- Тесты: `UploadRunnerTests` +1 (TerminalAgent с учёткой, 401).

После раскатки регистрации на весь парк — `AllowLegacyApiToken=false`.

## Этап H — готовность к проду во многих организациях

Пока Watcher стоит у одной команды, многое решается руками (`deploy.sh`,
SSH на сервер). При раскатке на десятки независимых организаций каждая
ручная операция превращается в обращение в поддержку. Ниже то, что нужно
для такого масштаба, по убыванию важности. Найденные баги кода — в
`code-review-2026-10.md`, их чинить раньше всего этого.

### Задача H1 — вход через AD/LDAP (и позже OIDC)

**Статус:** ✅ LDAP/AD (см. `docs/operations.md`, «Вход через Active Directory /
LDAP»); OIDC — ⛔ не делаем (решение владельца 2026-10-12, см. «Что сознательно
НЕ входит») · **Объём:** M · **Зависит от:** C1

В организациях учётки живут в Active Directory / FreeIPA / Samba. Отдельные
локальные пароли Watcher никто не захочет вести, а уволенный сотрудник
должен терять доступ сам, при отключении в AD. Сделать LDAP bind +
сопоставление групп AD с ролями (`Watcher-Admins` → `admin`, `Watcher-Viewers`
→ `viewer`). Локальный `admin` оставить как аварийный вход. OIDC (Keycloak,
ADFS) — следующим шагом.

### Задача H2 — обновление агентов с сервера

**Статус:** ✅ сервер (пакеты с подписью, целевая версия группы, раздел
«Обновления») и агенты (проверка подписи на станции, Windows — `update.ps1`
задачей от SYSTEM с откатом файлов, Linux — `apply-update.sh` через
`systemd-run`) — `docs/operations.md`, «Обновление агентов с сервера» · **Объём:** L · **Зависит от:** D2, B1

Сейчас обновление агента — это заново MSI или скрипт на каждой станции. На
тысячах станций в разных организациях это главная операционная боль. Сделать
так: сервер хранит пакет агента нужной версии, heartbeat отвечает
«доступна версия X для этой группы», служба скачивает пакет, **проверяет
подпись** и обновляется. Раскатка по группам (сначала пилотная), откат,
версия видна в `#/fleet`. Без проверки подписи эту функцию делать нельзя:
иначе сервер Watcher становится точкой, с которой можно запустить что угодно
на всём парке.

Решения владельца (2026-10-12):
- **Свой ключ обновлений** ECDSA P-256, не Authenticode: одинаково для Windows
  и Linux и не зависит от хранилища доверия станции. Закрытый — у владельца,
  вне сервера; открытый — на станции при установке (без него станция не
  обновляется) и на сервере (только чтобы ловить ошибки при загрузке).
  Подписывается «платформа, версия, SHA-256» (`UpdateSigning.Message`).
- **Откат разрешён**: целевая версия группы может быть старше текущей. Цена —
  взломанный сервер может откатить парк на старую, но подписанную версию.
- **Охват**: Windows (MSI и `install.ps1` — замена файлов отдельным процессом
  от SYSTEM, при неудаче — возврат старых), Linux — только `.deb`/`.rpm`
  (установка через `systemd-run`, чтобы перезапуск служб пакета не прервал её).

### Задача H3 — подпись кода и совместимость с антивирусами

**Статус:** ✅ пакеты `.deb`/`.rpm` (`watcher-agent-setup`) и подпись релиза
cosign — `docs/install.md`; Authenticode любым PFX (по умолчанию
самоподписанный с `CA:FALSE`, раздача GPO) — `docs/codesign.md`; исключения
для AV/EDR — `docs/av-edr.md` · **Объём:** S–M

Агент, который снимает экран и работает как служба, антивирусы и EDR почти
наверняка пометят как подозрительный. В каждой организации это будет первым
тикетом. Нужно: подписывать `exe`/`msi` сертификатом издателя (Authenticode),
подписывать Linux-пакеты, опубликовать для админов документ «исключения для
AV/EDR» (пути, хеши, издатель) и сделать нормальные пакеты `.deb`/`.rpm`
вместо `install-*.sh` (их проще согласовывать с ИБ заказчика).

Вместе с кадрами агент может дёшево писать заголовок активного окна и имя
процесса (раз в несколько секунд, при смене). На сервере это даёт поиск
«когда пользователь открывал X» без просмотра часов видео и подписи на
таймлайне плеера (E3). Для разборов инцидентов это главный ускоритель.
Данные попадают под те же исключения, что и видео (H8).

## Что сознательно НЕ входит

- Баннер/legal notice о записи на станциях (бывшая Задача C4: `LegalNotice*`
  на Windows, `Banner`/`/etc/issue.net`/`motd` на Linux, флагом инсталлятора).
  Убрано решением владельца 2026-10-08 — не нужно. Уведомление сотрудников о
  записи — организационная мера вне Watcher; при необходимости баннер
  ставится штатными средствами (GPO, конфиг sshd) без участия инсталлятора.

- **Нагрузочные тесты (бывшая H10).** Решение владельца 2026-10-12: проверкой
  под нагрузкой служит развёртывание в собственной сети (сотни станций), а не
  симулятор. Требования к железу для других организаций — по итогам этой
  эксплуатации (`/metrics`, H4), регулярный прогон Windows-агента на VM — по
  мере надобности вручную.
- **S3-совместимое хранилище записей (часть H6).** Решение владельца
  2026-10-12: пока не нужно — записи помещаются на диск сервера, а лимиты
  объёма и свободного места, сроки по группам и legal hold уже есть. Вернуться,
  если видео перестанет помещаться на один том.
- **Вход через OIDC (Keycloak, ADFS, Entra ID) — вторая часть H1.** Решение
  владельца 2026-10-12: вход через AD по LDAP уже закрывает доменных
  пользователей и отключение уволенных. OIDC нужен для SSO с MFA или чисто
  облачного каталога — вернуться, если появится такое требование.

- Шифрование записей на уровне приложения: дорого (ключи, поиск по консоли
  ломается), а выигрыш против шифрования диска сервера (LUKS) небольшой. В
  `operations.md` достаточно рекомендации «диск с данными — LUKS» и схемы
  бэкапа SQLite (`sqlite3 .backup`) + blobs.
- Замена SQLite на Postgres: при текущих объёмах (~300 агентов, heartbeat
  5 rps) SQLite в WAL справляется. Вернуться, если появится несколько
  инстансов сервера.
