# GuardRepair: имя помощника и миграция задачи

Этап переработки от 2026-11-05. Этот PR реализует смену имени бинарника и
перенос постоянной Windows-задачи. Требования к защите по умолчанию, новой
схеме группового обновления и начальной базе ремонта остаются следующими этапами.

Совместимое продолжение этого этапа —
[групповые обновления GuardRepair](guardrepair-group-updates.md).

## Результат

Проект `src/Watcher.Guard` публикует `GuardRepair.exe` на Windows и
`GuardRepair` на Linux. ZIP/MSI и TAR/DEB/RPM используют новые имена. На Windows
MSI также содержит переходную копию `Watcher.Guard.exe`: после Authenticode
она копируется из основного executable побайтно. Сборщик MSI отклоняет
несовпадающие копии. При сборке комплекта из готовых агентов подпись ставится
также на GuardRepair и его скрипты, затем обновляется переходная копия.

Это нужно старому GuardEngine: после проверенного обновления он пересчитывает
хеши по прежним именам. При первом тике новый Guard переносит ожидаемый хеш
`Watcher.Guard.exe` в `GuardRepair.exe` только при совпадении байтов нового
файла с уже доверенным хешем. Отсутствующий или неподтверждённый файл не
принимается как новая база. Исходная политика не изменяется до успешной
атомарной записи. Персональные учётки, конфиги и резервные снимки не меняются.

Постоянная задача — `\Microsoft\Watcher\GuardRepair`, SYSTEM, при загрузке
и каждые две минуты. Описание указывает принадлежность Watcher и назначение
ремонта. Создаётся только собственная папка Watcher; существующие папки и ACL
`\Microsoft` не изменяются. Ошибка доступа не вызывает расширения прав.
Для запуска установщика от SYSTEM используется временная задача
`\GuardRepairBootstrap`, удаляемая после завершения. Её оставляют при таймауте
для диагностики. Наличие новой или прежней `\WatcherGuardBootstrap` запрещает
второй одновременный bootstrap; существующие задачи не перезаписываются.

Перед изменением новой задачи или удалением `\WatcherGuard` проверяются
пользователь SYSTEM, единственное действие и его точные команда и аргументы:
прежнее (PowerShell `recover.ps1` этой установки) или, с 0.16, лаунчер
`WatcherGuard\GuardRepair.exe tick`. Совпадение одного имени задачи
не является разрешением удалить её. Ошибка чтения задачи не считается её
отсутствием. Старая задача удаляется после регистрации новой и установки её
SDDL. При ошибке прежняя каноническая задача восстанавливается из XML/SDDL,
либо удаляется только что созданная задача; старая задача остаётся.

**0.16, задача без PowerShell.** Задача регистрируется через `schtasks /XML`
(права самой задачи — в `SecurityDescriptor` XML). При обновлении с 0.15.x
установщик прежнюю задачу не меняет: если обновление откатится, прежний
установщик снова её проверит и чужую не тронет. Переводит задачу на лаунчер
уже зафиксированная версия на своём тике — когда нет журнала обновления и
`launcher` указывает на неё; затем `recover.ps1`/`protect.ps1` удаляются.
Действие задачи после этого больше не меняется: откат Guard — это смена
`launcher`, лаунчер запустит любую проверенную версию.

Guard 0.15.x после установки MSI пересчитывает хеши всех файлов своей
политики, в том числе `guard-install.ps1`/`guard-protect.ps1`/`guard-recover.ps1`,
которых в MSI 0.16 нет. Поэтому `GuardRepair install` при обновлении такой
станции кладёт на их место однострочные заглушки (комментарий без кода), а
зафиксированная новая версия убирает их имена из политики и удаляет
заглушки — вместе с переводом задачи. Свежая установка заглушек не получает.
Alias `Watcher.Guard.exe` остаётся в MSI по той же причине.

Проверено на стенде 2026-11-10 групповым обновлением Guard 0.15.1 → тестовая
0.15.34 (Windows 10, Server 2019) и 0.15.2 → 0.15.34 (Windows 11): commit,
перевод задачи на лаунчер, права задачи из XML, удаление `recover.ps1`,
`protect.ps1` и заглушек; восстановление удалённого `Watcher.SessionService.exe`
через лаунчер менее чем за 2 минуты; перезагрузка — Guard запускается по
триггеру загрузки. Свежая установка без прежней задачи и запуск
`GuardRepair install` администратором (временная SYSTEM-задача) на стенде не
проверялись.

При штатном удалении помощник после подтверждения сервера вызывает
проверенное удаление обеих принадлежащих установке задач. Ошибка или таймаут
снятия расписания сохраняет персональные учётки для повторной доставки.
Каталоги планировщика и чужие задачи не удаляются.

Launcher предпочитает новое имя, но поддерживает прежнее имя по сохранённому
SHA-256. Неверный хеш нового файла запрещает запуск; переход к старому файлу
не скрывает повреждение. Linux timer и пути состояния сохраняются.

## Границы этапа

Состояние по-прежнему находится в `C:\Program Files\WatcherGuard` и
`/var/lib/watcher/guard`. Не выполняется перенос в будущие отдельные каталоги
программы и резервных данных. Не меняются основная служба
`WatcherSessionService`, регистрация агентов, текущая проверка разрешений
обслуживания, блокировка защищённого ZIP-обновления и необходимость заранее
подписанного пакета ремонта. Автоматическое включение защиты этим этапом
не заявляется. Перед выпуском с изменениями агентов потребуется обновить
обе версии по правилам `docs/development.md`.

  ошибки регистрации/ACL/удаления, восстановление прежнего XML/SDDL, чужие
  задачи, существующий bootstrap, недоступный запрос/родитель, удаление
  расписания и хеши launcher.
- 4 сценария Linux launcher: старое/новое имя, неверный хеш и некорректный
  launcher. Проверки MSI прошли, включая отказ от несовпадающего alias.
- Собраны self-contained `GuardRepair.exe` и `GuardRepair`.
  Собраны тестовые DEB/RPM с настоящим GuardRepair и заглушками остальных
  агентов; в DEB проверен новый путь. Это проверка упаковки, не готовые
  установочные пакеты всего агента.
- Разбор четырёх PowerShell-скриптов PowerShell 7.4.13, shellcheck изменённых
  Bash-скриптов и `git diff --check` прошли. Разбор PS7 не заменяет Windows
  PowerShell 5.1 на VM.

PowerShell тестирует функции из настоящего `recover.ps1` с подставным планировщиком;
он не запускает установку, службы, bootstrap/tick или изменение ACL хоста.
Linux launcher проверяется в отдельном временном корне. Проверки MSI
используют заглушки и тестовый сертификат, не устанавливают пакет.

Остаётся пакетный прогон на выделенных VM Windows 10/11/Server 2019 и Linux:
перенос существующей задачи и обновление защищённого MSI со старым Guard,
новая установка, повторная установка, реальные ACL планировщика, загрузка
после перезагрузки и штатное удаление без самовосстановления. Локальные
подстановки не подтверждают поведение Windows Task Scheduler или MSI на VM.

## Обновление установок без Guard (WatcherUpgradeRecovery)

Станция без защиты (`WatcherGuard\enabled` нет) обновляется обычным MSI, но
прежний продукт удаляется внутри транзакции нового. На случай сбоя после
удаления работает страховка (с 0.16 — в GuardRepair, без PowerShell):

1. **prepare** — immediate custom action `PrepareLegacyRecovery` до
   `RemoveExistingProducts`: `GuardRepair legacy-msi-prepare {ProductCode}`.
   От SYSTEM (автообновление, GPO) — сразу; от администратора (ручной
   `msiexec`) — через одноразовую SYSTEM-задачу `\WatcherUpgradeRecovery-<код>Bootstrap`
   и копию GuardRepair в закрытом `Program Files\WatcherUpgradeBootstrap-<nonce>`.
   В `Program Files\WatcherUpgradeRecovery\<код>` (владелец SYSTEM, администраторам
   только чтение) сохраняются: исходный подписанный MSI прежней версии (подписант
   должен совпадать с подписантом установленного exe), конфиги, учётки,
   транскрипты, SDDL службы, настройки аудита; журнал `state.json` (phase
   `prepared`); копия GuardRepair `recover.exe` и задача
   `\WatcherUpgradeRecovery-<код>` (при загрузке и раз в минуту, от SYSTEM).
   Любая ошибка подготовки останавливает обновление **до** удаления прежней
   версии (MSI 1603); причина — в `%SystemRoot%\Logs\WatcherUpgradeRecovery\recovery.log`.
2. **restore-config** — `agent-install` новой версии возвращает снятые конфиги.
3. **recover** — задача: Windows Installer свободен, версия совпадает с
   продуктом и служба в ожидаемом состоянии → `committed`, задача удаляется.
   Иначе — откат: новый продукт удаляется, прежний MSI ставится заново
   (`MAINTENANCEKEY=""` — станция остаётся без защиты), возвращаются конфиги,
   учётки, служба, её права и настройки аудита → `rolled-back`. Ошибки отката —
   в `recovery-errors.log` журнала; задача повторяет попытку.

Проверено на стенде (Win11): ручное обновление от администратора → committed;
обновление от SYSTEM с остановленной после установки службой → откат на прежнюю
версию с сохранением регистрации; переход «без защиты → защита» обновлением → committed.
