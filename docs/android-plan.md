# Android-агент: план разработки и внедрения

Пошаговый план к решению из `android-develop.md`: **агент — владелец
устройства (свой MDM)**, телефоны подключаются после сброса к заводским.
Составлен 2026-10-21, пересмотрен 2026-10-22 (с «без владельца» на
владельца устройства). Каждый этап — отдельный PR в `main` (без
стековых PR), со своими тестами и живой проверкой на эмуляторах; этап
закрыт, когда выполнен его критерий готовности.

Порядок: сначала **инвентаризация и контроль соответствия на всём
парке** (этапы 1–10) — видимость устройств организации без вмешательства
в их работу, потом **активное управление** — политики, запреты, команды,
киоск (этапы 11–13).
Номера 7–9 сохранены с прошлой версии плана — на них ссылаются код и
`android-build.md`.

**Стенд:** тестовая VM с Android SDK и эмуляторами **Android 10 / 14 / 15**
(headless, KVM) + тестовый сервер watcher. Роль владельца на эмуляторе
назначается через `adb shell dpm set-device-owner` на чистом образе
(`-wipe-data`). Эмуляторы не повторяют вендорские прошивки и Play
Protect — это проверяется на живых телефонах (этап 9).

## Сквозные правила

- Код агента — `android/` (Kotlin, Gradle), отдельно от .NET-части;
  `minSdk 29`, `targetSdk` — актуальный.
- Имя пакета и компонента `AdminReceiver` после этапа 5 **не меняются**
  — иначе на устройствах слетит роль владельца.
- Сбой агента или сервера не должен ломать телефон: никакого перехвата
  трафика; политики применяет система и хранит сама.
- Все политики управления по умолчанию выключены; включаются с сервера
  явно, сначала на тестовой группе. Защитный список пакетов (звонилка,
  SMS, настройки, системный UI, Play Маркет, агент) заблокировать нельзя.
- Контракт с сервером — как у остальных агентов (регистрация → секрет
  агента, heartbeat, конфиг-блоб); новое только там, где Android требует.
- Ключ подписи APK — вне репозитория; в репозитории только процедура.
- Тесты: чистая логика (очередь, diff приложений, агрегация сетевого
  журнала, проверка политик против защитного списка) — JVM unit-тесты;
  поведение на устройстве — инструментальные тесты на трёх эмуляторах.
- Любой новый списковый API на сервере — с пагинацией и лимитами
  (`development.md`).

## Этап 1. Каркас проекта ✅

- `android/`: Gradle-проект, Kotlin, один модуль `app`, версия агента
  согласована с остальными агентами.
- Скрипт сборки (debug/release APK) и прогона тестов на стенде.
- Foreground service агента + уведомление; автозапуск после перезагрузки.
- **Готово:** APK собирается на стенде, ставится через adb на все три
  эмулятора, служба живёт после перезагрузки эмулятора. (PR #168)

## Этап 2. Регистрация и heartbeat

- Сервер: новый вид агента `android` (`AgentAuth.Kinds`), платформа
  `android` для heartbeat.
- Агент: регистрация по токену (ввод/QR) → секрет в Android Keystore;
  heartbeat с версией, состоянием и очередью; применение конфига с
  сервера (`configHash`).
- Привязка «устройство ↔ сотрудник» — имя хоста + поле в веб-UI.
- **Готово:** три эмулятора видны в «Хостах» тестового сервера,
  heartbeat идёт, конфиг из веб-UI доходит до устройства.

## Этап 3. Сбор событий: приложения и устройство

- Агент: `UsageEvents` (на экране / ушло с экрана), перечень приложений
  с источником установки, установки/удаления (diff + receiver),
  состояние устройства (ОС, патч, Wi-Fi, батарея, экран), объём трафика
  по приложениям (`NetworkStatsManager`).
- Локальная очередь событий (SQLite) с лимитом и автоочисткой,
  отправка пачками, «только Wi-Fi» из конфига.
- Сервер: `POST` приёма событий (валидация, лимиты на пачку), таблица
  событий с индексами по хосту/времени, retention как у остальных данных.
- **Готово:** запуск/закрытие приложения и установка APK на эмуляторе
  появляются на сервере ≤ 1 интервала отправки; переполнение очереди
  без сети не роняет агента.
- **Статус:** код агента и сервера написан (`POST /api/events`, миграции
  20–21, лента `GET /api/inventory/{name}/events`); сборка, lint и
  JVM-тесты агента, серверные тесты — зелёные. Приёмка на эмуляторах
  Android 10/14/15 пройдена 2026-10-22: запуск приложения и
  удаление/установка APK на сервере через ≤ 1 интервал heartbeat; без сети
  агент жив, после возврата сети накопленное догружается без дублей.
  Переполнение очереди до предела строк отдельно не воспроизводилось.
  Отклонение от плана: «только Wi-Fi» — локальный
  переключатель на устройстве, не из конфига сервера (серверная схема
  конфига пока только станционная). SSID в `device_state` не собирается —
  требовал бы разрешения на геолокацию; только тип сети.

## Этап 4. Веб-UI для Android

- Страница устройства: лента приложений (что и сколько), установки/
  удаления, трафик по приложениям, состояние агента.
- Флот: Android-хосты, пропуски heartbeat, «агент ослеп».
- e2e-тесты (Playwright) на новые страницы.
- **Готово:** по одному экрану видно, какие приложения запускались и что
  устанавливалось на устройстве за день.
- **Статус:** сделано. Сервер: сводка за период
  `GET /api/inventory/{name}/android-summary?from&to` (`AndroidSummary.cs`,
  не больше 7 суток; время на экране считается по парам foreground/background,
  интервал закрывают выход на экран другого приложения и выключение экрана),
  в `/api/inventory` — платформа, последнее событие и доступ к статистике.
  Агент шлёт `usageAccess` в `device_state`; «агент ослеп» (`usageAccess=false`) —
  проблема хоста (фильтр «с проблемами», карточка и панель на Обзоре). Веб-UI:
  вкладка «Устройство» вместо «Видео»/«Консоли» у Android-хостов (день: приложения
  на экране, установки/удаления с источником, трафик, состояние, перечень
  приложений с фильтром «не из магазина»), бейджи Android/«агент ослеп» и фильтр
  по устройствам в «Хостах». e2e — `tests/e2e/specs/android.spec.js`. Приёмка на
  эмуляторах Android 10/14/15 пройдена 2026-10-22: реальные запуски, удаление APK,
  трафик и перечень видны в сводке; отзыв доступа на одном эмуляторе → «агент
  ослеп» в карточке и на Обзоре.

## Этап 5. Владелец устройства

- `AdminReceiver` (`DeviceAdminReceiver`) + `device_admin.xml`;
  назначение через `dpm set-device-owner` на чистом эмуляторе.
- Агент как владелец: защита от удаления (`setUninstallBlocked`),
  выдача себе разрешений (`setPermissionGrantState`, доступ к статистике),
  отчёт на сервер «роль на месте».
- Снятие роли командой с сервера (`clearDeviceOwnerApp`) — нужно уже
  здесь, чтобы стенд и пилот можно было откатить без сброса.
- Проверка QR-подключения (6 касаний, агент по ссылке с сервера) на
  эмуляторах с Google Play: пропускает ли Play Protect. Результат — в
  `android-develop.md`.
- **Готово:** на всех трёх эмуляторах после `-wipe-data` роль
  назначается, агент не удаляется из настроек, разрешения выданы без
  участия пользователя, роль снимается командой и агент удаляется
  обычным образом.
- **Статус:** сделано. `AdminReceiver` (`DeviceAdminReceiver`) +
  `res/xml/device_admin.xml`; `DeviceOwner` (isOwner/enforce/clear) и чистая
  `DeviceOwnerPolicy` (список runtime-разрешений). При heartbeat агент-владелец
  закрепляет политики и шлёт `ownerActive`; сервер хранит роль, показывает её
  (вкладка «Устройство», «Инфо») и отдаёт команду `clearOwner`, когда админ
  нажал «Снять роль владельца» (`POST /api/fleet/{id}/android/clear-owner`,
  Management) — агент вызывает `clearDeviceOwnerApp`. Миграция БД 22. Приёмка
  на эмуляторах a10/a14/a15 (`-wipe-data` → `dpm set-device-owner`): роль
  назначается, `setUninstallBlocked` держит удаление, снятие командой возвращает
  штатное удаление. **Отклонение:** доступ к статистике использования
  (`PACKAGE_USAGE_STATS`) — appop, `setPermissionGrantState` его не выдаёт;
  владелец авто-выдаёт только runtime-разрешения (POST_NOTIFICATIONS), статистика
  остаётся отдельным шагом онбординга (Этап 7), «агент ослеп» её контролирует.
  QR-подключение не проверялось (эмуляторы без Google Play-провижининга) —
  перенесено в Этап 7/9.

## Этап 6. Сетевой журнал и журнал безопасности

- `setNetworkLoggingEnabled` → `onNetworkLogsAvailable`: `DnsEvent` и
  `ConnectEvent` с пакетом приложения; агрегация (домен × приложение ×
  интервал), чтобы не забить сервер.
- `setSecurityLoggingEnabled` → события безопасности (adb, разблокировки,
  загрузка, изменения политик) в общую очередь.
- Веб-UI: сетевой журнал устройства с фильтром по приложению и домену;
  журнал безопасности.
- **Готово:** открыть сайт в браузере эмулятора → домен с пакетом
  браузера в веб-UI ≤ 1 интервала отправки + время пачки журнала
  системы (замерить); батарея/CPU агента в разумных пределах (замер).
- **Статус:** сделано. Агент-владелец в `enforce` включает
  `setNetworkLoggingEnabled`/`setSecurityLoggingEnabled`; журналы приходят в
  колбэки `AdminReceiver` (`onNetworkLogsAvailable`/`onSecurityLogsAvailable`),
  извлекаются `OwnerLogs` и агрегируются чистой `OwnerLogsLogic` (DNS и
  соединения схлопываются по домену/адресу × приложение в пачке, события
  безопасности — по именованному тегу). Типы событий `net_dns`/`net_connect`/
  `security` (пакет — в detail). Сервер: сводка за день считает сетевой журнал
  (агрегат по домену/адресу × приложение) и журнал безопасности
  (`AndroidSummary`); веб-UI — панели «Сетевой журнал» (фильтр по приложению и
  домену) и «Журнал безопасности» на вкладке «Устройство». Unit-, серверные и
  e2e-тесты зелёные. **Живьём на эмуляторе-владельце a10:** реальные DNS
  (example.com/org/net из webview и shell) и соединение агента с сервером долетели
  в веб-UI агрегированными со счётчиками (батч форсирован `dpm force-network-logs`,
  т.к. система отдаёт пачки по своему расписанию). Журнал безопасности: включение
  и весь путь (колбэк→retrieve→очередь→сервер→UI) есть и покрыт тестами, но
  эмулятор событий безопасности не отдал (`retrieveSecurityLogs` пуст — известное
  ограничение AOSP-образов), живой захват переносится на пилот (Этап 9).

## Этап 7. Подключение устройства (onboarding)

- Скрипт для админа (`android/tools/provision.sh`): проверка «нет
  аккаунтов» → `adb install` → `dpm set-device-owner` → регистрация на
  сервере → самопроверка → отключение отладки по USB.
- Если на этапе 5 QR-подключение прошло — QR-код из веб-UI как
  альтернатива скрипту.
- Определение производителя и подсказки по вендорским настройкам фона;
  отчёт «готово» на сервер.
- Инструкция «сброс → подключение → вернуть аккаунты и данные» в
  `install.md`.
- **Готово:** чистый эмулятор подключается скриптом за ≤ 5 минут, на
  сервере — «готово» без ручных шагов, кроме мастера первого запуска.
- **Статус:** сделано. `android/tools/provision.sh`: проверка «нет аккаунтов»
  и свободной роли → `adb install` → доступ к статистике → `dpm set-device-owner`
  → авто-регистрация (запуск `MainActivity` с extras serverUrl/token/host,
  `Provisioning.parse` их проверяет, агент регистрируется сам) → самопроверка
  (владелец, статистика, процесс) → подсказка по вендору (MIUI/EMUI/…).
  Опционально `--disable-adb`. Инструкция «сброс → подключение → возврат данных»
  и путь удаления — в `install.md`. Unit-тесты `ProvisioningTest`. Приёмка на
  эмуляторе a10 (`--allow-provisioned`): роль назначается и агент
  авто-регистрируется < 5 минут. QR-подключение — на пилот (Этап 9), эмуляторы
  его не воспроизводят. На реальном устройстве скрипт запускают на свежесброшенном
  до мастера; на эмуляторе — с `--allow-provisioned`.

## Этап 8. Обновление агента

- Канал обновлений через существующий механизм сервера (подписанные
  пакеты), APK вместо MSI/архива.
- Тихая установка владельцем через `PackageInstaller`, без
  подтверждения пользователя.
- **Готово:** новая версия, загруженная в веб-UI, ставится на три
  эмулятора без участия пользователя; роль владельца и выданные
  разрешения после обновления на месте.
- **Статус:** сделано. Канал — существующий (подписанные пакеты H2): платформа
  `android`, пакет `.apk`. Агент при регистрации пинит открытый ключ обновлений
  (сервер отдаёт `updatePublicKey` в ответе enroll), в heartbeat парсит offer,
  качает пакет под своей учёткой, сверяет SHA-256 и подпись (`UpdateCheck`,
  ECDSA P-256 как у станций) и ставит тихо через `PackageInstaller` —
  владелец без подтверждения пользователя. Итог — `UpdateInstallReceiver`
  (статус в heartbeat `updateStatus`, провал тормозит повтор на час). Обновление
  на месте: тот же пакет и подпись APK, поэтому роль владельца, разрешения и
  данные сохраняются. В веб-UI (Настройки → Обновления) добавлена платформа
  «Android APK»; `sign-update.sh` теперь принимает `--platform android`. Живая
  приёмка на a10: 0.14.4 → 0.14.5 по назначению версии группе, роль владельца и
  доступ к статистике после обновления на месте. Unit-тесты `UpdateCheckTest`,
  серверный тест передачи ключа.

## Этап 11. Политики: блокировки и запреты

- Конфиг-блоб: список блокируемых приложений (`setPackagesSuspended`),
  скрытых (`setApplicationHidden`), запреты (user restrictions: установка
  из неизвестных источников, свой VPN, Private DNS, USB-передача файлов,
  отладка, сброс), мобильный интернет приложениям
  (`setMeteredDataDisabledPackages`).
- Защитный список — проверка на сервере (не сохранить политику) и в
  агенте (не применить).
- Агент подтверждает применённую версию политики; рассогласование и
  каждое срабатывание блокировки — события на сервер.
- Веб-UI: политики на устройство и на группу, тестовая группа;
  отдельное право «управление телефонами»; журнал действий админов.
- **Готово:** приложение из списка на трёх эмуляторах не запускается и
  остаётся заблокированным после ребута; запрет установки APK работает;
  снятие политики возвращает всё как было; попытка заблокировать пакет
  из защитного списка отклоняется сервером и агентом.
- **Статус: ядро сделано (PR A), веб-UI — следующим PR.** Политика живёт в
  конфиг-блобе (ключ `androidPolicy`): `suspendedPackages`, `hiddenPackages`,
  `restrictions` (из разрешённого набора user-restrictions), `meteredDataDisabledPackages`
  — доставляется агенту тем же каналом, что настройки станций (merge группа+хост,
  versioning). Валидация и защитный список — на сервере (`AndroidPolicy.cs`,
  отказ 400) и в агенте (`AndroidPolicyLogic`, фильтр + runtime-защита домашнего
  экрана/звонилки/SMS). Агент применяет через `DevicePolicyManager`
  (setPackagesSuspended / setApplicationHidden / add/clearUserRestriction /
  setMeteredDataDisabledPackages), дельтой при смене конфига и **форсированно на
  старте процесса** — т.к. на части прошивок suspension не переживает ребут
  (подтверждено на эмуляторе: без переприменения блокировка слетала). Отчёт
  применения и отказы — событие `policy`. Живая приёмка на эмуляторе a10
  (владелец): блокировка применяется, **держится после ребута**, снятие
  откатывает, защищённый пакет отклоняется сервером (400) и агентом (unit).
  **PR B (веб-UI, сделано):** редактор политик на вкладке «Устройство» и в
  конфиге группы (блокировать/скрыть приложения, запреты устройства, без
  мобильного интернета); отдельное право «управление телефонами»
  (`can_manage_phones`, политика `PhoneManagement`, admin всегда) с
  переключателем в списке пользователей; редактирование — отдельными
  эндпоинтами `…/android-policy`, не затрагивая станционный конфиг. Изменения
  политики пишутся в журнал действий (audit `host/group.android-policy.set`).
  События на каждое срабатывание блокировки не делаем: платформа не даёт
  надёжного колбэка на попытку запуска заблокированного приложения
  (docs/development.md, «не наращивать эвристики»). Тестовая группа — это
  обычная группа с политикой, применённая к пилотным устройствам.

## Этап 12. Удалённая блокировка устройства

Решение пользователя (2026-10-26): блокировка экрана (`lockNow`) и сброс
(`wipeData`) не нужны — смысла нет. Вместо них — **полная удалённая
блокировка устройства** на случай утери или несанкционированного
вмешательства: по команде админа телефон запирается на экран-заглушку
(lock-task / kiosk), им нельзя пользоваться, снимается только командой.
Снятие роли владельца — уже с Этапа 5.

- Желаемое состояние блокировки — в heartbeat (как clearOwner): админ
  переключает командой `POST …/android/lock` (право «управление
  телефонами»), агент-владелец приводит устройство к нему.
- Блокировка: агент вносит себя в lock-task allowlist
  (`setLockTaskPackages`) и поднимает полноэкранную `LockActivity`
  (через full-screen-intent, надёжно из фона), которая входит в lock-task
  (`startLockTask`) — home/recents отключены. Снятие: активность выходит
  из lock-task и закрывается. Переживает ребут (служба поднимается
  BootReceiver и переблокирует по желаемому состоянию).
- Команда — в журнал действий админов (`host.android-lock`).
- **Готово:** команда из веб-UI блокирует эмулятор (lock-task LOCKED,
  на экране заглушка), блокировка держится после ребута, команда снятия
  разблокирует; статус виден в веб-UI.
- **Статус: сделано.** Живая приёмка на эмуляторе a10: lock → экран-заглушка
  в lock-task (LOCKED), после ребута заблокирован снова, unlock → снято
  (lock-task NONE). Ограничение Android 14+: full-screen-intent требует
  разрешения USE_FULL_SCREEN_INTENT (на 13 и ниже работает без вопросов) —
  проверить на пилоте, при необходимости выдать владельцем.

## Этап 13. Киоск-планшеты

- Режим киоска: `setLockTaskPackages` + `startLockTask`, разрешённые
  приложения из политики, выход из киоска только командой с сервера.
- **Готово:** планшет-эмулятор в киоске не выходит в настройки и другие
  приложения; команда снимает киоск.
- **Статус: сделано.** Разрешённые приложения — `kioskPackages` в androidPolicy
  (доставка/право те же, что у политик). Агент-владелец: `setLockTaskPackages`
  (разрешённые + сам агент), домашний экран = лаунчер киоска `KioskActivity`
  (`addPersistentPreferredActivity` HOME), которая входит в `startLockTask` и
  показывает разрешённые приложения кнопками; выход из киоска — только когда
  список пуст (команда с сервера). Переживает ребут (переприменение на старте).
  Живая приёмка на эмуляторе a10: киоск включается (lock-task LOCKED, лаунчер —
  домашний), Настройки и прочие приложения не открываются, разрешённое
  запускается; держится после ребута; пустой список снимает киоск (с задержкой
  до интервала heartbeat). Редактор — поле «Киоск: разрешённые приложения» в
  политике устройства/группы.

## Этап 12+. Офлайн-разблокировка по учётке администратора

Запрос пользователя (2026-10-26): управлять телефоном, когда сервер недоступен —
в частности снять блокировку/киоск по **логину-паролю администратора watcher**,
без сети. Это break-glass: временно, до связи с сервером.

- Сервер шлёт в каждом heartbeat Android-агента `adminCredentials` —
  логины и хэши паролей локальных админов (`role='admin'`,
  `auth_source='local'`). Агент хранит их зашифровано (`SecretStore`),
  обновляет при каждом heartbeat — пароль сменили, хэш доедет.
- Проверка пароля — локально, без сети и без сторонних либ: хэш
  ASP.NET Identity (`PasswordHasher`, PBKDF2 v3) проверяется через JCA
  (`PBKDF2WithHmacSHA1/256/512`), `AdminAuth.verify`.
- На экране блокировки и в киоске — видимая кнопка «Вход администратора»
  открывает окно логина. Верный админ → `adminOverride=true`, экран
  снимается (`LockState.shouldLock=false` / `KioskState.allowed=∅`), выход
  из lock-task. (Кнопку видно, но вход только по логину/паролю с локальной
  PBKDF2-проверкой — видимость защиту не ослабляет.)
- Оверрайд **одноразовый**: следующий heartbeat несёт `adminUnlocked=true`,
  сервер снимает запрос блокировки (`androidLockRequested=0`, `lockDevice=false`),
  после чего агент сбрасывает оверрайд — будущая команда блокировки снова
  срабатывает. Ребут восстанавливает мандат политики (киоск/блокировку сервер
  переназначает по желаемому состоянию).
- **Статус: сделано.** Unit-тесты `AdminAuth` против реального хэша ASP.NET
  (SHA1/256/512), серверный интеграционный тест (heartbeat отдаёт локальных
  админов, `adminUnlocked` снимает блокировку), живая приёмка на эмуляторе a10:
  блокировка → жест → неверный пароль не пускает → верный снимает → сервер
  снял запрос блокировки.

## Этап 12+. Запись экрана по согласию

Запрос пользователя (2026-10-26): запись экрана двух типов. Запись — только
по согласию: владелец устройства НЕ может писать экран молча, системный запрос
MediaProjection и есть согласие. Два PR.

- Политика `androidPolicy.screenRecord {mode: off|device|perApp, apps:[…]}`.
  Доставка/право — те же, что у остальных политик. Видео идёт на тот же
  `/api/upload`, что станции (привязка к хосту из учётки Android-агента);
  вкладка «Видео» у телефона появляется, когда есть записи. Без звука.
- Захват: `ScreenCaptureService` (foreground, тип mediaProjection) из одного
  согласия держит `MediaProjection` весь сеанс, пишет сегменты MP4 фикс. длины
  (ротация — меняется только `MediaRecorder` на том же `VirtualDisplay`, чтобы не
  переспрашивать согласие на 14+), грузит `VideoUploader`. Кап по высоте 1280,
  лимит несоправленного спула.
- **Режим device (PR1):** согласие при разблокировке (`ACTION_USER_PRESENT`) не
  чаще раза в сутки; «да» → запись весь сеанс, «нет» → (PR2: блокировка).
- **Режим perApp (PR2):** приложения из списка держим `setPackagesSuspended`
  Реактивно: наблюдатель переднего плана (UsageEvents) ловит выход целевого
  приложения на экран → согласие; «да» → запись, пока им пользуются, по выходу
  запись останавливается; «нет» → уходим на домашний экран. Чистый suspend-гейт
  владельцу недоступен (кастомный SuspendDialogInfo требует системного SUSPEND_APPS),
  Accessibility по решению пользователя не берём.
- **PR1 — сделано.** Серверная часть (`/api/upload` принимает android,
  валидация `screenRecord`, вкладка «Видео»), агент (`ScreenCaptureService`,
  `ScreenConsentActivity`, `VideoUploader`, `ScreenRecordController`, парс
  политики), веб-редактор (переключатель режима + пикер приложений). Проверено:
  серверные+agent unit тесты, e2e, живая приёмка на эмуляторе a10 (политика
  device → согласие → сегмент записан и долетел на сервер, segments 0→1).
- **PR2 — сделано.** Часть A (PR #192): режим device, отказ от согласия → блокировка
  телефона (экран-заглушка Этапа 12), снятие админом/сервером/выключением записи.
  Часть B (perApp): реактивный наблюдатель переднего плана (`ForegroundWatcher`),
  согласие при запуске целевого приложения, запись во время использования, отказ →
  домой. Живая приёмка на эмуляторе a10.
