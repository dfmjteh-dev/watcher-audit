# Конфигурация

Все три компонента читают JSON-конфиги. Все параметры можно менять без перекомпиляции.

## Сервер: `/opt/watcher/appsettings.json`

```json
{
  "Server": {
    "DataDir": "/opt/watcher/data",
    "DbPath": "/opt/watcher/data/watcher.db",
    "MaxUploadSizeMb": 512,
    "AdminUser": "admin",
    "AdminPassword": "<сгенерированный>",
    "RetentionDays": 30,
    "RetentionMaxBytes": 0,
    "MinFreeDiskPercent": 5,
    "RetentionScanIntervalMinutes": 60,
    "AuditRetentionDays": 365,
    "Transcode": { "Enabled": true, "Crf": 41, "Preset": 7, "Workers": 0 }
  },
  "Kestrel": {
    "Endpoints": { "Http": { "Url": "http://0.0.0.0:5050" } }
  }
}
```

| Ключ | Назначение |
|---|---|
| `DataDir` | Папка для БД и блобов. Должна быть писаемой для `www-data`. |
| `DbPath` | Файл SQLite. Обычно `<DataDir>/watcher.db`. |
| `MaxUploadSizeMb` | Лимит одного multipart-запроса. 512 МБ хватит на любые разумные сегменты. |
| `AgentKitDir` | Каталог комплекта установки агентов (install-server.sh). Пусто — страницы «Установка агентов» нет. В Docker Compose — `/kit` (смонтирован из `WATCHER_KIT_DIR`, по умолчанию `/opt/watcher-kit`, только чтение); systemd — `/opt/watcher-kit`. |
| `AllowAnonymousAgents` | `false` по умолчанию. `true` — агентские эндпоинты принимают запросы без учётки агента, хост — из тела запроса. **Только разработка и тесты**, в продакшене не включать. |
| `AdminUser` | Логин первого веб-пользователя. Используется только один раз — при старте с пустой таблицей `users` из него создаётся запись в БД (пароль хэшируется), дальше на вход эти два поля не влияют и их можно убрать из конфига. |
| `AdminPassword` | Пароль первого веб-пользователя, см. `AdminUser`. Если оба поля пустые и в БД ещё нет ни одного пользователя — веб-интерфейс недоступен, пока пользователь не будет создан (см. `docs/architecture.md`, раздел «Авторизация»). |
| `CookieSecure` | `true` по умолчанию — cookie `watcher_auth` всегда с флагом `Secure`, независимо от того, что Kestrel видит как схему запроса. `false` — только для dev/тестов без TLS впереди (иначе браузер/HttpClient не отошлёт cookie обратно по http). |
| `Siem:*` | Экспорт журнала доступа в SIEM по syslog (H4) — см. «Экспорт в SIEM» ниже. |
| `Ldap:*` | Вход через Active Directory / LDAP (H1) — см. «Вход через AD / LDAP» ниже. |
| `RetentionDays` | Удалять записи (видео и консоль) старше N дней. Старой считается запись, у которой и время записи, и время выгрузки старше N дней, поэтому только что выгруженная запись с неверной датой станции (например, 2000 год после сброса BIOS) живёт ещё N дней, а не удаляется при первом же проходе (R7). 0 = не чистить по возрасту. |
| `UpdatePublicKey` | Открытый ключ обновлений агентов (H2) — строка base64 из `tools/update-signing/new-update-key.sh` (`update-key.pub.txt`). Пусто (по умолчанию) — пакеты обновлений не принимаются. Тот же ключ ставится на станции. См. `docs/operations.md`, «Обновление агентов с сервера». |
| `MaxConcurrentAgentUpdates` | Сколько агентов одновременно получают пакет обновления (0.15.0, по умолчанию `10`). Пакет ~100 МБ: назначили версию сразу многим группам — остальные хосты ждут очереди, а не качают десятки гигабайт разом. Слот освобождается, когда хост пришёл с новой версией, или через 30 мин. `0` — без ограничения (как до 0.15.0). |
| `RetentionDays` у группы, legal hold | Не ключи файла: задаются в веб-UI (Настройки → Хранилище) и хранятся в БД — `docs/operations.md`, «Сроки хранения по группам и legal hold». |
| `RetentionMaxBytes` | Общий лимит на видео и консоль вместе: когда суммарный размер больше, удаляются самые старые записи из обеих таблиц (R8). 0 = без лимита. |
| `MinFreeDiskPercent` | Если на томе с `DataDir` свободно меньше этого процента, retention удаляет самые старые записи, независимо от возраста, пока свободное место не вернётся к порогу. На `#/` в этот момент показывается предупреждение. Место считается по всему тому: если его заняли не записи watcher (логи, чужие файлы), удаляться всё равно будут записи. 5 по умолчанию, 0 = выключено (при `RetentionMaxBytes = 0` диск тогда может заполниться до отказа). |
| `RetentionScanIntervalMinutes` | Как часто бегает чистка. Минимум 5 минут. |
| `MetricsToken` | Bearer-токен для `GET /metrics` (формат Prometheus, H4). Пусто (по умолчанию) — эндпоинт выключен, отвечает 404. Отдельный от учёток агентов: Prometheus/Zabbix не должны уметь выгружать записи от имени агента. См. `docs/operations.md`, «Мониторинг». |
| `Alerts:*` | Встроенные алерты (H4) — см. таблицу «Алерты» ниже. |
| `ExportMaxItems`, `ExportMaxMb` | Пределы одной выгрузки записей (H7): не больше 5000 записей и 20480 МБ. Больше — отказ с просьбой сузить период. zip собирается на лету, без временных файлов, но держит запрос открытым всё время скачивания. См. `docs/operations.md`, «Выгрузка записей». |
| `AuditRetentionDays` | Сколько дней хранить журнал доступа (`#/settings/audit`, Этап C3). Отдельно от `RetentionDays` и по умолчанию дольше (365) — «кто смотрел запись» спрашивают и после удаления самой записи. 0 = хранить бессрочно. `RetentionMaxBytes` на журнал не действует. |
| `Transcode:*` | Пережатие записей в AV1 на сервере — см. «Пережатие записей» ниже. |
| `ServerUpdate:Dir` | Каталог заявок обновления из веб-интерфейса (`docs/operations.md`, «Обновление сервера из веб-интерфейса»). Пусто — выключено. Ставит install-server.sh: Docker — `/updates` (`/var/lib/watcher-server-update` хоста), systemd — `/var/lib/watcher-server-update`. |
| `ServerUpdate:GitHubRepo` | `owner/repo` публичного репозитория с релизами, по умолчанию `dfmjteh-dev/watcher-audit`. |
| `ServerUpdate:MaxUploadMb` | Предел архива при ручной загрузке, 4096 МБ. Отдельно от `MaxUploadSizeMb` (записи агентов). |
| `Kestrel.Endpoints.Http.Url` | На какой адрес и порт слушать. **Побеждает `ASPNETCORE_URLS`**, если задан (подтверждено живьём — Kestrel логирует "Overriding address(es) ... Binding to endpoints defined via IConfiguration instead" и реально слушает адрес отсюда) — install-server.sh (B3) поэтому пишет адрес именно сюда, не только в переменную окружения systemd-юнита. По умолчанию в Docker — все интерфейсы контейнера (`0.0.0.0:5050`, не публикуется на хост, см. `docker-compose.yml`); в systemd-fallback — `127.0.0.1:5050` (`EXPOSE_HTTP=true` при установке — `0.0.0.0`, без TLS). |

### Алерты (`Server:Alerts`, H4)

Выключены, пока не задан ни один канал (`WebhookUrl` или SMTP). Переменные
окружения — `Server__Alerts__WebhookUrl`, `Server__Alerts__Smtp__Host` и т.д.
Что приходит и как выглядит — `docs/operations.md`, «Встроенные алерты».

| Параметр | По умолчанию | Описание |
|---|---|---|
| `Title` | `Watcher` | Имя сервера в тексте уведомления — различать несколько установок. |
| `CheckIntervalSeconds` | 60 | Как часто проверять (не меньше 15). |
| `HostSilentHours` | 72 | Хост не присылал heartbeat дольше N часов. Станции выключают на ночь и выходные — поэтому не час. 0 — не следить. |
| `DiskLowPercent` | 10 | Свободно на томе с `DataDir` меньше N% — предупреждение до того, как retention начнёт удалять записи раньше срока (`MinFreeDiskPercent`). 0 — выкл. |
| `RepeatHours` | 24 | Напоминание об алертах, которые всё ещё активны. 0 — только при срабатывании и решении. |
| `MaxListedHosts` | 20 | Сколько хостов одного вида перечислять в сообщении, остальные — «и ещё N». |
| `WebhookUrl` | — | POST JSON с полем `text` (Mattermost, Slack, Rocket.Chat — входящий webhook как есть; Telegram — `https://api.telegram.org/bot<токен>/sendMessage?chat_id=<id>`). URL с токеном — секрет, только через `.env`/env. |
| `Smtp:Host`, `Smtp:Port` | —, 587 | SMTP-сервер. |
| `Smtp:UseTls` | `true` | STARTTLS. Неявный TLS (порт 465) не поддерживается. |
| `Smtp:User`, `Smtp:Password` | — | Пусто — без авторизации (релей во внутренней сети). Пароль — только через env. |
| `Smtp:From`, `Smtp:To` | — | Отправитель; получатели через запятую. |

После изменений: `sudo systemctl restart watcher-server`.

### Пережатие записей (`Server:Transcode`)

Агент пишет видео быстрым x264 `ultrafast`: для станции это почти бесплатно (на
RDS-сервере с сотней сессий важно), но файлы в 4–6 раз больше, чем нужно для
экрана. Сервер пережимает их в AV1 (SVT-AV1) — самые свежие необработанные
сначала, по `Workers` файлов одновременно, ffmpeg с наименьшим приоритетом
(nice 19: веб и приём записей берут CPU первыми). Пока очередь есть — без
пауз (прогонами по `MaxRunMinutes`, итог каждого — в журнал и на «Обзор»);
очередь пуста — проверка раз в `IntervalMinutes`. Результат — тот же mp4 с
индексом в начале: плеер, выгрузка и API не меняются. Исходный файл удаляется
сразу после подмены; если запись в этот момент смотрят, плеер незаметно
переоткрывает новую версию с той же секунды (`?v=` в URL видео).

ffmpeg — закреплённая статическая сборка с SVT-AV1 4.x
(`tools/fetch-ffmpeg-linux.sh`, проверка по SHA-256): в Docker-образе
`/usr/local/bin/ffmpeg`, в systemd-варианте install-server.sh кладёт его в
`/opt/watcher/ffmpeg` (`FfmpegPath`). SVT-AV1 1.4.1 из Debian 12 на тех же
записях втрое медленнее. Нет ffmpeg с `libsvtav1` — сервер работает, в журнале
`transcode: disabled — …`, записи остаются как есть.

Значения по умолчанию — по замеру на 120 сегментах прода (2026-10-19, средний
~1,2 МБ, 720p, 2 кадра/с):

| SVT-AV1, пресет/crf | Файлов/мин на 4 ядрах | Сжатие к x264 агента | SSIM мин / ср |
|---|---|---|---|
| 1.4.1, 8/35, 1 файл × 4 потока (0.14.0) | 10 | ×3,5 | 0,989 / 0,994 |
| 4.2, 7/39, 4 файла × 1 поток | 37 | ×4,4 | 0,987 / 0,992 |
| 4.2, **7/41**, 4 × 1 | 37 | ×4,8 | 0,986 / 0,991 |
| 4.2, 7/43, 4 × 1 | 38 | ×5,3 | 0,985 / 0,990 |
| 4.2, 8/37, 4 × 1 | 46 | ×3,6 | 0,983 / 0,991 |
| 4.2, 9/37, 4 × 1 | 109 | ×3,5 | 0,981 / 0,987 |

Один поток на файл и файлы параллельно быстрее, чем несколько потоков на один
короткий файл. На 7/41 мелкий текст (таблицы 1С) читается так же, как в
исходнике. Не успевает за притоком — `Preset` 8 или 9 (быстрее, файлы
чуть крупнее); места мало, а CPU хватает — `Crf` выше.

| Ключ | По умолчанию | Назначение |
|---|---|---|
| `Enabled` | `true` | `false` — не пережимать. Уже пережатые записи остаются пережатыми. |
| `IntervalMinutes` | 60 | Очередь пуста — как часто проверять. Минимум 5. |
| `MaxRunMinutes` | 50 | Длина одного прогона (итог — в журнал и на «Обзор»); очередь осталась — следующий сразу. |
| `MinAgeMinutes` | 30 | Не трогать запись раньше, чем через N минут после приёма: свежую чаще смотрят сразу. |
| `Crf` | 41 | Качество SVT-AV1: больше — меньше файл. |
| `Preset` | 7 | Скорость SVT-AV1 (0–13): больше — быстрее и крупнее файл. |
| `Threads` | 1 | Потоков SVT-AV1 на файл (`lp`). |
| `Workers` | 0 | Верхняя граница параллельных задач; 0 — статический потолок по CPU, `Threads` и общей памяти. Перед выдачей каждой задачи дополнительно проверяется текущий запас RAM хоста и cgroup; явное значение не отключает защиту. |
| `MemoryPerWorkerMb` | 600 | Оценка для статического потолка. Динамический контроль начинает с максимума этого значения и 1536 МиБ, затем повышает оценку по пиковому RSS дочерних процессов с запасом 25%. |
| `MinSavingPercent` | 10 | Пережатый меньше исходного меньше чем на N % — остаётся исходный. |
| `FfmpegPath` | `ffmpeg` | Путь, если не в `PATH`. |
| `QuarantineDays` | 7 | Срок карантина до разрешения отдельной очистки (1–30 суток). |
| `QuarantineMaxBytes` | 10737418240 | Квота карантина; при заполнении исходник остаётся активным. |

**Сбои.** Длительность до и после сверяется по заголовку mp4 (без ffprobe);
не сошлась — независимая проверка исходника и до трёх повторов с задержками
5/30/120 минут. История сохраняется после перезапуска. Сервер упал посреди
пережатия: недописанные `.part` удаляются при старте службы; если строка уже
указывала на пережатый файл, а исходник остался — он удаляется при старте и
после каждого прогона; «ничейный» пережатый файл (упал между переносом файла
и записью в БД) перезаписывается при повторной попытке, а при удалении записи
(retention, админ, удаление хоста) удаляются оба варианта файла.

Записи под действующим legal hold не пережимаются. Хеш: у пережатой записи в
БД (`sha256`, его проверяет выгрузка) — хеш нового файла, хеш от агента
остаётся в `source_sha256` и попадает в `manifest.json` выгрузки
(`sourceSha256`, `hashSource: "transcode"`). После исчерпания попыток пригодный
исходник получает `kept`; непроверенный остаётся `failed` с причиной. Повреждённый
контейнер сначала восстанавливается remux; непригодный файл удаляется из активного
реестра только после проверенного карантина и аудита. Автоматической очистки
карантина нет — отдельный admin API с dry-run, сроком и повторной проверкой hold.
В Docker — `Server__Transcode__Enabled=false` и т.п. в `.env`.

### В Docker Compose — через `.env`, не `appsettings.json`

Те же ключи секции `Server` задаются переменными окружения в `.env`
(`cp .env.example .env`), по конвенции ASP.NET Core `Server__<Ключ>`
(двойное подчёркивание = разделитель секции):

```
Server__AdminUser=admin
Server__AdminPassword=<свой пароль, только для самого первого старта>
WATCHER_DOMAIN=watcher.internal   # для Caddyfile, не для Watcher.Server напрямую
```

Агенты регистрируются токеном регистрации из веб-UI (Настройки → Агенты) и
получают собственную учётку. Для разработки, где агенты ходят без учётки, —
`Server__AllowAnonymousAgents=true`.

`DataDir`/`DbPath` в Docker-варианте не трогаются — захардкожены на `/data` в
`docker-compose.yml` (named volume `watcher-data`), чтобы апдейт образа не задевал
данные. После изменений `.env`: `sudo docker compose up -d` (пересоздаст контейнер
с новым окружением, volume не трогает).

### Вход через AD / LDAP (`Server:Ldap`, H1)

С 0.12 то же настраивается в веб-UI: **Настройки → Вход через AD** (только
admin) — с кнопкой «Проверить подключение» (соединение, TLS, служебная учётка,
база поиска, а с логином и паролем — группы и роль этого пользователя).
Сохранённое там хранится в БД (`server_settings`, ключ `ldap`), **главнее**
`Server:Ldap` из `.env`/appsettings и применяется без перезапуска; «Сбросить к
файлу настроек» возвращает к `.env`. Пароль служебной учётки веб-UI не
показывает (только «задан»), пустое поле при сохранении — прежний пароль.
Корневой CA контроллера там вставляется PEM-текстом (`CaCertPem`), а не путём.

Выключено, пока не задан `Url`. Как настроить AD по шагам и разбирать отказы —
`docs/operations.md`, «Вход через Active Directory / LDAP». Ошибка в настройках
не мешает серверу стартовать: LDAP выключается (в логе — почему), локальный
admin входит как обычно.

| Параметр | По умолчанию | Описание |
|---|---|---|
| `Url` | — | `ldaps://dc1.corp.local:636` или `ldap://dc1.corp.local:389` + `StartTls=true`. Имя — как в сертификате контроллера: по нему проверяется TLS. `ldap://` без StartTLS не принимается (пароли открытым текстом). |
| `StartTls` | `false` | Для `ldap://`. |
| `AllowPlaintext` | `false` | 0.12.1: разрешить `ldap://` без StartTLS. Пароли пользователей и служебной учётки идут к контроллеру **открытым текстом** — только если на контроллерах нет сертификата для LDAPS. Контроллер с политикой «LDAP server signing requirements = Require signing» такой вход всё равно отклонит. В веб-UI — галка «Без шифрования», в состоянии — пометка «без шифрования». |
| `CaCertPath` | — | Корневой CA контроллера (PEM), если он не в системном хранилище. Имя и цепочка проверяются всё равно. |
| `BindDn`, `BindPassword` | — | Служебная учётка для поиска пользователей: обычный пользователь домена, без прав. AD принимает UPN (`svc-watcher@corp.local`). Пароль — только через env / `.env`. |
| `SearchBase` | — | Где искать: `DC=corp,DC=local` или конкретный OU. |
| `UserFilter` | AD: `sAMAccountName` или UPN | `{0}` — введённый логин (экранируется). OpenLDAP: `(uid={0})`. Ввод `CORP\user` тоже работает. |
| `LoginAttribute` | `sAMAccountName` | Чьё значение становится именем в Watcher — одно и то же при любом способе ввода. |
| `GroupRoles` | — | Список «группа → роль»: `GroupRoles__0__Group`, `GroupRoles__0__Role` и т.д. Группа — DN или просто имя (CN). Несколько групп — старшая роль (admin > operator > viewer). Нет ни одной — вход запрещён. |
| `ExportGroups` | — | Группы (DN или имя), дающие право выгрузки записей (H7): `ExportGroups__0=Watcher-Exporters`. Пусто — ни у кого из каталога этого права нет. Проверяется при входе и перепроверке, сессию не закрывает. |
| `NestedGroups` | `true` | Учитывать вложенные группы (AD). Не AD — `false`. |
| `RecheckMinutes` | 15 | Как часто перепроверять вошедшего пользователя в каталоге: отключён, удалён, выведен из групп — сессия закрывается сразу, роль сменилась — нужно войти заново. |
| `TimeoutSeconds` | 5 | Таймаут соединения и поиска. |

### Экспорт в SIEM (`Server:Siem`, H4)

Журнал доступа (`#/settings/audit`: входы, просмотры видео и консоли, изменения
пользователей, групп, конфигов, регистрация агентов) уходит в SIEM заказчика
по syslog (RFC 5424). Выключено, пока не задан `Host`. Переменные окружения —
`Server__Siem__Host` и т.д. Как это работает и что проверить —
`docs/operations.md`, «Экспорт журнала доступа в SIEM».

| Параметр | По умолчанию | Описание |
|---|---|---|
| `Host`, `Port` | —, 514 | Приёмник syslog. Для `tls` обычно 6514. |
| `Protocol` | `tcp` | `udp`, `tcp` или `tls`. В журнале логины и IP — по сети лучше `tls`. UDP теряет записи без следа и режет сообщение до 2048 байт. |
| `Format` | `cef` | `cef` (ArcSight, QRadar, Splunk, MaxPatrol и др.) или `json`. |
| `Framing` | `octet` | Только `tcp`/`tls`: `octet` — RFC 6587 «длина пробел сообщение» (rsyslog, syslog-ng `syslog()`); `lf` — через перевод строки (syslog-ng `network()`, простые приёмники). |
| `Facility` | 10 | 10 — authpriv; 13 — log audit; 16–23 — local0–local7. |
| `Hostname` | имя машины | HOSTNAME в syslog. В Docker имя машины — случайный id контейнера, задайте явно. |
| `AppName` | `watcher` | APP-NAME в syslog. |
| `CaCertPath` | — | Для `tls`: корневой CA приёмника, если он не в системном хранилище. Имя сервера и цепочка проверяются всё равно. |
| `SendHistory` | `false` | `false` — при первом запуске начать с конца журнала; `true` — отправить весь накопленный журнал. |
| `PollSeconds`, `BatchSize` | 5, 200 | Как часто проверять журнал и сколько записей за раз. |

## Станция, capture: `C:\Watcher\Watcher.Capture.json`

```json
{
  "Capture": {
    "QueueDir": "C:\\ProgramData\\Watcher\\queue",
    "LogDir":   "C:\\ProgramData\\Watcher\\logs",
    "FfmpegPath": "C:\\Watcher\\ffmpeg.exe",
    "CaptureIntervalMs": 500,
    "DownscaleWidth":  1920,
    "DownscaleHeight": 1080,
    "MotionThresholdPercent": 0.5,
    "MotionThresholdPixelDelta": 25,
    "IdleSecondsToCloseSegment": 10,
    "MaxSegmentSeconds": 300,
    "PreRollSeconds": 10,
    "OutputFps": 2,
    "Crf": 30,
    "Preset": "ultrafast",
    "FfmpegWriteTimeoutMs": 5000,
    "LogRetainedDays": 14,
    "LogFileSizeLimitMb": 10,
    "ConfigCachePath": "C:\\ProgramData\\Watcher\\config\\capture-config.json",
    "ConfigCheckIntervalSeconds": 30
  }
}
```

| Ключ | Назначение |
|---|---|
| `QueueDir` | Куда capture складывает mp4 + json. Должна быть писаемой пользовательской сессией. |
| `LogDir` | Логи capture (Serilog rolling-file). Файл `watcher-YYYYMMDD.log`. |
| `FfmpegPath` | Путь к ffmpeg.exe. Установщик ставит в `C:\Watcher\ffmpeg.exe`. |
| `CaptureIntervalMs` | Интервал захвата кадров. 500 = 2 кадра/сек. Меньше = плавнее видео, больше CPU. |
| `DownscaleWidth/Height` | С 0.13 — предел размера **одного монитора** в записи: весь рабочий стол снимается с сохранением пропорций, каждый монитор уменьшается не больше этого размера, экран меньше — пишется как есть (не растягивается). Два монитора 1920×1080 при 1920×1080 — видео 3840×1080; раскладка мониторов уходит в sidecar (`monitors`), в плеере можно показать один. Кадр целиком — не больше 7680×4320. До 0.13 весь стол растягивался в этот размер без пропорций. Выше — больше размер файла. |
| `MotionThresholdPercent` | Сколько % пикселей должно измениться, чтобы считать motion. 0.5 = чувствительно, 5 = только большие изменения. |
| `MotionThresholdPixelDelta` | На сколько яркость пикселя должна отличаться чтобы считать его «изменившимся». 25 — оптимально, ниже = ловит шум, выше = пропускает мелочи. |
| `IdleSecondsToCloseSegment` | После N сек без motion закрываем текущий сегмент. |
| `MaxSegmentSeconds` | Максимальная длина одного сегмента. Долгая активность нарезается. По умолчанию 5 мин. |
| `PreRollSeconds` | Сколько кадров до motion включить в начало сегмента (из ring buffer). 10 сек = первое действие не отрезается. |
| `OutputFps` | Целевой fps в mp4. Не больше чем `1000/CaptureIntervalMs`. |
| `Crf` | Качество H.264. 18 = visually lossless, 23 = норм, 30 = сжато, 35 = плохо. Выше CRF = меньше файл. |
| `Preset` | Скорость кодирования. `ultrafast` для слабого CPU, `medium` для лучшего сжатия. |
| `FfmpegWriteTimeoutMs` | Таймаут записи кадра в stdin ffmpeg. Если ffmpeg подвис (завис процесс/диск), запись не блокирует цикл захвата вечно — по истечении таймаута процесс убивается, сегмент прерывается. |
| `LogRetainedDays` | Сколько последних дневных лог-файлов хранить, остальные удаляются автоматически. |
| `LogFileSizeLimitMb` | Лимит размера одного лог-файла. При превышении в тот же день создаётся новый файл (`watcher-YYYYMMDD_001.log` и т.д.). |
| `ConfigCachePath` | Файл с конфигом, пришедшим из веб-UI (пишет `Watcher.Uploader` после heartbeat, читает `Watcher.Capture` раз в `ConfigCheckIntervalSeconds`, см. `docs/architecture.md`, «Централизованная конфигурация»). Должен совпадать с `Watcher.Uploader.json#ConfigCachePath` — по умолчанию у обоих один и тот же путь. |
| `ConfigCheckIntervalSeconds` | Как часто перечитывать `ConfigCachePath`. Применяется на лету всё, включая `DownscaleWidth`/`DownscaleHeight` — при смене разрешения закрывается текущий сегмент и чистится pre-roll буфер, перезапуск процесса не нужен (см. `architecture.md`). |

**`activity` (H9)** — тоже ключ конфига хоста/группы (веб-UI, «Активное окно»):
что Capture пишет об активном окне рядом с видео — `full` (имя процесса и
заголовок окна, по умолчанию), `process` (только процесс) или `off`. Смены окна
(не чаще раза в секунду, до 2000 на сегмент) уходят в `.mp4.json` сегмента,
сервер раскладывает их для поиска по окнам и подписей в плеере. Заголовки —
содержимое экрана (темы писем, имена файлов): поиск по ним пишется в журнал
доступа (`activity.search`), как и поиск по консоли. Windows — активное окно
сессии пользователя; Linux — EWMH (`_NET_ACTIVE_WINDOW`), то есть нужен
менеджер окон, который его выставляет (GNOME, KDE, XFCE).

**`showCursor` (0.14.3)** — ключ конфига хоста/группы (веб-UI, «Курсор мыши на
видео»), по умолчанию `true`: Capture рисует указатель мыши на кадре (Windows —
`GetCursorInfo` + `DrawIconEx`, Linux — XFixes, `libXfixes.so.3`; нет библиотеки —
курсор не рисуется, запись идёт). Рисуется **после** детектора движения — само
движение мыши запись не открывает. На уменьшенном кадре курсор мельче, но не
меньше 16 px.

**`schedule`, `excludeProcesses`, `excludeTitles` (H8)** — ключи конфига
хоста/группы (веб-UI: «Записывать только», «Пауза, когда активна программа»,
«Пауза, когда заголовок окна содержит»):

```json
{
  "schedule": [{ "days": [1, 2, 3, 4, 5], "from": "09:00", "to": "18:00" }],
  "excludeProcesses": ["KeePass", "1cv8"],
  "excludeTitles": ["Сбербанк Онлайн"]
}
```

- `schedule` — окна записи по часам **станции**; дни ISO (1 = пн … 7 = вс);
  `from` > `to` — через полночь (22:00–06:00 «пт» — с вечера пятницы до утра
  субботы); `00:00`–`00:00` — весь день. Нет ключа или пустой массив — запись
  всегда. Если расписание задано, но агент не разобрал ни одного окна, он не
  пишет вовсе: ошибка в сторону «не записывать».
- `excludeProcesses` — имя процесса без учёта регистра, `.exe` необязателен
  (Linux: имя из `/proc/<pid>/comm`, обрезанное до 15 символов, сравнивается с
  началом правила). `excludeTitles` — подстрока заголовка без учёта регистра.
- `excludeSites` / `includeSites` (0.14.3, «Пауза, когда открыт сайт», «Записывать
  только когда открыт сайт») — домен активной вкладки браузера вместе с
  поддоменами: `sberbank.ru` — и `online.sberbank.ru`, но не `notsberbank.ru`;
  правило можно вписать как есть (`https://www.sberbank.ru/x`, `*.sberbank.ru` —
  схема, `www.`, путь и порт отбрасываются). Надёжнее заголовка: сайт не может
  назваться иначе. Домен знает только Windows-агент 0.14.3+ (адресная строка
  через UI Automation, `BrowserSite`); на Linux и у старых агентов
  `excludeSites` не срабатывает, а `includeSites` не совпадает никогда. Первые
  доли секунды нового окна браузера, пока домен не прочитан, правило не
  действует — для строгого исключения добавьте и правило по заголовку.
  Браузеры агент определяет сам: встроенный список плюс зарегистрированные в
  системе (`HKLM`/`HKCU\SOFTWARE\Clients\StartMenuInternet`, раз в час).
- Пока вне расписания или на переднем плане исключённое окно — пауза: кадры не
  снимаются, открытый сегмент закрывается, pre-roll очищается, в активность
  (H9) окно не попадает, в лог агента — только причина паузы, без имени окна.
- Сервер проверяет ключи (до 50 окон расписания, до 200 правил по 128 символов).

**`consoleLiveIntervalSec` (0.12)** — как часто агент консоли (Linux и
Windows) шлёт ещё открытую сессию, секунды, 10–3600, по умолчанию 60 (веб-UI:
«Консоль: отправка открытой сессии»). Доходит до агента заголовком ответа на
выгрузку консоли — у консольного агента нет heartbeat, поэтому новое значение
он применяет после ближайшей выгрузки. При ~300 агентах и 60 с — около 5
запросов в секунду на сервер, только от станций, где сессия открыта и в ней
что-то происходит.

**`includeProcesses`, `includeTitles` (0.13)** — обратное `excludeProcesses` /
`excludeTitles`: если задано хоть одно правило, экран пишется только пока на
переднем плане одна из этих программ или окно с подстрокой в заголовке («или»
между списками). Окно не определить — не пишется. Исключения действуют поверх
(включённое, но исключённое окно не пишется). Те же правила записи и пределы,
что у исключений.

В веб-UI (0.13) пользователи и программы выбираются из тех, что уже
встречались на хосте или хостах группы за 90 дней (`GET /api/fleet/{id}/known`,
`GET /api/groups/{id}/known`), можно вписать своё; расписание — сеткой «день ×
час» (окна не по целым часам — по-прежнему текстом). В «Инфо» хоста —
пользователи (видео и консоль, когда последний раз) и время по программам за 30
дней (`GET /api/inventory/{name}/people`; время программы — от смены окна до
следующей в сегменте, последней — до конца сегмента).

**`pauseVideo`, `pauseConsole`, `pauseUntil`, `pauseReason` (0.13)** —
«Снять с записи» (веб-UI: кнопка в шапке хоста или секция «Пауза записи» в
конфиге группы/хоста). `pauseVideo: true` — процесс записи экрана не пишет
(агент на связи, отметка «не пишет — по конфигу»); `pauseConsole: true` —
сервер не сохраняет консоль хоста (консольный агент конфиг не читает, сессии
приходят и отбрасываются с `skipped`). `pauseUntil` — дата `yyyy-MM-dd`
включительно (время станции), после неё запись возобновляется сама; нет —
бессрочно. `pauseReason` — до 200 символов, видна в «Хостах». Пауза группы у
хоста снимается `false` в его конфиге («Вернуть запись» так и делает).

**`serviceConnections` (0.13)** — служебные подключения в «Консоли» (веб-UI:
«Консоль и SSH» в конфиге группы/хоста или кнопка «Скрыть похожие» в открытой
сессии). Массив до 100 правил `{user, from, command, action, note}`: `user` —
пользователь (как в `excludeUsers`, доменное имя совпадает с коротким), `from` —
IP или подсеть (`10.20.30.0/24`), `command` — с чего начинается **каждая**
команда сессии (строки `linux-exec` — без времени и каталога), `action` —
`hide` (по умолчанию: запись сохраняется с пометкой `service`, список
`/api/terminal-sessions?service=hide` её не отдаёт, `only` — только такие) или
`drop` (сервер отвечает агенту `skipped`, как при `excludeUsers`). Пустое поле —
любое значение, но `user` или `from` обязателен. Применяет только сервер, к
записям ввода (`terminal-input`): идущая сессия, пока она идёт, только
скрывается — `drop` срабатывает на последнем куске, если у сессии нет вывода.
После правки конфига группы/хоста или смены группы пометка уже записанных
сессий пересчитывается по новым правилам (`drop` задним числом не удаляет).
Список у хоста заменяет список группы целиком, как и остальные поля.

**`skipTranscriptOrigins` (0.16)** — какие транскрипты PowerShell с Windows
сервер не сохраняет (веб-UI: «Консоль и SSH» → «Не сохранять PowerShell,
запущенный…»). Массив кодов происхождения, которые присылает агент:
`automation` (планировщик заданий, службы), `sql-agent`, `local` (рабочий стол
станции, в том числе RDP), `winrm` (PowerShell Remoting), `unknown` (нет событий
4688). `ssh` не отключается. По умолчанию пусто — сохраняется всё. Сервер
отвечает агенту `skipped`, как при `excludeUsers`; записи Linux и агентов до
0.16 (без метки) не фильтруются. В выводе скриптов автоматизации бывают пароли
и токены — если это важно, отключите `automation`.

**`queueMaxAgeDays` (0.13)** — сколько дней станция хранит невыгруженные
записи, если сервер недоступен: 0–3650, по умолчанию 30, 0 — без срока (веб-UI:
«Хранение на станции»). Старше — удаляются (раз в 10 минут) и считаются
потерей (`droppedSegments`) — чтобы месяц без сервера не забил диск станции.
Видео-агент берёт срок из кэша конфига heartbeat (`ConfigCachePath`), консольный
— из заголовка `X-Watcher-Queue-Max-Age` ответа на выгрузку и сохраняет его в
`queue-max-age-days` рядом с учёткой; оба переживают перезапуск без сервера. На
станции, ни разу не видевшей сервер, действует `QueueMaxAgeDays` агента (30).
Запись консоли удаляется, только когда старше срока все её файлы (идущая сессия
не трогается). Квота по размеру (`QueueMaxBytes`) — отдельно.

Что собирает агент и как это сократить — сводка для ИБ и юристов заказчика:
`docs/data-collected.md`.

**`AllowUsers`/`ExcludeUsers` (Фаза 5)** — НЕ ключи `Watcher.Capture.json`, а
часть того же JSON-блоба, что приходит через `ConfigCachePath` (эффективный
конфиг хоста/группы с сервера, см. выше). Редактируются в веб-UI
(`#/settings/groups/<id>/config`/`#/hosts/<имя>/config`, поле со списком пользователей
через запятую), не руками в файле. `AllowUsers` непустой — захват только для
перечисленных (whitelist, главнее `ExcludeUsers`); иначе `ExcludeUsers`
непустой — захват для всех, кроме них; ни один не задан — для всех, как и до
этой фазы. На Windows те же правила применяет служба `WatcherSessionService`
(Задача D3): исключённому пользователю Capture не запускается вовсе, а
разрешённому снова — запускается без перелогина; изменение доходит до станции
за ~1–1,5 мин (heartbeat + тик службы). Подробности — `docs/architecture.md`,
разделы `Watcher.Capture` и `Watcher.SessionService`.

## Станция, uploader: `C:\Watcher\Watcher.Uploader.json`

На Windows этот файл читает служба `WatcherSessionService` (выгрузка внутри
неё с Задачи D2), на Linux — процесс `Watcher.Uploader`. В нём токен регистрации,
поэтому установщик (MSI) ставит на него ACL только SYSTEM и Administrators —
открыть его можно только из PowerShell от администратора.

```json
{
  "Uploader": {
    "QueueDir":    "C:\\ProgramData\\Watcher\\queue",
    "SentDir":     "C:\\ProgramData\\Watcher\\sent",
    "LogDir":      "C:\\ProgramData\\Watcher\\logs",
    "ServerUrl":   "https://watcher.internal",
    "PollIntervalSeconds": 10,
    "FileQuietSeconds": 5,
    "MaxRetryDelaySeconds": 300,
    "DeleteAfterUpload": true,
    "SentRetentionDays": 1,
    "SentMaxBytes": 1073741824,
    "QueueMaxBytes": 0,
    "EnrollToken": "wenr_...",
    "CredentialPath": "C:\\ProgramData\\Watcher\\agent\\credential.json",
    "HeartbeatIntervalSeconds": 60,
    "ConfigCachePath": "C:\\ProgramData\\Watcher\\config\\capture-config.json",
    "LogRetainedDays": 14,
    "LogFileSizeLimitMb": 10,
    "FfmpegPath": "C:\\Watcher\\ffmpeg.exe",
    "OrphanMinAgeMinutes": 30
  }
}
```

| Ключ | Назначение |
|---|---|
| `QueueDir` | Откуда читать готовые mp4. Должна совпадать с `Watcher.Capture.json#QueueDir`. |
| `SentDir` | Куда переносить успешно загруженные (если `DeleteAfterUpload=false`). |
| `LogDir` | Логи uploader (Serilog rolling-file). Файл `uploader-YYYYMMDD.log`. |
| `ServerUrl` | Куда слать. С `http://` или `https://`. `http://` на не-localhost — предупреждение в логе агента при каждом старте и в веб-UI (`#/hosts`, колонка «Соединение»): видео и секрет учётки идут открытым текстом. Для `https://` с самоподписанным сертификатом сервера — см. `docs/install.md`, «HTTPS для агентов» (`CACERT` у MSI). |
| `PollIntervalSeconds` | Как часто проверять очередь. 10 — норм. |
| `FileQuietSeconds` | Сколько секунд файл должен быть «тих» (не модифицироваться) перед отправкой. Защита от отправки полузаписанного. |
| `MaxRetryDelaySeconds` | До скольки увеличивать паузу при сетевых ошибках. Экспоненциальный backoff. |
| `DeleteAfterUpload` | `true` (по умолчанию) — удалять после успеха. `false` — переносить в `sent/`. |
| `SentRetentionDays` | Сколько дней держать в `sent/` если он используется. |
| `SentMaxBytes` | Лимит размера `sent/`. 1 ГБ = 1073741824 байт. |
| `QueueMaxBytes` | Жёсткий порог на `queue/` (Фаза 5) — ещё не отправленное. `0` — без лимита (дефолт). При превышении удаляются самые старые «тихие» сегменты (не те, что Capture мог ещё дозаписывать); счётчик удалённых уходит в heartbeat как `droppedSegments`, виден в `#/hosts`. |
| `QueueMaxAgeDays` | 0.13: невыгруженное старше стольких дней удаляется (`droppedSegments`), `0` — без срока, по умолчанию 30. `queueMaxAgeDays` в конфиге группы/хоста главнее. |
| `EnrollToken` | Токен регистрации из веб-UI (Настройки → Агенты, Задача G1). Пишет установщик из свойства MSI `ENROLLTOKEN`. Агент меняет его на свою учётку (`POST /api/enroll`) и дальше ходит с ней; после отзыва учётки тем же токеном заново не регистрируется — нужен новый. |
| `CredentialPath` | Где агент хранит свою учётку (секрет). Windows — каталог с ACL только SYSTEM и Administrators (создаётся агентом), Linux — `700`/`600`. Удалить файл — агент зарегистрируется заново по `EnrollToken` (сервер пометит это как повторную учётку). |
| `HeartbeatIntervalSeconds` | Как часто слать `POST /api/heartbeat` (host/ip/версия/`droppedSegments`). 60 — при ~300 агентах это 5 запросов/сек на сервер, эндпоинт сделан дешёвым специально под эту нагрузку. Ответ сервера несёт `{configVersion, config}` — эффективный конфиг хоста: конфиг его группы, поверх него по полям — настройки самого хоста (с 0.12; раньше конфиг хоста заменял групповой целиком); ключа нет ни там, ни там — агент берёт своё значение по умолчанию; группа хосту назначается отдельно, в веб-UI `#/hosts` (см. `docs/architecture.md`, «Идентификация хостов» и «Централизованная конфигурация»), heartbeat её не трогает. |
| `ConfigCachePath` | Куда писать конфиг, пришедший в ответе heartbeat (конфиг группы и хоста из веб-UI, склеенный по полям, см. `docs/architecture.md`, «Централизованная конфигурация»). Известному хосту сервер всегда отвечает объектом, хотя бы `{}` — очистка конфига группы доходит до станции. `Watcher.Capture` реально читает и применяет этот файл (`ConfigReload.cs`, Фаза 4) — на лету, без перезапуска процесса, включая смену разрешения; подробности в `docs/architecture.md`. |
| `LogRetainedDays` | Сколько последних дневных лог-файлов хранить, остальные удаляются автоматически. |
| `LogFileSizeLimitMb` | Лимит размера одного лог-файла. При превышении в тот же день создаётся новый файл (`uploader-YYYYMMDD_001.log` и т.д.). |
| `FfmpegPath` | ffmpeg для разбора сегментов, оборванных убийством Capture (выход из системы, выключение, падение) — `.rec.mp4` и mp4 без `.json`. Пишут установщик Windows (`<InstallDir>\ffmpeg.exe`) и `install-capture-linux.sh` (`ffmpeg`). Пусто (дефолт в коде) — разбор выключен, такие файлы лежат в очереди до квоты. |
| `OrphanMinAgeMinutes` | Сколько минут файл без `.json` не должен меняться, чтобы считаться брошенным. 30 по умолчанию; проверка раз в 10 минут и при старте. |

После изменения конфига нужно перезапустить:
```powershell
# Watcher.Capture.json — Capture перечитает после перезапуска процесса,
# служба поднимет его сама за ≤15 сек (watchdog):
Get-Process Watcher.Capture | Stop-Process -Force
# Watcher.Uploader.json — выгрузка живёт в службе:
Restart-Service WatcherSessionService
```

## Станция Linux: `~/.local/opt/watcher/Watcher.Capture.Linux.json` / `/opt/watcher-uploader/Watcher.Uploader.json`

Те же ключи и смысл, что у Windows-агента выше. С Задачи G1c Capture — служба
пользователя (`systemd --user`, конфиг в его `~/.local/opt/watcher/`), Uploader —
системная (root, `/opt/watcher-uploader/`, конфиг `600`). Оба файла пишет
`install-capture-linux.sh`. Отличия:

| Ключ | Отличие от Windows |
|---|---|
| `QueueDir`/`ConfigCachePath` | Общие для всех пользователей станции: `/var/lib/watcher/queue` (`1733`) и `/var/lib/watcher/config/capture-config.json` — оба процесса должны смотреть в одно место, установщик пишет их в оба конфига. `LogDir` у Capture — свой (`~/.local/share/watcher/logs`, по умолчанию), у Uploader — `/var/lib/watcher/logs`. |
| `SentDir`/`CredentialPath` | `/var/lib/watcher/sent`, `/var/lib/watcher/agent/credential.json` (`700`/`600` root). |
| `FfmpegPath` | `"ffmpeg"` (ищется в `PATH`, системный пакет), не абсолютный путь на вшитый `ffmpeg.exe`. |

Перезапуск после ручной правки конфига:
```bash
systemctl --user restart watcher-capture
sudo systemctl restart watcher-uploader
```

## Станция Linux, терминальный агент: `/opt/watcher-terminal-agent/appsettings.json` + `Watcher.TerminalAgent.json`

Два файла, не один: `appsettings.json` — бандлится вместе с бинарником
(нетронутые дефолты), `Watcher.TerminalAgent.json` рядом — пишет сам
`install-terminal-agent.sh` только если задан `--server-url` (при повторном
запуске без `--server-url` файл удаляется, выгрузка выключается — см.
`docs/install.md`). Оба грузятся как один конфиг (ASP.NET Core `IConfiguration`,
второй файл переопределяет поля первого).

```json
{
  "TerminalAgent": {
    "AuditLogPath": "/var/log/audit/audit.log",
    "BookmarkPath": "/var/lib/watcher-terminal-agent/bookmark.txt",
    "QueueDir": "/var/lib/watcher-terminal-agent/queue",
    "RawOutputDir": "/var/lib/watcher-terminal-agent/raw-output",
    "QueueSentDir": "/var/lib/watcher-terminal-agent/queue/sent",
    "RawOutputSentDir": "/var/lib/watcher-terminal-agent/raw-output/sent",
    "ServerUrl": "https://watcher.internal",
    "UploadQuietSeconds": 2,
    "QueueMaxBytes": 0,
    "RawOutputMaxBytes": 0,
    "QueueSentRetentionDays": 7,
    "QueueSentMaxBytes": 1073741824,
    "RawOutputSentRetentionDays": 7,
    "RawOutputSentMaxBytes": 10737418240,
    "SentRetentionScanIntervalMinutes": 30,
    "PollIntervalSeconds": 5,
    "AbandonedSessionTimeoutSeconds": 86400,
    "LogDir": "/var/lib/watcher-terminal-agent/logs",
    "LogRetainedDays": 14,
    "LogFileSizeLimitMb": 10
  }
}
```

| Ключ | Назначение |
|---|---|
| `AuditLogPath` | Куда `auditd` пишет события (ввод, 8a). Обычно не меняется. |
| `BookmarkPath` | Byte-offset последней прочитанной позиции `AuditLogPath` — переживает рестарт агента. |
| `QueueDir`/`QueueSentDir` | Готовые JSON-записи ввода (`kind: terminal-input`), ещё не отправленные / уже отправленные. |
| `RawOutputDir`/`RawOutputSentDir` | Сюда `watcher-term-wrap.sh` (8b, вывод) пишет `.out`/`.timing`/`.json`-тройки; агент читает их отсюда же (сам не пишет). |
| `ServerUrl` | Если `ServerUrl` пуст — выгрузка выключена, агент только собирает локально. `http://` на не-localhost — предупреждение в логе при каждом старте. |
| `UploadQuietSeconds` | Файл не трогается для выгрузки/квоты, если его mtime моложе этого порога (защита от гонки с ещё дописывающим процессом). |
| `QueueMaxBytes`/`RawOutputMaxBytes` | Жёсткий порог на неотправленное, `0` = без лимита. Разные дефолты по дизайну — ввод и вывод разного типичного размера, см. `docs/architecture.md`. |
| `QueueMaxAgeDays` | 0.13: срок хранения неотправленного (ввод, вывод, состояние живой выгрузки), `0` — без срока, по умолчанию 30. Присланный сервером (`queueMaxAgeDays`) главнее и сохраняется в `queue-max-age-days` рядом с учёткой. |
| `QueueSentRetentionDays`/`QueueSentMaxBytes`, `RawOutputSentRetentionDays`/`RawOutputSentMaxBytes` | Ротация `sent/`, отдельная пара на каждый из двух пайплайнов. |
| `SentRetentionScanIntervalMinutes` | Как часто гонять чистку `sent/`. |
| `PollIntervalSeconds` | Как часто агент проверяет `queue/`/`raw-output/` на новое для выгрузки. |
| `AbandonedSessionTimeoutSeconds` | Сессия без `USER_END` дольше этого — сбрасывается как зависшая (см. `SessionCollector.SweepAbandoned`, `docs/architecture.md`). |
| `LogDir`/`LogRetainedDays`/`LogFileSizeLimitMb` | Логи агента, та же схема ротации, что у остальных компонентов. |

Списка пользователей в этом файле нет: PAM/`script`-обёртка пишут всех, а
кого не сохранять — `allowUsers` / `excludeUsers` в конфиге группы/хоста на
сервере (`docs/architecture.md`, «Централизованная конфигурация»).

Перезапуск после ручной правки конфига:
```bash
sudo systemctl restart watcher-terminal-agent
```

## Станция Windows, SessionService: `C:\Watcher\Watcher.SessionService.json`

Служба `WatcherSessionService` ставится на любую Windows-станцию — она запускает Capture в сессии каждого пользователя и
выгружает очередь. Этот файл — локальные настройки самой службы; кого
писать (`allowUsers`/`excludeUsers`) она берёт из конфига хоста/группы в
веб-UI (Задача D3) — в сессии исключённого пользователя Capture не запускается.

```json
{
  "SessionService": {
    "CaptureExePath": "C:\\Watcher\\Watcher.Capture.exe",
    "LogDir": "C:\\ProgramData\\Watcher\\session-service-logs",
    "LogRetainedDays": 14,
    "LogFileSizeLimitMb": 10
  }
}
```

| Ключ | Назначение |
|---|---|
| `RunUploader` | `true` (по умолчанию) — служба выгружает очередь сама (Задача D2), конфиг выгрузки — `Watcher.Uploader.json` рядом. `false` — только запуск Capture. |
| `CaptureExePath` | Что запускать в сессии каждого залогиненного пользователя через `CreateProcessAsUser`. |
| `ConfigCachePath` | Откуда брать `allowUsers`/`excludeUsers` (D3), когда выгрузка выключена (`RunUploader=false`); при включённой — берётся `ConfigCachePath` из `Watcher.Uploader.json`, его же пишет heartbeat. По умолчанию `C:\ProgramData\Watcher\config\capture-config.json`. |
| `LogDir`/`LogRetainedDays`/`LogFileSizeLimitMb` | Логи службы, та же схема ротации, что у остальных компонентов. |
| `TerminalAudit:Enabled` | Консольный аудит сессий PowerShell (Задача F1; до 0.16 — только SSH) — пишет установщик (MSI `TERMINALAUDIT=1`, по умолчанию), он же включает политики транскрипции и аудит 4688 (без них включать нечего). Нужен `RunUploader=true`: сервер и токен регистрации — из `Watcher.Uploader.json`. Лог — в `uploader-*.log` (`Watcher.TerminalAudit`). |
| `TerminalAudit:TranscriptDir` | Папка транскриптов (`C:\ProgramData\Watcher\transcripts`) — та же, что `OutputDirectory` политики. |
| `TerminalAudit:CredentialPath` | Учётка агента вида «консоль» (`C:\ProgramData\Watcher\agent\terminal-credential.json`), отдельно от учётки видео. |
| `TerminalAudit:ScanIntervalSeconds` / `UnknownGraceMinutes` | Опрос папки (15 с) и сколько ждать событие 4688 для закрытого транскрипта (10 мин), затем он выгружается с `origin=unknown`. Незавершённое чтение истории Security откладывает выгрузку. `UnknownRetentionHours` до 0.16 больше не используется. |
| `TerminalAudit:OriginsPath` | Решения по конкретным файлам, по умолчанию `C:\ProgramData\Watcher\agent\transcript-origins.json`. |
| `TerminalAudit:ProcessHistoryPath` | Локальный кэш метаданных 4688: `C:\ProgramData\Watcher\agent\process-starts.json`, до 20 000 событий/48 ч. Командные строки не хранятся. |
| `TerminalAudit:DiagnosticsPath` | Сводка количеств Unknown по причинам и состояние сборщика: `C:\ProgramData\Watcher\agent\transcript-diagnostics.json`, без текста сессий. |
| `TerminalAudit:QuarantineDir` | Защищённый локальный карантин повреждённых транскриптов: `C:\ProgramData\Watcher\agent\transcript-quarantine`. Копии, попавшие туда до 0.16 как Unknown, агент выгружает с `origin=unknown` и удаляет. |
| `TerminalAudit:QuarantineDays` / `QuarantineMaxBytes` | 7 дней / 268435456 байт (256 МиБ); допустимы 1–30 дней / 1 МиБ–1 ГиБ, значения ограничиваются. Дополнительно максимум 2000 копий; при нехватке ёмкости удаляются старейшие копии. При ошибке переноса исходник остаётся в активной папке, её суммарный размер этим лимитом не ограничен. |

Подробности классификации, кэша, причин и карантина — [transcript-classification.md](transcript-classification.md).

`Watcher.Capture.json`/`Watcher.Uploader.json` рядом не меняются — `Capture`
запускается с тем же конфигом, что и на обычной станции, просто per-session,
а `Uploader` остаётся общим на хост (см. `docs/architecture.md`).

Перезапуск после ручной правки конфига:
```powershell
Restart-Service WatcherSessionService
```

## Android-агент (Этапы 2–3)

У Android-агента нет файла конфигурации в репозитории: настройки вводятся на
устройстве при подключении и хранятся в приватных `SharedPreferences`
приложения (`com.watcher.agent`). Сервер новых ключей в `appsettings.json` для
Android не добавляет — Android-хост регистрируется тем же `POST /api/enroll`
(`kind: "android"`) и ходит тем же `POST /api/heartbeat`, что станции.

| Значение | Где задаётся | По умолчанию |
|---|---|---|
| Адрес сервера (`http`/`https`) | экран подключения в приложении | — (вводится) |
| Токен регистрации (`wenr_…`) | экран подключения (Настройки → Агенты на сервере) | — |
| Имя хоста | экран подключения, предзаполняется из модели устройства | `<производитель> <модель>` |
| Секрет агента (`wagt_…`) | выдаётся сервером при регистрации | хранится шифрованным (Android Keystore, AES-GCM) |
| Интервал heartbeat | ключ `heartbeat_interval_ms` в `SharedPreferences` | 60 000 мс |
| Кэш конфига (`config_version`/`config_hash`/`config_json`) | обновляется из ответа heartbeat | пусто, пока сервер не назначил конфиг |
| «Только Wi-Fi» для отправки событий (`wifi_only`) | переключатель на экране агента | выкл. |
| Интервал «тяжёлых» срезов — `device_state`, трафик (`event_collection_interval_ms`) | ключ в `SharedPreferences` | 300 000 мс (пределы 1 мин…1 сут) |
| Предел локальной очереди событий (`event_queue_max_rows`) | ключ в `SharedPreferences` | 5000 строк (пределы 100…50 000); старше 7 суток — удаляются |

Секрет агента на диск в открытом виде не попадает и не логируется: в `SharedPreferences` лежит только
шифртекст, ключ — в Android Keystore. Привязка «устройство ↔ сотрудник»
задаётся на сервере (веб-UI, `PATCH /api/fleet/{id}` поле `person`), агент её
не задаёт.

Настройки сбора событий (Этап 3) пока локальные: серверная схема конфига
(`AgentConfigValidation`) знает только поля станций и чужие ключи отвергает,
поэтому «только Wi-Fi» с сервера не задаётся — переключатель на устройстве.
Перенос в конфиг группы — вместе с android-схемой конфига (поздние этапы).

Запуски приложений (`UsageEvents`) и трафик по приложениям собираются только
при выданном **доступе к статистике использования** (специальный доступ, не
обычное разрешение): Настройки → Приложения → Специальный доступ → Доступ к
истории использования → Watcher; на экране агента есть кнопка туда. Без
доступа агент шлёт установки/удаления, перечень приложений и состояние
устройства. После Этапа 5 (агент — владелец устройства) доступ выдаётся без
участия пользователя.

Адрес сервера может быть обычным `http` (на корпоративной сети — как heartbeat
станций по LAN): в манифесте стоит `android:usesCleartextTraffic="true"`, иначе
на `targetSdk 28+` cleartext-HTTP блокируется. Где доступен `https` — указывать
`https`-адрес.

## Диагностика и подписанное обслуживание

Диагностика включена в персонально зарегистрированных Windows/Linux-агентах. Отдельный HTTP-запрос раз в 30 секунд,
экспоненциальный повтор до 15 минут; сервер ограничивает приём учётки разом
в 5 секунд и телом 64 КиБ. Настраиваемого удалённого Debug/raw-log режима нет.

Поля `Server` (по умолчанию пустые, обслуживание недоступно):

| Поле | Назначение |
|---|---|
| `MaintenanceSigningKeyPath` | Закрытый PEM P-256 ключ обслуживания |
| `MaintenancePreviousSigningKeyPath` | Прежний закрытый ключ на время смены pin агентов |
| `MaintenanceKeyPasswordFile` | Файл пароля зашифрованного PEM; закрыть от посторонних |

В контейнере: соответствующие `Server__...` переменные задают **пути**, ключи
и пароль монтируются read-only секретами. Агенту передаётся только открытый
SPKI DER в base64: `MAINTENANCEKEY` MSI,
`--maintenance-key` watcher-agent-setup. Нужен также существующий UpdatePublicKey.
Ключ обслуживания и ключ издателя пакетов должны быть разными.

API хоста `/api/hosts/{name}`:

| Метод и суффикс | Доступ и назначение |
|---|---|
| GET `/diagnostics?cursor=` | События по 50, ViewerScope |
| GET `/diagnostics/state` | Последняя связь и последний пакет, ViewerScope |
| POST `/diagnostics/request` | AdminOnly, запрос пакета всем активным учёткам хоста |
| GET `/maintenance` | AdminOnly, последние 50 разрешений |
| POST `/maintenance` | AdminOnly; credentialId, action, minutes (1..60), packageId для update, offline |

`offline=true` разрешает экспорт до первого отчёта о pin; правильный pin всё
равно проверяет агент. Удаление защищённого хоста через `/api/fleet/{id}`
ожидает результат uninstall. Для окончательно утраченной VM администратор
может явно передать `forgetProtected=true`: действие аудируется, legal hold
сохраняет приоритет. Это удаление серверной карточки, не удаление агента.

Порядок настройки, ротация, офлайн-обслуживание и восстановление:
[agent-protection.md](agent-protection.md).

## Групповое обновление защищённых агентов

Для уже настроенного GuardRepair используется существующий
`Server:MaintenanceSigningKeyPath` либо `MaintenancePreviousSigningKeyPath`,
соответствующий сообщённому pin агента. Цель задаётся обычной версией группы;
для Windows нужен подписанный MSI этой версии, для Linux — DEB/RPM. Отдельные
разрешения по хостам выпускаются автоматически. Без подходящего ключа или
пакета хост показывает blocked. Действующее обслуживание откладывает выдачу;
завершённое удаление блокирует самопереустановку.
